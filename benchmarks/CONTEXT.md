# benchmarks — performance and fidelity evidence
## Intent
Measure the evoxc rewrite against the frozen pre-rewrite JAX library on one box — timing, search quality and memory — with numbers anyone can regenerate, whichever side wins.
The committed old-vs-new verdict is FAIL (timing and quality) on the merged tree: `RESULTS.md` records the new side's `old/new` speed-up spanning 0.38x on `custom_pagie_p500` to 4.06x on `xor_p1000`, faster on 3 of the 7 comparable cases (`xor_p500` 2.59x, `xor_p1000` 4.06x, `xor3d_p1000` 1.07x) and slower on the two pop-100 func-fit rows, and `PERF_NUMPY.md` holds the hand-measured per-pass before/after pairs.
That verdict is computed, not written: `harness/protocol.py` derives it from the committed JSON, so flipping it needs new measurements, and `RESULTS.md` is never softened by hand.
Nothing here ships: the harness never imports both implementations in one process (JAX thread pools and evoxc/iree allocators would corrupt timings), it spawns one subprocess per run and renders its report from the measured JSON.
The benchmark environment is `jax` on the old side only and `evoxc` on the new side.

## Layout
- `run_benchmark.py` — CLI: plans the case matrix, spawns one worker subprocess per run, aggregates, regenerates `RESULTS.md`; `--list`/`--dry-run`/`--render-from-json` are numpy-free, and `--persist-note` writes a record's `meta.report_note` only.
- `cases.py` — the case matrix: problem, genome, NEAT config, budget and fitness target declared as plain data that both implementations consume.
- `harness/` — protocol (schema, aggregation, verdict), per-implementation adapters, worker entry point, report writer plus its presentation helpers and data-derived sections (see `./harness/CONTEXT.md`).
- `spikes/` — measured formulation evidence behind the depth-parallel design (`FORMULATION.md` + runnable micro-benchmark).
- `legacy_jax/` — frozen pre-rewrite JAX implementation: the timing baseline and numerical oracle (read-only, see its `CONTEXT.md`).
- `results/` — machine-readable run records: eight committed evidence records beside git-ignored scratch `*.json`; provenance and never-edit rules in `./results/CONTEXT.md`.
- `RESULTS.md`, `THREADS.md`, `iree.md`, `results/xor3d_quality_2026-11-04.md` — generated reports, one per harness record, each rewritten only by the renderer that owns it.
- `PERF_NUMPY.md` — hand-maintained before/after record of three passes: the two numpy-interpreter passes (op-count; tiled func-fit evaluate plus RL rollout hoist) and the dependency-side A/B of the old pinned `evoxc` tag against the numpy-interpreter pass the tree now pins (`fe85a534`), with their wall, peak RSS, build and executed op counts, profile splits, cost rules and reproduce commands (`git archive` + one venv per leg for pass 3).
- `BACKENDS.md` — hand-maintained measured record of the `iree` leg on one IREE 3.13.0 llvm-cpu session (not an accelerator session).
- `GPU.md` — hand-written accelerator report whose measured block between `<!-- BEGIN MEASURED (gpu_measure.py) -->`/`<!-- END MEASURED (gpu_measure.py) -->` only `gpu_measure.py` ever rewrites; the rendered per-case tables belong there, and this file keeps only the current record's one summary line.
- `gpu_measure.py` — the accelerator CLI (`run`/`matrix`/`render`/`--list`) over the named targets, driving `gpu_targets.py` and `gpu_report.py`; `run` and `matrix` share `--xla-flags TEXT`.
- `gpu_targets.py` — its data half: the named target table (`numpy`, `iree-llvm-cpu`, `iree-rocm`, `xla-rocm`), the `PJRT_TARGETS` set, `XLA_WORKAROUND_FLAGS` (the command-buffer workaround both accelerator tools export and record), plugin resolution and the plugin fingerprint; stdlib-only at import so `--list`/`--help` stay numpy-free.
- `gpu_report.py` — its record half: the `tensorneat-gpu/1` schema, markers, tolerances, the `XLA_FLAGS (xla targets)` environment row and every rendered line of `GPU.md`'s block.
- `xla_plugin_probe.py` — standalone smoke gate for the `xla` adapter through a user-supplied PJRT plugin: a gate with exit codes, never a measurement.
- `backend_measure.py` — standalone one-configuration-per-process measurement (setup/build, 3 warmup + 20 timed generations, peak RSS); the protocol behind `BACKENDS.md`.
- `forward_measure.py` — the batch **forward-pass** protocol (`run`/`matrix`/`render`/`--list`): one forward pass of a whole population, new evoxc (`numpy`/`iree-rocm`/`xla-rocm`) against the frozen JAX baseline, one `(workload, target)` row per fresh process, build/setup reported beside the timing and never charged to a pass; writes the `tensorneat-forward/1` record and renders `FORWARD.md`'s marked block through `gpu_report.splice_block`. All four targets are in `DEFAULT_TARGETS`, so the shipped matrix is 7 workloads x 4 targets = 28 rows.
- `FORWARD.md` — hand-written forward-pass report whose measured block between `<!-- BEGIN MEASURED (forward_measure.py) -->`/`<!-- END MEASURED (forward_measure.py) -->` only `forward_measure.py` ever rewrites; every per-forward number belongs there, not here; it quotes the four-target session (`forward.json`, `8c63309`).
## Metric Protocol
Every number comes from one worker run of one `(case, impl, backend, repeat)` tuple.
- `compile_time_s` — one-off build/compile of the generation step: on the old side `jax.jit(pipeline.step).lower(state).compile()`; on the new side the first `Pipeline.step` call, which performs the evoxc build (it also advances the state by one generation, reported as `generations_consumed_before_timing`).
- warmup — `--warmup` generations run untimed and discarded before any measurement.
- `generation_ms` — wall clock of one `step` call *including* the host sync (`jax.device_get` on the old side, evoxc host materialisation on the new side), sampled over `--generations` generations after the warmup.
- `ms_per_generation` — median of `generation_ms`; `gens_per_second` = `1000 / median`.
- `rss_final_mb` — the per-run `resource.getrusage(RUSAGE_SELF).ru_maxrss` high-water mark, sampled after import (`rss_after_import_mb`), after compile (`rss_after_compile_mb`) and at process end (`rss_final_mb`); because it is a high-water mark, the three samples attribute memory to phases.
- quality — from the same timed run: per-generation `best_fitness` / `mean_fitness` / `valid_count` curves, `final_best_fitness`, and `generations_to_target` (first generation whose best fitness reaches the case's `fitness_target`; `null` means "not within the budget", rendered as `>N` in a per-repeat row).
- In an aggregated row `generations_to_target` is the median over the repeats that reached the target, and `gens_to_target_all` (per repeat, seed-sorted) is rendered beside it: every repeat reached prints the plain median, a partial reach prints `median (reached/total)`, and no reach prints `>N (0/total)` — `xor_p100`/old prints `78 (2/3)` (seeds `62/93/None`) and `xor3d_p100`/old prints `149 (1/3)`.
- A case may declare `gens_to_target=False` in `cases.py` (`cartpole_p100` does, because its horizon-capped return is already maxed out by the initial population and no reachable-yet-above-initial target exists); the worker then measures with `target=None`, the record's `quality.target` is `null`, and every table renders `n/a (no informative target)` instead of a reach claim.
- `cartpole_p100` declares `gens_to_target=False`, so its record stores `quality.target: null` and `RESULTS.md` renders `n/a (no informative target)` in both gens-to-target cells; a record measured before the flag existed would still carry the old `generations_to_target` and render a number.
- The quality curves also carry the untimed warmup generations, so 150 timed generations on the old side record 153 entries (`warmup + timed`; the new side records one fewer because its build consumes one), and `generations_to_target` is indexed against that longer curve — an old-side seed-42 XOR3d run therefore reaches `-0.05` at entry 149 while `final_best_fitness` is the value at entry 153.
- A per-case `final_best_fitness` is the median over the 3 repeats (seeds 42/43/44), not one seed: `xor3d_p100`'s published `-0.0894` is the median of `-0.0278` (seed 42), `-0.1224` (seed 43) and `-0.0894` (seed 44).
- repeats — repeat `r` uses `seed + r`, so repeats sample timing noise *and* search variance; per-case values are medians over repeats with min/max kept in JSON.
- load — measured conditions, never a verdict input: each worker records `os.getloadavg()` at start and end (`loadavg_start`/`loadavg_end`, optional keys) and `protocol.env_report()` records the document-build load average; the report prints them so a shared box is visible instead of implied.
- repeat spread — the headline prints the speed-up range `old_min/new_max … old_max/new_min` over the per-repeat medians next to the median, and `## Quality curves` prints one row per repeat plus the element-wise-median aggregate row: per-repeat spread is the honest uncertainty measure, a median alone is not.
- That range prints the pessimistic ratio first (`old_min/new_max` is the worst speed-up for the new side) and the headline column is titled `Speed-up range (worst–best)` accordingly: `xor_p100` shows `0.59x–1.37x`.
## Forward-Pass Protocol (`forward_measure.py`)
Every number in that protocol comes from one `run` of one `(workload, target)` tuple, in its own process.
- a *workload* is a case from `cases.py` (for its population and genome geometry: input/output width, `max_nodes`/`max_conns`, read-out) plus a sample count `S`: 4 for XOR, 500 for the Pagie tiling, 1 for an RL observation; one forward pass evaluates `population x S` rows through every individual's own network.
- `ms_per_forward` — mean/median/min/max of the `--passes` timed passes, each timed with `time.perf_counter()` *including* the host materialisation of the output block, after `--warmup` untimed passes; the ten per-pass samples are kept in the record.
- the input block is drawn once from `default_rng(seed)` and pre-placed on the device, so no transfer sits inside the timed region; the payload is the `setup()` population, fixed for the whole row.
- targets are `gpu_targets.TARGETS` verbatim (`numpy`, `iree-rocm`, `xla-rocm`) plus `jax`; all four are in `DEFAULT_TARGETS`, and a PJRT target's plugin is resolved once per matrix (`--pjrt-plugin`, then `$EVOXC_PJRT_PLUGIN`) and wired both into `compile_options["plugin_path"]` and the child's environment, never falling back to another backend.
- `xla-rocm` builds and runs because `Pipeline.setup()` runs the host setup graphs on the numpy reference backend and registers the real backend/device afterwards (`src/tensorneat/pipeline.py`, `fcbf677f`); each xla row logs its own `XLA backend allocating 143.77GiB … for BFCAllocator` reserve at client creation, so the leg needs ~144 GiB of free device memory, and `TF_XLA_HSACO_CACHE_DIR` is unset so it recompiles its kernel per process.
- `setup_s` and `build_s` are one-off and reported beside the timing, never charged to a pass (`Pipeline.setup()` + one `evoxc.build` on the new side, `algorithm.setup` + `vmap(transform)` + `jax.jit(...).lower().compile()` on the old side).
- `rows_per_second`/`forwards_per_second` are `rows * 1000 / median` and `1000 / median`; `peak_rss_mib` is the row process's high-water mark (one row per process is what makes it meaningful); `device_memory` is sampled at the *start* of a row, before that row's own device client exists, so it reads whatever else holds the device: the four-target `FORWARD.md` session spans 286–193 939 MiB used because a co-tenant held ~144 GiB (75 % of the device) intermittently, and that range must never be read as the record's own footprint.
- the JAX baseline pins `XLA_PYTHON_CLIENT_PREALLOCATE=false` before importing JAX and records the policy as `jax_allocator`: the default 75 % reservation of the shared 205.8 GB `MI300X VF` fails rows with `HIP_ERROR_OutOfMemory` and inflates their RSS.
- the numerical-agreement section holds every new-side target against the `numpy` leg on the same payload (`1e-6 + 1e-5 x |reference|`, same tolerance constants as `gpu_report`); the JAX side is not value-comparable by design, because it draws its own population from its own PRNG.
- a leg that cannot run is an `error` row with its message (never a missing row): `run` writes a record even on a traceback, and `matrix` synthesises one for a crash, a timeout, an `OSError` or a non-JSON child.
## Fairness Rules (binding)
1. One implementation per process: the old side loads JAX, the new side asserts `jax`/`torch` never entered `sys.modules` after `import tensorneat` (a built-in release-gate check).
2. Runs are strictly sequential — never two benchmark processes at once, one fresh interpreter per run.
3. Thread count is set identically for both sides: `--threads N` exports `OMP/MKL/OPENBLAS/NUMEXPR_NUM_THREADS=N` and, on the old side, `XLA_FLAGS=--xla_cpu_multi_thread_eigen=false intra_op_parallelism_threads=N`; the default `--threads 0` leaves runtime defaults ("as users run it") and `--threads 1` reproduces a thread-bound box.
4. Identical work: same seed, same case config (pop size, genome sizes, species size, mutation defaults), same generation budget and fitness target for both sides; `cases.py` declares the config as plain data that the builders consume, so the JSON record and the constructed objects cannot drift.
5. No logging inside the timed region: stdout/stderr are redirected to `os.devnull` for the warmup+timed loop on both sides, the new pipeline runs with `is_detailed=False`, and the harness drives the compiled `step` directly so the legacy `analysis()`/print path is never entered.
6. Compile is measured, not charged to generations: the one-off build is reported separately and the generation it consumes on the new side is excluded from the quality curve.
7. Same dataset: XOR/XOR3d literals; `CustomFuncFit` uses the same sampler settings (`num_samples=500`, box `[-1,1]^2`) — legacy draws from the global `np.random` (seeded explicitly before construction), the new side from `default_rng(seed)`: same distribution, different draws.
8. The measured baseline wins: the declared numbers in `../CONTEXT.md` are printed next to the measured old row for sanity, but the verdict compares against the old row measured in the same run on the same box.
## What Is Not Compared
- Trajectories or bitwise equality: the sides use different PRNGs (JAX `PRNGKey` vs evoxc splitmix64), so one seed identifies the same *workload*, not the same search. Numerical fidelity is `test/parity/`'s job.
- Accelerator numbers: the contract is CPU; `--backend iree|xla|tvm` rows are informational.
- Import time and visualization/codegen cost (only `rss_after_import_mb` is recorded).
- CartPole against the legacy side: the pre-rewrite library has no evoxc CartPole (its RL problems are gym/brax/mujoco based and need extra dependencies), so that case is new-only and marked `n/a` for old; its cost in the current record is 307.16 ms/gen, against 275.24 ms/gen in `PERF_NUMPY.md` pass 2 (`90d97b4`) and 381.73 ms/gen in the pre-fix record.
## Cross-implementation Config Parity (xor3d quality gap)
`Case.build` feeds one config dict to both stacks, so every value a case *sets* is identical; the xor3d `-0.25` plateau comes entirely from defaults the case dict leaves unset.
Genuine drift in class defaults (old -> new), both in `genome/gene/conn/default.py`: weight `mutate_rate` 0.2 -> 0.8, weight `replace_rate` 0.015 -> 0.1, weight clip `[-5, 5]` -> unclipped; the new `GeneAttr` class default (0.2/0.015) still matches the legacy numbers, only `DefaultConn` overrides them (NEAT-python values).
New-only structural caps with no legacy equivalent: `DefaultGenome.max_in_degree = max(initial in-degree, 4)` (4 for XOR3d's 3 inputs; the legacy genome has no per-node in-degree cap) and `max_depth = 16`.
Deliberate structural-mutation drift: the new side ships connection gates `conn_add=0.4` / `conn_delete=0.05` against the legacy 0.2/0.2, because equal rates delete freshly added connections at a higher acceptance rate (measured: xor3d pop 100 escapes the constant-0.5 basin on 13/20 seeds, the frozen oracle on 4/20).
Identical on both sides: hidden activation `ACT.sigmoid` (single-element option list), `init_hidden_layers=()` (a fresh genome is the fully connected input->output network, 3 edges for XOR3d), node add/delete rates 0.2/0.2, bias/response defaults and `[-5, 5]` bounds, crossover, distance (1.0/0.4, normalised by max gene count), every NEAT knob (species_size is a count of species *slots* in both, compatibility_threshold 2.0, genome_elitism 2, species_elitism 2, max_stagnation 15, spawn_number_change_rate 0.5), and the seed plumbing (one key per side from the same `seed + repeat`; the PRNGs differ by design).
`survival_threshold=0.01` selects the top-ranked member on both sides in practice: the new side clamps `floor(threshold * members)` to >= 1, the legacy side floors it to 0 and divides 0/0 into a NaN probability vector (JAX `choice` then yields index 0).
Both sides compose the four structural gates sequentially and independently, and both pair elite children with their own parents instead of cloning one champion into every elite slot.
`-0.25` is the trivial plateau (`sigmoid(0)=0.5` -> mse 0.25) and is also where the legacy side sits for its first ~75 generations of xor3d_p100, so the remaining pop-100 gap is a slower escape from a shared plateau, not a different starting point: the new side leaves it on xor3d_p500/p1000 and on xor3d_p100 seed 42 only.
## Verdict Rules
- timing PASS when `new_ms_per_generation <= old_ms_per_generation` for every case both sides ran (speed-up >= 1.00x).
- quality PASS when `new_final_best >= old_final_best - max(QUALITY_TOLERANCE_REL * |old_final_best|, QUALITY_ABS_TOL)` for every such case, with `QUALITY_TOLERANCE_REL = 0.10` and `QUALITY_ABS_TOL = 1e-3` owned by `harness/protocol.py`.
- The absolute floor exists because the relative rule degenerates at the optimum: `xor3d_p1000`'s old final best is `-1.4e-09` (rendered `-0.0000`), so the relative rule would demand the new side beat `-1.5e-09` while the `0.001` floor sets the threshold at `-0.001`, which is why the new side's `-1.7e-11` (rendered `-0.0000`) passes in `RESULTS.md`; `1e-3` therefore means "both at the optimum within 1e-3" and keeps every case whose old fitness is meaningfully below the optimum on the relative rule, so a real gap still fails: only `xor3d_p100` fails in the current `authoritative.json` (`-0.0894` old vs `-0.2500` new), while the pre-fix record also failed `xor3d_p500` (`-0.1789` vs `-0.2500`) and `custom_pagie_p500` (`-0.0064` vs `-0.0219`).
- The verdict renders the active tolerance (`max(10% × |old|, 0.001)`) in each quality-failure reason and in the `Sub-verdicts` line, and the report prints it in the headline and old-vs-new notes.
- overall PASS when both pass; `INCOMPLETE` while any run is `error`/`skipped` (listing them); otherwise FAIL with the offending rows named.
## How To Run
```
python benchmarks/run_benchmark.py --list
python benchmarks/run_benchmark.py --impl both --backend numpy --cases all --generations 150 --warmup 3 --repeats 3 --json benchmarks/results/authoritative.json   # regenerates the committed RESULTS.md
python benchmarks/run_benchmark.py --impl old --cases xor_p100 --generations 30 --repeats 1
python benchmarks/run_benchmark.py --impl new --backend numpy --cases xor_p100,xor_p1000
python benchmarks/run_benchmark.py --impl new --backend iree --cases xor_p500
python benchmarks/run_benchmark.py --render-from-json benchmarks/results/authoritative.json --out benchmarks/RESULTS.md   # reproduces the committed report: the record stores its own meta.report_note
python benchmarks/run_benchmark.py --render-from-json benchmarks/results/authoritative.json --out $TMPDIR/re-render.md
# self-describing companion report (its own H1 + the one-line note under the banner)
python benchmarks/run_benchmark.py --impl both --backend numpy --cases xor_p100,xor_p500,xor_p1000 --generations 150 --warmup 3 --repeats 2 --threads 1 --report-title "TensorNEAT benchmark — thread-bound sensitivity (XOR family, --threads 1)" --report-note "This is the thread-bound sensitivity run (\`--threads 1\`, the declared-contract condition) of the XOR family; the authoritative default-thread matrix is \`RESULTS.md\`." --out benchmarks/THREADS.md --json benchmarks/results/threads1.json
python benchmarks/run_benchmark.py --render-from-json benchmarks/results/iree.json --out benchmarks/iree.md   # reproduces the committed historical note, which the record stores
python benchmarks/run_benchmark.py --render-from-json benchmarks/results/authoritative.json --out benchmarks/RESULTS.md --report-note "<the committed scope note>" --persist-note   # only when the note itself changes: writes it into the record's meta, then renders
```
A single-case rerun never touches the committed evidence: point both outputs somewhere else, e.g. `python benchmarks/run_benchmark.py --impl both --backend numpy --cases xor3d_p100 --generations 150 --warmup 3 --repeats 1 --seed 42 --json $TMPDIR/x3d.json --out $TMPDIR/x3d.md` (~15 s both sides); `--json` alone would write the git-ignored scratch `results/latest.json` while `--out` would still regenerate `RESULTS.md`, so pass both.
A quality-only matrix is the same command with `--repeats 3 --seed 42`, which is exactly one repeat per seed for seeds 42/43/44 (repeat `r` uses `seed + r`): `--cases xor3d_p100,xor3d_p500,xor3d_p1000,custom_pagie_p500 --json benchmarks/results/<name>.json --out benchmarks/results/<name>.md --report-title ... --report-note ...` — that is how `results/xor3d_quality_2026-11-04.json` was measured, and on a pre-tiling tree that leg alone is a ~50-minute background job rather than a foreground short timeout.
`--json` (default `benchmarks/results/latest.json`) holds per-run and aggregated records; `--out` (default `benchmarks/RESULTS.md`) is the regenerated report; `--dry-run` prints the planned subprocess commands without running them.
`--report-title TEXT` overrides the H1 and `--report-note TEXT` adds one italic line directly under the banner; both are stored as `meta.report_title`/`meta.report_note` by the measurement path, both are honoured by `--render-from-json` (the flags win over the stored values), and passing neither reproduces the stored values (so a committed report re-renders with its own title and note).
`--persist-note` is the supported way to change a note on an existing record: it requires `--render-from-json` and `--report-note`, writes the note into that record's `meta.report_note` before rendering, re-reads the file and refuses to render if anything outside `meta` moved — the `runs`/`aggregated`/`verdict` bodies and every measured number stay byte-identical.
Every committed record stores its own note, so a bare `--render-from-json` reproduces each committed report's banner note.
`--render-from-json PATH` re-renders `--out` from an existing run record only: it recomputes `aggregated` and `verdict` from the stored `runs`, rebuilds `meta` from the stored document where present, spawns no worker and never rewrites the JSON; it re-probes only the code-scope dirty state (`meta.env.git_dirty`/`git_dirty_paths`) and keeps the stored `git_commit` as the measurement's provenance. It fails loudly (exit 2) on an unreadable file, a wrong/absent `schema` or a missing `runs` list — this is how the report text is iterated without re-measuring.
The reproduce block names the record the report was rendered from: a record `benchmarks/results/.gitignore` re-includes is committed evidence and the block says every table cell is traceable; a scratch record (the default `latest.json` or any other git-ignored JSON) is labelled as not committed.
`meta.command` is stored as `shlex.join([sys.executable, *sys.argv])`, so the reproduce block renders it verbatim and `shlex.split` of the rendered line returns exactly that argv; a record written before that change (unquoted `" ".join(argv)`) is re-quoted from `meta.report_title`/`meta.report_note` when it is rendered.
`--list`, `--dry-run` and `--render-from-json` all run on a numpy-free interpreter (`/usr/bin/python3`).
The worker prepends `benchmarks/legacy_jax` (old side) or `src` (new side) to `sys.path`, so an installed `tensorneat` never shadows the tree under test; the legacy side needs the `bench` extra (`jax`), the new side only `evoxc` + `numpy`.
The `iree` llvm-cpu leg is measured with `backend_measure.py` instead (one configuration per fresh process): `uv run --extra iree python benchmarks/backend_measure.py --backend numpy|iree --case xor --pop 100|500|1000`, plus `--opt-level O0` and the coverage-smoke commands listed in `BACKENDS.md`.
The accelerator matrix is `gpu_measure.py`, not the harness: `python3 benchmarks/gpu_measure.py --list` is numpy-free, one row is `uv run --extra iree python benchmarks/gpu_measure.py run --case xor_p500 --target iree-rocm --json $TMPDIR/row.json`, and the committed `GPU.md` block is regenerated by the `matrix` and `render` commands in `GPU.md`'s `## Reproduce` — never by re-rendering a record you did not measure.
An `xla` target needs a PJRT C API plugin, which the `xla-rocm` extra installs as part of the sync: `uv sync --extra iree --extra xla-rocm` (or `--all-extras`) resolves the locked `jax-rocm7-pjrt==0.10.2`, which leaves `xla_rocm_plugin.so` under `.venv/lib/python3.12/site-packages/jax_plugins/xla_rocm7/`, named by `--pjrt-plugin PATH` or `$EVOXC_PJRT_PLUGIN` (a wheel installed by hand with `uv pip install --no-deps` is untracked, so a later `uv sync` prunes it).
`uv run python benchmarks/xla_plugin_probe.py --pjrt-plugin "$EVOXC_PJRT_PLUGIN"` is the one-command `xla` smoke gate (~10 s).
An `xla` row also exports `XLA_FLAGS=--xla_gpu_enable_command_buffer=WHILE` by default (`gpu_targets.XLA_WORKAROUND_FLAGS`), because on this box a generation graph's long `while` intermittently SIGSEGVs inside `PJRT_LoadedExecutable_Execute`/`hipGraphLaunch` under FUSION command-buffer capture; `--xla-flags TEXT` overrides it on `run` and `matrix` of both `gpu_measure.py` and `forward_measure.py`, and `--xla-flags ''` measures without it (the variable is then removed from the child environment, never inherited).
`matrix` forwards the flag to each row child in the `--xla-flags=VALUE` form, so a value beginning with `--` (the default does) has to be written `--xla-flags=VALUE` rather than as two tokens — the space form makes every row child exit 2 in argparse before measuring.
The value is recorded per row (`record["xla_flags"]`, `null` for a target that does not use XLA) and per document (`meta["xla_flags"]`, `null` when no planned target is an `xla` target), and both `gpu_report.py` and the forward renderer print one `XLA_FLAGS (xla targets)` environment row that reads "not recorded (record predates the workaround)" for a record whose `meta` carries no such key.

The batch **forward pass** is `forward_measure.py`, a separate protocol: `python3 benchmarks/forward_measure.py --list` is numpy-free, one row is `uv run --all-extras python benchmarks/forward_measure.py run --workload xor_p500_s4 --target iree-rocm` (~8 s), and the committed `FORWARD.md` block is regenerated by `uv run --all-extras python benchmarks/forward_measure.py matrix --workloads all --targets numpy,iree-rocm,xla-rocm,jax --passes 10 --warmup 3 --pjrt-plugin "$EVOXC_PJRT_PLUGIN" --json benchmarks/results/forward.json --out benchmarks/FORWARD.md` (~3 min for 28 rows) and re-rendered by `uv run --all-extras python benchmarks/forward_measure.py render --json benchmarks/results/forward.json --out benchmarks/FORWARD.md`.
`--targets` defaults to `numpy,iree-rocm,xla-rocm,jax`, so the shipped matrix now includes the `xla` leg; it needs `--pjrt-plugin PATH` or `$EVOXC_PJRT_PLUGIN` (the extra's plugin wheel) and `matrix` resolves that once up front, so a default matrix without a plugin exits 2 with the named `PluginError` instead of measuring.
## Notes for Agents
- `--list`, `--dry-run` and `--render-from-json` must work on an interpreter without numpy: `cases.py` is stdlib-only at module scope and `harness/protocol.py` guards its numpy import (`np = None`), so keep new module-scope imports on the numpy-free paths clean.
- A failing run is always an `error`/`skipped` row, never a missing row: `harness/worker.py` writes its record even on a traceback, and the CLI synthesises a row when a worker dies without writing one.
- Cheap protocol check for any new record: the old side is deterministic, so a rerun of a case reproduces its `authoritative.json` `final_best_fitness` bit-for-bit while only the new-side rows may move.
- Generation accounting is verifiable from a record: `generation_ms` holds exactly `timed_generations` samples (150 on both sides), the old-side curve holds `warmup + timed` entries and the new-side curve one fewer because its build consumes a generation (`generations_consumed_before_timing` 1 versus 0).
- `benchmarks/results/.gitignore` keeps `results/*.json` untracked except the eight records the committed reports were rendered from, which are evidence and must never be hand-edited (see `./results/CONTEXT.md`); `RESULTS.md`, `THREADS.md`, `iree.md`, `results/xor3d_quality_2026-11-04.md` and the interior of `GPU.md`'s measured markers are committed evidence only ever rewritten by `run_benchmark.py`/`gpu_measure.py`, while `BACKENDS.md`/`PERF_NUMPY.md`/`GPU.md`'s prose are hand-written measurement records.
- `RESULTS.md` is the measured default-thread matrix (both sides, environment fingerprint with CPU model/cores/RAM/versions/git SHA + dirty flag/thread settings/load average, headline table with median speed-up / per-repeat range / quality overlap, data-derived win/lose narrative with the memory paragraph, per-repeat quality curves, companion pointers); `THREADS.md` and `iree.md` are the same renderer on their own records and titles, and all three keep the `--report-note` that scopes them to their tree.
- The environment row's dirty flag is computed over the **code under test only** (`protocol.GIT_DIRTY_PATHS`: `src/`, `benchmarks/harness/` (incl. `worker.py`), `benchmarks/legacy_jax/`, `benchmarks/cases.py`, `benchmarks/run_benchmark.py`, `benchmarks/backend_measure.py`, `benchmarks/gpu_measure.py`, `test/`, `pyproject.toml`, `uv.lock`, `.python-version`), with `protocol.GIT_EVIDENCE_PATHS` (`RESULTS.md`, `THREADS.md`, `iree.md`, `results/`, `BACKENDS.md`, `GPU.md`, `spikes/`) never counted: the harness writes its own report and JSON while it samples the fingerprint, so a full-tree `git status` always called a clean measurement "dirty". The row names up to `GIT_DIRTY_PATH_LIMIT` offending paths (`(dirty: src/... +N more)`) and renders a clean tree as `(clean — generated report artifacts are not counted)`; a change to the dirty scope is a protocol change and `RESULTS.md` is regenerated with it.
- `loadavg_start`/`loadavg_end` are optional per-run keys: JSON written before they existed still aggregates and renders (`loadavg_summary` reports `n_runs = 0` and the report says `n/a (not recorded)`), and the schema stays `tensorneat-bench/1`.
- The `## Environment` table always carries the shared-box caveat sentence: measurement conditions are stated, and repeat spread is the uncertainty measure — never drop the caveat or replace a spread with a single median.
- A backend whose runtime is absent (for example `iree` without `iree-base-compiler`/`iree-base-runtime`) becomes an `error` row with the backend's message; the rest of the matrix still runs and the verdict stays `INCOMPLETE`, never a crash.
- The `## What is not compared` section says the old-vs-new verdict is numpy-only by protocol and that an accelerator row is informational (never part of the verdict); it points at `BACKENDS.md` only when that file sits next to the report, and that file is where the `iree` leg's measured numbers live (session-scoped: see `## Provenance`). `## Protocol` / `## How to reproduce` point at `THREADS.md` under the same rule, and a companion pointer never names the report's own file (a `THREADS.md` render drops the `THREADS.md` sentence). Both checks are `os.path.exists` on the report directory, so a checkout without those files stays truthful.
- The `## Headline` note and the `## How to reproduce` note say "the old side always runs on JAX" only when the document holds an old-side row; an all-new-side document (the `iree` attempt) states that no old-side row is recorded instead.
- The `## Why the new side wins and loses` section reads the measured speed-ups: it states which side won each case and each population, and rewrites its mechanism paragraph accordingly. Never hard-code the new side as the winner. The memory paragraph is generated the same way from the aggregated `rss_final_mb` (per-case new/old ratio, worst case, XOR growth, the import floor, then the mechanism).
- A case's `fitness_target` must be unreachable by the initial population, or `generations_to_target` reads 1 for every run and the column carries no information: XOR3d's `-0.05` sits below the trivial linear-baseline fitness of `-0.25`, and Pagie's `-0.01` sits below the ~`-0.049` the legacy first generation already reaches (its measured final best is ~`-0.005`). The rule is enforced by review, not by code.
- The `custom_pagie_p500` quality gap of the pre-fix record (`-0.0064` old vs `-0.0219` new) was a PRNG-driven search-trajectory difference, not a kernel difference: the two sides draw different samples from the same distribution, and the current record measures it inside the tolerance at `-0.0066` vs `-0.0064`.
- An `xla` row needs **both** wirings: the resolved plugin goes into `compile_options["plugin_path"]` for the build *and* into the row process's `EVOXC_PJRT_PLUGIN`, because `evoxc.backends.registry.get("xla")` calls `XlaBackend.check_available()`, whose `_load_plugin()` takes no options and therefore reads only the variable (the compile option wins in every later discovery call but cannot satisfy that probe). `--targets all` includes `xla-rocm` by name, so an all-target matrix needs the plugin too; the shipped default matrix (`DEFAULT_TARGETS`) stays `numpy,iree-llvm-cpu,iree-rocm`.
- The `XLA_FLAGS` workaround is an environment setting, never a compile option: XLA reads `XLA_FLAGS` at backend init, before the plugin builds the executable, so `--xla-flags` is exported into the row process's environment (and into every `matrix` child's) for `gpu_targets.PJRT_TARGETS` only, while a numpy/iree/jax row keeps its inherited environment untouched; `--xla-flags ''` removes the variable instead of setting it, so the without-workaround leg is a real absence.
- `results/fix_after.json` is a git-ignored scratch record carrying pass 2's case-scoped numbers (`custom_pagie_p500`, `cartpole_p100`, XOR p500, XOR3d p500 controls); it is not evidence and the report rendered from it lives in `$TMPDIR`.

## Constraints
- Python >= 3.11; harness dependencies are stdlib + `numpy` (plus `jax` on the old side only, via the `bench` extra).
- The compiled legs need `uv sync --extra iree`, which resolves IREE 3.13.0 (IREE 3.10/3.11 aborted in the HIP HAL on any while/scan loop, which is why an older session had no rocm row); `O2`/`O3` SIGSEGV inside `iree-compile` on this graph, so every shipped compiled record is the default opt level, `O0` or `O1`.
- An `xla` leg needs the `xla-rocm` extra (`uv sync --extra xla-rocm`), which installs the locked `jax-rocm7-pjrt==0.10.2` plugin wheel and keeps it for as long as the sync asks for that extra, plus `EVOXC_PJRT_PLUGIN` pointing at its `jax_plugins/xla_rocm7/xla_rocm_plugin.so`, or the same path through `--pjrt-plugin`; nothing falls back, so a missing plugin is an `error` row with the named `PluginError` (and `matrix` exits 2 when a planned PJRT target has no plugin), and a wheel installed by hand with `uv pip install --no-deps` is pruned by a later `uv sync` because no extra tracks it; the forward matrix now ships that leg by default, so a `matrix` run needs the plugin.
- A committed accelerator record must carry the plugin's identity whenever it measured an `xla` target (`meta.pjrt_plugin` and `record["pjrt_plugin"]`: absolute path, basename, `size_bytes`, `sha256`), rendered as basename, size and a 12-hex sha256 — a number measured against a different `.so` is a different experiment.
- Never edit `legacy_jax/` — a moving baseline makes every number meaningless.
- Never hand-edit a generated report or a committed record; a document that needs a scope line gets it from `--report-title`/`--report-note` at render time, and `--persist-note` stores it in the record so later renders keep it.
- Quote no number without the tree or session it came from, and read a record's CPU legs together with the `evoxc` pin it ran (`## Known Issues`): `RESULTS.md`, `THREADS.md`, `iree.md`, `BACKENDS.md`, `GPU.md` and `PERF_NUMPY.md` each describe a different tree, and only a fresh harness run may be described as HEAD.
- Nothing outside `benchmarks/` is read except the two implementation trees under test and the host fingerprint (`/proc/cpuinfo`, `/proc/meminfo`, `git rev-parse`/`git status` on this checkout); nothing outside `benchmarks/` is written.
- Files stay under ~1000 lines with one responsibility each: protocol / adapters / worker / reporter / report format / report sections / CLI / cases; the accelerator protocol is the one justified exception (`gpu_measure.py` carries its CLI plus the `run`/`matrix` drivers and `gpu_report.py` the schema plus every rendered line, both just over the ceiling after the `xla-rocm` target landed, with `gpu_targets.py` holding the target table, plugin resolution and plugin fingerprint).
`forward_measure.py` is the second documented exception: it is deliberately one file (the forward-pass protocol is a single deliverable, and half of it — the `run`/`matrix`/`render`/`--list` CLI plus the per-target builders — cannot be split without a second module that only it reads), so it carries the measure half and the render half that `gpu_measure.py`/`gpu_report.py` split, at ~1350 lines.
A forward-pass row that measures the JAX baseline must run `forward_measure._prepare_jax_allocator()` before importing `jax`: on a shared device the default XLA preallocation is 75 % of VRAM, and the rows failed with `HIP_ERROR_OutOfMemory` under it.
- A run that cannot work must fail loudly (`status="error"` with the traceback in JSON and a non-zero exit from the worker) — never a silently missing row.
## Test Strategy
There is no pytest suite in this node (`test/` is a sibling, read-only); its verification is running the harness, and every check below is cheap.
- `python benchmarks/run_benchmark.py --list` prints the 8-case matrix on an interpreter without `numpy` (exit 0); `--dry-run --impl both --cases xor_p100,cartpole_p100` prints both worker commands and skips `cartpole_p100/old` with a reason.
- Old-side smoke: `--impl old --cases xor_p100 --generations 5 --warmup 2 --repeats 1` gives one `ok` row (~30 ms/gen at pop 100) and the verdict `INCOMPLETE` because no new-side row exists.
- New-side failure path: `--impl new --cases xor_p100 --generations 2 --repeats 1` must render `status="error"` rows with the exception line and exit 1 — the CLI never crashes on a broken implementation.
- Unavailable-backend smoke (no IREE runtime): `--impl new --backend iree,numpy --cases xor_p100 --generations 2 --warmup 1 --repeats 1 --out $TMPDIR/x.md --json $TMPDIR/x.json` records the `iree` row as `error` and still measures and reports the `numpy` row; the matrix never aborts.
- Report smoke: `--impl both --backend numpy --cases xor_p100 --generations 2 --warmup 1 --repeats 1 --out $TMPDIR/report.md --json $TMPDIR/report.json` renders the headline, environment fingerprint and win/lose sections from those records, and both files are valid; write them into `$TMPDIR` so a smoke run never clobbers the committed `RESULTS.md`. The JSON must carry `loadavg_start`/`loadavg_end` on every run and the report's `Load average (1/5/15 min)` row must show them next to the document-build load.
- Fingerprint smoke: a report rendered while `RESULTS.md`/`THREADS.md`/`iree.md`/`results/*.json` are touched still renders `(clean — generated report artifacts are not counted)`; an uncommitted edit under `src/` or `benchmarks/harness/` flips `git_dirty` to true and names the path (`(dirty: src/... +N more)` for more than `GIT_DIRTY_PATH_LIMIT` paths). Verify with `--render-from-json benchmarks/results/authoritative.json --out $TMPDIR/re-render.md` on a clean tree and a 2-generation smoke from a deliberately dirtied source file, then restore that file exactly.
