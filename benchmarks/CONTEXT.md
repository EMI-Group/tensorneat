# benchmarks — performance and fidelity evidence
## Intent
Measure the evoxc rewrite against the frozen pre-rewrite JAX library on one box — timing, search quality and memory — with numbers anyone can regenerate, whichever side wins.
The committed verdict is FAIL on timing, and `RESULTS.md` carries that record's per-case numbers: the declared legacy baseline is 51/109/157 ms/gen at pop 100/500/1000, and on it the new side's `old/new` speed-up spans 0.16x on `custom_pagie_p500` (6.4x slower) to 2.88x on `xor_p1000`, faster on 3 of the 7 comparable cases.
The post-fix case-scoped numbers live in `PERF_NUMPY.md`: `custom_pagie_p500` at 833.81 ms/gen (0.65x of the old side measured in the same session) and `cartpole_p100` at 275.24 ms/gen, which leaves pagie the slowest cell per generation and the verdict unflipped until a full harness re-run replaces `RESULTS.md`/`authoritative.json`.
`RESULTS.md` is the honest measured record of that FAIL and is never softened by hand: its verdict is computed by `harness/protocol.py` from the committed JSON, so flipping it needs new measurements, not new prose.
Nothing here ships: the harness never imports both implementations in one process (JAX thread pools and evoxc/iree allocators would corrupt timings), it spawns one subprocess per run and renders `RESULTS.md` from the measured JSON.
`RESULTS.md` is generated evidence, never hand-edited.

## Layout
- `run_benchmark.py` — CLI: plans the case matrix, spawns the worker subprocesses, aggregates, regenerates `RESULTS.md`; `--list`/`--dry-run` are numpy-free, `--render-from-json` re-renders without a measurement, and `--persist-note` (with `--render-from-json` + `--report-note`) writes a note into a record's `meta` only.
- `cases.py` — the case matrix: the logical workload (problem, genome, NEAT config, pop/gen budget, target) declared as data and shared by both implementations.
- `harness/` — protocol (schema, aggregation, verdict rules), per-implementation adapters, worker entry point, report writer plus its presentation helpers (`report_format.py`) and data-derived sections (`report_sections.py`).
- `spikes/` — measured formulation evidence behind the depth-parallel design (`FORMULATION.md` + runnable micro-benchmark).
- `legacy_jax/` — frozen pre-rewrite JAX implementation; the timing baseline and numerical oracle (read-only, see its `CONTEXT.md`).
- `results/` — machine-readable run records: the five committed evidence records (`authoritative.json` for `RESULTS.md`, `threads1.json` for `THREADS.md`, `iree.json` for `iree.md`, `xor3d_quality_2026-11-04.json` for `xor3d_quality_2026-11-04.md`, `gpu_rocm_2026-11-05.json` for `GPU.md`) plus scratch `*.json` (e.g. the default `latest.json`), git-ignored and safe to delete.
- `results/xor3d_quality_2026-11-04.md` — generated post-search-quality-fix report of `xor3d_p100 xor3d_p500 xor3d_p1000 custom_pagie_p500` (numpy backend, both sides, 150 generations, seeds 42/43/44): headline table, environment fingerprint, verdict, per-repeat quality curves; the other generated reports (`RESULTS.md`, `THREADS.md`, `iree.md`) are untouched by it.
- `RESULTS.md` — the generated report of the pre-fix record: environment fingerprint, protocol, headline old-vs-new table (median speed-up plus the per-repeat range and quality overlap), per-case tables, verdict, win/lose narrative with the generated memory paragraph, per-repeat quality curves, declared baseline, non-comparisons, how to reproduce, and a `--report-note` line naming the fix commits that postdate it.
- `PERF_NUMPY.md` — hand-maintained record of the two measured numpy-interpreter passes: the op-count pass (`a697531` → the tree recorded at `f619f46`: XOR p100/p500/p1000, XOR3d p500) and the tiled func-fit evaluate plus RL rollout hoist (`ce5bb88` → `90d97b4`: `custom_pagie_p500`, `cartpole_p100`, XOR p500 and XOR3d p500 controls). Each pass carries its before/after wall time, peak RSS, build and executed op counts, the profile split, the changes and their measured deltas, the cost rules and the reproduce commands. Not generated; `RESULTS.md` stays the generated old-vs-new report.
- `gpu_measure.py` — standalone accelerator protocol (`run`/`matrix`/`render`/`--list`) for the four targets `numpy`, `iree-llvm-cpu`, `iree-rocm`, `xla-rocm`, plus raw `--device`/`--device-index`/`--target-backends`/`--rocm-target`/`--iree-compile-arg` passthrough, `--pjrt-plugin PATH` (forwarded to every row child, wired into both `compile_options["plugin_path"]` and the row process's `EVOXC_PJRT_PLUGIN`) and the optional `--trace N` lockstep trajectory (`run` and `matrix`, which forwards it to each child); its target table, plugin resolution and plugin fingerprint are `gpu_targets.py`, its record half (schema, markers, tolerances, fingerprint, block renderer) is `gpu_report.py`, its report is `GPU.md`, and the committed record is the 2026-11-05 `numpy` vs `iree` rocm matrix (`--warmup 3 --generations 20 --trace 14`).
- `gpu_targets.py` — the accelerator protocol's data half: the named target table (`numpy`, `iree-llvm-cpu`, `iree-rocm`, `xla-rocm`; a target is `{"backend", "device", "compile_options"}`), which targets need a PJRT C API plugin, the `--pjrt-plugin`/`$EVOXC_PJRT_PLUGIN` resolution order with its named error, and the plugin fingerprint (absolute path, basename, `size_bytes`, `sha256`); stdlib-only at import, so `--list`/`--help` stay numpy-free, and it holds no rendering and no measurement.
- `GPU.md` — hand-written accelerator report with a measured block between `<!-- BEGIN MEASURED (gpu_measure.py) -->`/`<!-- END MEASURED (gpu_measure.py) -->` that only `gpu_measure.py` ever rewrites (its block heading lists the record's own target labels, and its `## Per-generation trajectory` section appears only when a record carries an `ok` `--trace` trajectory): the committed block is the 2026-11-05 session `numpy` vs `iree` rocm over six cases, 12 `ok` rows and no blocked row, with the per-case 14-generation trajectory that backs the fidelity conclusion; the prose states that the device wins every row per generation (1.6x–17x) against a 9.0–15.1 s one-off `iree-compile` per shape (break-even 15 generations on `custom_pagie_p500` up to 504 on `xor_p100`), that the device leg's driver RSS (1903–2064 MiB) is higher than the numpy leg's (160–1310 MiB) on every row, and that generation 1 is the only equality gate.
- `BACKENDS.md` — measured compiled-backend evidence from one IREE 3.13.0 session: `iree` llvm-cpu compiles and runs every case and is 1.54x/5.47x/6.63x slower per generation than numpy at pop 100/500/1000, paying an 8.0–9.6 s `iree-compile` per static shape (74 % of a 23-generation wall clock at pop 100, 15–18 % at pop 1000); peak RSS favours `iree` only at pop 1000 once the resident compiler library is subtracted, `xla` has no PJRT plugin, and `O2`/`O3` SIGSEGV inside `iree-compile`; it carries the per-gate failure/fix record and the remaining exporter deferrals.
- `THREADS.md` — generated report of the committed `--threads 1` sensitivity run of the XOR family (`results/threads1.json`); the report points at it only when the file sits next to the report.
- `iree.md` — historical generated report of the pre-fix IREE attempt (`results/iree.json`): all 8 cases `error` in `Pipeline.setup` (including the `cartpole_p100 / iree` row), verdict `INCOMPLETE`; kept as the record of that state, superseded by `BACKENDS.md`, whose compiled-backend measurements belong to a later session on a later tree.
## Metric Protocol
Every number comes from one worker run of one `(case, impl, backend, repeat)` tuple.
- `compile_time_s` — one-off build/compile of the generation step: on the old side `jax.jit(pipeline.step).lower(state).compile()`; on the new side the first `Pipeline.step` call, which performs the evoxc build (it also advances the state by one generation, reported as `generations_consumed_before_timing`).
- warmup — `--warmup` generations run untimed and discarded before any measurement.
- `generation_ms` — wall clock of one `step` call *including* the host sync (`jax.device_get` on the old side, evoxc host materialisation on the new side), sampled over `--generations` generations after the warmup.
- `ms_per_generation` — median of `generation_ms`; `gens_per_second` = `1000 / median`.
- `rss_final_mb` — the per-run `resource.getrusage(RUSAGE_SELF).ru_maxrss` high-water mark, sampled after import (`rss_after_import_mb`), after compile (`rss_after_compile_mb`) and at process end (`rss_final_mb`); because it is a high-water mark, the three samples attribute memory to phases.
- quality — from the same timed run: per-generation `best_fitness` / `mean_fitness` / `valid_count` curves, `final_best_fitness`, and `generations_to_target` (first generation whose best fitness reaches the case's `fitness_target`; `null` means "not within the budget", rendered as `>N` in a per-repeat row).
- In an aggregated row `generations_to_target` is the median over the repeats that reached the target, and `gens_to_target_all` (per repeat, seed-sorted) is rendered beside it: every repeat reached prints the plain median, a partial reach prints `median (reached/total)`, and no reach prints `>N (0/total)` — `xor_p100`/old prints `78 (2/3)` (seeds `62/93/None`) and `xor3d_p100`/old prints `149 (1/3)`.
- A case may declare `gens_to_target=False` in `cases.py` (`cartpole_p100` does, because its horizon-capped return is already maxed out by the initial population and no reachable-yet-above-initial target exists); the worker then measures with `target=None`, the record's `quality.target` is `null`, and every table renders `n/a (no informative target)` instead of a reach claim.
- The committed pre-fix record was measured while `cartpole_p100` still declared `fitness_target=180`, so its stored `generations_to_target` 2/1/1 stays in `results/authoritative.json` and renders `1` in `RESULTS.md`; the suppression applies to every measurement recorded after the case gained the flag, and only a full re-measure would change that cell.
- The quality curves also carry the untimed warmup generations, so 150 timed generations on the old side record 153 entries (`warmup + timed`; the new side records one fewer because its build consumes one), and `generations_to_target` is indexed against that longer curve — an old-side seed-42 XOR3d run therefore reaches `-0.05` at entry 149 while `final_best_fitness` is the value at entry 153.
- A per-case `final_best_fitness` is the median over the 3 repeats (seeds 42/43/44), not one seed: `xor3d_p100`'s published `-0.0894` is the median of `-0.0278` (seed 42), `-0.1224` (seed 43) and `-0.0894` (seed 44).
- repeats — repeat `r` uses `seed + r`, so repeats sample timing noise *and* search variance; per-case values are medians over repeats with min/max kept in JSON.
- load — measured conditions, never a verdict input: each worker records `os.getloadavg()` at start and end (`loadavg_start`/`loadavg_end`, optional keys) and `protocol.env_report()` records the document-build load average; the report prints them so a shared box is visible instead of implied.
- repeat spread — the headline prints the speed-up range `old_min/new_max … old_max/new_min` over the per-repeat medians next to the median, and `## Quality curves` prints one row per repeat plus the element-wise-median aggregate row: per-repeat spread is the honest uncertainty measure, a median alone is not.
- That range prints the pessimistic ratio first (`old_min/new_max` is the worst speed-up for the new side) and the headline column is titled `Speed-up range (worst–best)` accordingly: `xor_p100` shows `0.59x–1.37x`.
## Fairness Rules (binding)
1. One implementation per process: the old side loads JAX, the new side asserts `jax`/`torch` never entered `sys.modules` after `import tensorneat` (a built-in release-gate check).
2. Runs are strictly sequential — never two benchmark processes at once, one fresh interpreter per run.
3. Thread count is set identically for both sides: `--threads N` exports `OMP/MKL/OPENBLAS/NUMEXPR_NUM_THREADS=N` and, on the old side, `XLA_FLAGS=--xla_cpu_multi_thread_eigen=false intra_op_parallelism_threads=N`; the default `--threads 0` leaves runtime defaults ("as users run it") and `--threads 1` reproduces a thread-bound box.
4. Identical work: same seed, same case config (pop size, genome sizes, species size, mutation defaults), same generation budget and fitness target for both sides; `cases.py` declares the config as plain data that the builders consume, so the JSON record and the constructed objects cannot drift.
5. No logging inside the timed region: stdout/stderr are redirected to `os.devnull` for the warmup+timed loop on both sides, the new pipeline runs with `is_detailed=False`, and the harness drives the compiled `step` directly so the legacy `analysis()`/print path is never entered.
6. Compile is measured, not charged to generations: the one-off build is reported separately and the generation it consumes on the new side is excluded from the quality curve.
7. Same dataset: XOR/XOR3d literals; `CustomFuncFit` uses the same sampler settings (`num_samples=500`, box `[-1,1]^2`) — legacy draws from the global `np.random` (seeded explicitly before construction), the new side from `default_rng(seed)`: same distribution, different draws.
8. The measured baseline wins: the declared numbers in `../CONTEXT.md` are printed next to the measured old row for sanity, but the verdict compares against the old row measured in the same run on the same box.
## What Is Not Compared
- Trajectories or bitwise equality: the sides use different PRNGs (JAX `PRNGKey` vs evoxc splitmix64), so one seed identifies the same *workload*, not the same search. Numerical fidelity is `test/parity/`'s job.
- Accelerator numbers: the contract is CPU; `--backend iree|xla|tvm` rows are informational.
- Import time and visualization/codegen cost (only `rss_after_import_mb` is recorded).
- CartPole against the legacy side: the pre-rewrite library has no evoxc CartPole (its RL problems are gym/brax/mujoco based and need extra dependencies), so that case is new-only and marked `n/a` for old; its post-hoist cost is 275.24 ms/gen (`PERF_NUMPY.md` pass 2 at `90d97b4`) against 381.73 ms/gen in the pre-fix `authoritative.json`.
## Cross-implementation Config Parity (xor3d quality gap)
`Case.build` feeds one config dict to both stacks, so every value a case *sets* is identical; the xor3d `-0.25` plateau comes entirely from defaults the case dict leaves unset.
Genuine drift in class defaults (old -> new), both in `genome/gene/conn/default.py`: weight `mutate_rate` 0.2 -> 0.8, weight `replace_rate` 0.015 -> 0.1, weight clip `[-5, 5]` -> unclipped; the new `GeneAttr` class default (0.2/0.015) still matches the legacy numbers, only `DefaultConn` overrides them (NEAT-python values).
New-only structural caps with no legacy equivalent: `DefaultGenome.max_in_degree = max(initial in-degree, 4)` (4 for XOR3d's 3 inputs; the legacy genome has no per-node in-degree cap) and `max_depth = 16`.
Deliberate structural-mutation drift: the new side ships connection gates `conn_add=0.4` / `conn_delete=0.05` against the legacy 0.2/0.2, because equal rates delete freshly added connections at a higher acceptance rate (measured: xor3d pop 100 escapes the constant-0.5 basin on 13/20 seeds, the frozen oracle on 4/20).
Identical on both sides: hidden activation `ACT.sigmoid` (single-element option list), `init_hidden_layers=()` (a fresh genome is the fully connected input->output network, 3 edges for XOR3d), node add/delete rates 0.2/0.2, bias/response defaults and `[-5, 5]` bounds, crossover, distance (1.0/0.4, normalised by max gene count), every NEAT knob (species_size is a count of species *slots* in both, compatibility_threshold 2.0, genome_elitism 2, species_elitism 2, max_stagnation 15, spawn_number_change_rate 0.5), and the seed plumbing (one key per side from the same `seed + repeat`; the PRNGs differ by design).
`survival_threshold=0.01` selects the top-ranked member on both sides in practice: the new side clamps `floor(threshold * members)` to >= 1, the legacy side floors it to 0 and divides 0/0 into a NaN probability vector (JAX `choice` then yields index 0).
Both sides compose the four structural gates sequentially and independently, and both pair elite children with their own parents instead of cloning one champion into every elite slot.
`-0.25` is the trivial plateau (`sigmoid(0)=0.5` -> mse 0.25) and is also where the legacy side sits for its first ~75 generations of xor3d_p100, so the remaining pop-100 gap is a slower escape from a shared plateau, not a different starting point: the new side leaves it on xor3d_p500/p1000 and on xor3d_p100 seed 42 only.
## Verdict Rules
- timing PASS when `new_ms_per_generation <= old_ms_per_generation` for every case both sides ran (speed-up >= 1.00x).
- quality PASS when `new_final_best >= old_final_best - max(QUALITY_TOLERANCE_REL * |old_final_best|, QUALITY_ABS_TOL)` for every such case, with `QUALITY_TOLERANCE_REL = 0.10` and `QUALITY_ABS_TOL = 1e-3` owned by `harness/protocol.py`.
- The absolute floor exists because the relative rule degenerates at the optimum: `xor3d_p1000`'s old final best is `-1.4e-09` (rendered `-0.0000`), so the relative rule would demand the new side beat `-1.5e-09` while the `0.001` floor sets the threshold at `-0.001`, which is why the new side's `-9.8e-05` (rendered `-0.0001`) passes in `RESULTS.md`; `1e-3` therefore means "both at the optimum within 1e-3" and keeps every case whose old fitness is meaningfully below the optimum on the relative rule, so a real gap still fails: in the pre-fix `authoritative.json` that is `xor3d_p100` (`-0.0894` old vs `-0.2500` new), `xor3d_p500` (`-0.1789` vs `-0.2500`) and `custom_pagie_p500` (`-0.0064` vs `-0.0219`), and in the post-fix `results/xor3d_quality_2026-11-04.json` only `xor3d_p100` (`-0.0894` vs `-0.2500`).
- The verdict renders the active tolerance (`max(10% × |old|, 0.001)`) in each quality-failure reason and in the `Sub-verdicts` line, and the report prints it in the headline and old-vs-new notes.
- overall PASS when both pass; `INCOMPLETE` while any run is `error`/`skipped` (listing them); otherwise FAIL with the offending rows named.

```
python benchmarks/run_benchmark.py --list
python benchmarks/run_benchmark.py --impl both --backend numpy --cases all --generations 150 --warmup 3 --repeats 3 --json benchmarks/results/authoritative.json   # regenerates the committed RESULTS.md
python benchmarks/run_benchmark.py --impl old --cases xor_p100 --generations 30 --repeats 1
python benchmarks/run_benchmark.py --impl new --backend numpy --cases xor_p100,xor_p1000
python benchmarks/run_benchmark.py --impl new --backend iree --cases xor_p500
python benchmarks/run_benchmark.py --render-from-json benchmarks/results/authoritative.json --out benchmarks/RESULTS.md   # reproduces the committed report: the record stores its own meta.report_note
python benchmarks/run_benchmark.py --render-from-json benchmarks/results/authoritative.json --out benchmarks/RESULTS.md --report-note "<the committed pre-fix scope note>" --persist-note   # only when the note itself changes: writes it into the record's meta, then renders
python benchmarks/run_benchmark.py --render-from-json benchmarks/results/authoritative.json --out $TMPDIR/re-render.md
# self-describing companion report (its own H1 + the one-line note under the banner)
python benchmarks/run_benchmark.py --impl both --backend numpy --cases xor_p100,xor_p500,xor_p1000 --generations 150 --warmup 3 --repeats 2 --threads 1 --report-title "TensorNEAT benchmark — thread-bound sensitivity (XOR family, --threads 1)" --report-note "This is the thread-bound sensitivity run (\`--threads 1\`, the declared-contract condition) of the XOR family; the authoritative default-thread matrix is \`RESULTS.md\`." --out benchmarks/THREADS.md --json benchmarks/results/threads1.json
python benchmarks/run_benchmark.py --render-from-json benchmarks/results/iree.json --out benchmarks/iree.md   # reproduces the committed historical note, which the record stores
# historical IREE attempt report: re-render only, never re-measure this record (the stored meta.command is the original run)
python benchmarks/run_benchmark.py --render-from-json benchmarks/results/iree.json --out benchmarks/iree.md --report-note "Historical pre-fix record, superseded by \`BACKENDS.md\` — the current measured \`iree\` evidence, where the backend lowers, compiles and runs the shipped problem classes. Every case below errored in \`Pipeline.setup\` before generation 0, so no row here is current. The measured CPU contract is \`RESULTS.md\` (numpy reference backend)." --persist-note
```
A single-case rerun never touches the committed evidence: point both outputs somewhere else, e.g. `python benchmarks/run_benchmark.py --impl both --backend numpy --cases xor3d_p100 --generations 150 --warmup 3 --repeats 1 --seed 42 --json $TMPDIR/x3d.json --out $TMPDIR/x3d.md` (~15 s both sides); `--json` alone would write the git-ignored scratch `results/latest.json` while `--out` would still regenerate `RESULTS.md`, so pass both.
A quality-only matrix is the same command with `--repeats 3 --seed 42`, which is exactly one repeat per seed for seeds 42/43/44 (repeat `r` uses `seed + r`): `python benchmarks/run_benchmark.py --impl both --backend numpy --cases xor3d_p100,xor3d_p500,xor3d_p1000,custom_pagie_p500 --generations 150 --warmup 3 --repeats 3 --seed 42 --json benchmarks/results/<name>.json --out benchmarks/results/<name>.md --report-title ... --report-note ...` — that is how `results/xor3d_quality_2026-11-04.json` was measured.
Budget such a matrix at ~50 minutes wall clock on a pre-tiling tree: the new-side `custom_pagie_p500` leg alone measured ~4.5 s/generation there (150 generations × 3 seeds), so run it as a background job rather than a foreground short timeout; a tree carrying pass 2's evaluate tiling measures 833.81 ms/generation on that leg (`PERF_NUMPY.md`).
`--report-title TEXT` overrides the H1 and `--report-note TEXT` adds one italic line directly under the banner; both are stored as `meta.report_title`/`meta.report_note` by the measurement path, both are honoured by `--render-from-json` (the flags win over the stored values), and passing neither reproduces the stored values (so a committed report re-renders with its own title and note).
`--persist-note` is the supported way to change a note on an existing record: it requires `--render-from-json` and `--report-note`, writes the note into that record's `meta.report_note` before rendering, re-reads the file and refuses to render if anything outside `meta` moved — the `runs`/`aggregated`/`verdict` bodies and every measured number stay byte-identical.
Every committed record now stores its own note (`authoritative.json`, `threads1.json`, `iree.json`, `xor3d_quality_2026-11-04.json`), so a bare `--render-from-json` reproduces each committed report's banner note.
The worker prepends `benchmarks/legacy_jax` (old side) or `src` (new side) to `sys.path`, so an installed `tensorneat` never shadows the tree under test; the legacy side needs the `bench` extra (`jax`), the new side only `evoxc` + `numpy`.
`--json` (default `benchmarks/results/latest.json`) holds per-run and aggregated records; `--out` (default `benchmarks/RESULTS.md`) is the regenerated report; `--dry-run` prints the planned subprocess commands without running them.
`--render-from-json PATH` re-renders `--out` from an existing run record only: it recomputes `aggregated` and `verdict` from the stored `runs`, rebuilds `meta` from the stored document where present, spawns no worker and never rewrites the JSON; it re-probes only the code-scope dirty state (`meta.env.git_dirty`/`git_dirty_paths`) and keeps the stored `git_commit` as the measurement's provenance. It fails loudly (exit 2) on an unreadable file, a wrong/absent `schema` or a missing `runs` list — this is how the report text is iterated without re-measuring.
The reproduce block names the record the report was rendered from: a record that `benchmarks/results/.gitignore` re-includes (`authoritative.json`, `threads1.json`, `iree.json`, `xor3d_quality_2026-11-04.json`, `gpu_rocm_2026-11-05.json`) is committed evidence and the block says every table cell is traceable; a scratch record (the default `latest.json` or any other git-ignored JSON) is labelled as not committed.
`meta.command` is stored as `shlex.join([sys.executable, *sys.argv])`, so the reproduce block renders it verbatim and `shlex.split` of the rendered line returns exactly that argv; a record written before that change (unquoted `" ".join(argv)`) is re-quoted from `meta.report_title`/`meta.report_note` when it is rendered.
`--list`, `--dry-run` and `--render-from-json` all run on a numpy-free interpreter (`/usr/bin/python3`).
The accelerator matrix is `gpu_measure.py`, not the harness: `python3 benchmarks/gpu_measure.py --list` (numpy-free), then
`uv run --extra iree python benchmarks/gpu_measure.py matrix --cases xor_p100,xor_p500,xor_p1000,xor3d_p500,custom_pagie_p500,cartpole_p100 --targets numpy,iree-rocm --warmup 3 --generations 20 --trace 14 --seed 42 --json benchmarks/results/gpu_rocm_2026-11-05.json --out benchmarks/GPU.md` (5 min 4 s on this box, 12 `ok` rows, exit 0),
`uv run --extra iree python benchmarks/gpu_measure.py run --case xor_p500 --target iree-rocm --json $TMPDIR/row.json` for one row in its own process, and
`uv run --extra iree python benchmarks/gpu_measure.py render --json benchmarks/results/gpu_rocm_2026-11-05.json --out benchmarks/GPU.md` to re-render without measuring.
The `iree` llvm-cpu leg is measured with `backend_measure.py` instead (one configuration per fresh process): `uv run --extra iree python benchmarks/backend_measure.py --backend numpy|iree --case xor --pop 100|500|1000`, plus `--opt-level O0` and the coverage-smoke commands listed in `BACKENDS.md`.
## Notes for Agents
- `--list`, `--dry-run` and `--render-from-json` must work on an interpreter without numpy: `cases.py` is stdlib-only at module scope and `harness/protocol.py` guards its numpy import (`np = None`), so keep new module-scope imports on the numpy-free paths clean.
- A failing run is always an `error`/`skipped` row, never a missing row: `harness/worker.py` writes its record even on a traceback, and the CLI synthesises a row when a worker dies without writing one.
- Cheap protocol check for any new record: the old side is deterministic, so a rerun of a case reproduces its `authoritative.json` `final_best_fitness` bit-for-bit (the post-fix export matches on all four xor3d/pagie cases) while only the new-side rows may move.
- Generation accounting is verifiable from a record: `generation_ms` holds exactly `timed_generations` samples (150 on both sides), the old-side curve holds `warmup + timed` entries and the new-side curve one fewer because its build consumes a generation (`generations_consumed_before_timing` 1 versus 0).
- `results/fix_after.json` is the git-ignored scratch record carrying pass 2's case-scoped numbers (`custom_pagie_p500`, `cartpole_p100`, XOR p500, XOR3d p500 controls); it is not evidence, is not committed, and the report rendered from it was written to `$TMPDIR`.
- `benchmarks/results/.gitignore` keeps `results/*.json` untracked except the records the committed reports were rendered from (`authoritative.json`, `threads1.json`, `iree.json`, `xor3d_quality_2026-11-04.json`, and `gpu_rocm_2026-11-05.json` for `GPU.md`), which are evidence and must never be hand-edited; `RESULTS.md`, `THREADS.md`, `iree.md`, `results/xor3d_quality_2026-11-04.md` and the interior of `GPU.md`'s measured markers are committed evidence and are only ever rewritten by `run_benchmark.py`/`gpu_measure.py` (or by `--render-from-json`/`render`, which only re-render from the existing JSON — the authoritative regeneration still comes from one measurement run), and `BACKENDS.md`/`PERF_NUMPY.md` are hand-written measurement records.
- `RESULTS.md` is the measured default-thread matrix (both sides, environment fingerprint with CPU model/cores/RAM/versions/git SHA + dirty flag/thread settings/load average, headline table with median speed-up / per-repeat range / quality overlap, data-derived win/lose narrative with the memory paragraph, per-repeat quality curves, companion pointers); `THREADS.md` and `iree.md` are the same renderer on their own records and titles. All three stay generated evidence, and each keeps the `--report-note` that scopes it to its tree.
- The environment row's dirty flag is computed over the **code under test only** (`protocol.GIT_DIRTY_PATHS`: `src/`, `benchmarks/harness/` (incl. `worker.py`), `benchmarks/legacy_jax/`, `benchmarks/cases.py`, `benchmarks/run_benchmark.py`, `benchmarks/backend_measure.py`, `benchmarks/gpu_measure.py`, `test/`, `pyproject.toml`, `uv.lock`, `.python-version`), with `protocol.GIT_EVIDENCE_PATHS` (`RESULTS.md`, `THREADS.md`, `iree.md`, `results/`, `BACKENDS.md`, `GPU.md`, `spikes/`) never counted: the harness writes its own report and JSON while it samples the fingerprint, so a full-tree `git status` always called a clean measurement "dirty". The row names up to `GIT_DIRTY_PATH_LIMIT` offending paths (`(dirty: src/... +N more)`) and renders a clean tree as `(clean — generated report artifacts are not counted)`; a change to the dirty scope is a protocol change and `RESULTS.md` is regenerated with it.
- `loadavg_start`/`loadavg_end` are optional per-run keys: JSON written before they existed still aggregates and renders (`loadavg_summary` reports `n_runs = 0` and the report says `n/a (not recorded)`), and the schema stays `tensorneat-bench/1`.
- The `## Environment` table always carries the shared-box caveat sentence: measurement conditions are stated, and repeat spread is the uncertainty measure — never drop the caveat or replace a spread with a single median.
- A backend whose runtime is absent (for example `iree` without `iree-base-compiler`/`iree-base-runtime`) becomes an `error` row with the backend's message; the rest of the matrix still runs and the verdict stays `INCOMPLETE`, never a crash.
- The `## What is not compared` section says the old-vs-new verdict is numpy-only by protocol and that an accelerator row is informational (never part of the verdict); it points at `BACKENDS.md` only when that file is next to the report, and that file is where the `iree` leg's measured numbers live (session-scoped: see `Provenance`). `## Protocol` / `## How to reproduce` point at `THREADS.md` under the same rule. Both checks use `os.path.exists` on the report directory, so a checkout without those files stays truthful.
- A companion pointer never names the report's own file: rendering `THREADS.md` drops the `THREADS.md` sentence while the other companion (`BACKENDS.md`) keeps its pointer.
- The `## Headline` note and the `## How to reproduce` note say "the old side always runs on JAX" only when the document holds an old-side row; an all-new-side document (the `iree` attempt) states that no old-side row is recorded instead.
- The `## Why the new side wins and loses` section reads the measured speed-ups: it states which side won each case and each population, and rewrites its mechanism paragraph accordingly. Never hard-code the new side as the winner. The memory paragraph is generated the same way from the aggregated `rss_final_mb` (per-case new/old ratio, worst case, XOR growth, the import floor, then the mechanism).
- A case's `fitness_target` must be unreachable by the initial population, or `generations_to_target` reads 1 for every run and the column carries no information: XOR3d's `-0.05` sits below the trivial linear-baseline fitness of `-0.25`, and Pagie's `-0.01` sits below the ~`-0.049` the legacy first generation already reaches (its measured final best is ~`-0.005`).
- The pre-fix `custom_pagie_p500` quality gap (`-0.0064` old vs `-0.0219` new in `authoritative.json`) is a PRNG-driven search-trajectory difference, not a kernel difference: the two sides draw different samples from the same distribution, and both cost passes are byte-identical to the trees they replace; `results/xor3d_quality_2026-11-04.json` measures it inside the tolerance at `-0.0066` vs `-0.0064`.
- Bench environment: `jax` only on the old side, `evoxc` on the new side; the verdict compares the old row measured on the same box, never the declared 51/109/157 ms contract numbers.
## Known Issues
- The accelerator cross-check is an equality gate at generation 1 only: on the four wide cases the committed trace's first key divergence lands at generation 6 (`xor_p500`), 9 (`xor_p1000`), 9 (`xor3d_p500`) and 10 (`custom_pagie_p500`, transient — identical again over generations 11–14), with the float tolerance first exceeded one to three generations earlier — a near-tie selection flip driven by a few float32 ulps in the initial normal draw and amplified by the `sort_desc_legacy`/`pair_parents` ranking under `survival_threshold = 0.01` (one breeding parent per species) — while `xor_p100` and `cartpole_p100` stay key-identical for all 14 traced generations, so a long-horizon accelerator-vs-numpy comparison is a trajectory comparison on the fitness view, never a key-array equality test.
- The accelerator timings are one seed and one committed repeat, and the box was shared while measuring: the committed record's document-build load average is 7.76/4.99/2.81 and the scratch repeat's 3.43/4.59/3.36, with no median moving more than 6.8 % between the two sessions (all 12 final fitness values reproduced bit-for-bit); the per-row `min–max` and that repeat are the uncertainty measures, never a single median, and the two CPU rows cross-check against `BACKENDS.md`'s near-idle numpy rows within ~5 %.
- `results/authoritative.json` mixes two worker fingerprints: the 17 XOR runs (both sides) recorded `95701646` and the other 28 recorded `ebeaf1f8`; the trees differ only in `CONTEXT.md`, so `RESULTS.md`'s single `Git commit` row is right for the code under test but does not show the mix.
- `Interpreter used:` is host-dependent: a re-render prints `.venv/bin/python` only while the recording worktree exists next to the record, else the basename `python`, so committed reports are not byte-identical across boxes.
- A report rendered outside this checkout (`$TMPDIR`) loses the `BACKENDS.md`/`THREADS.md` companion pointers and prints the bare output filename in its footer, so a temp-path render is never byte-identical to the committed file even when every table cell matches.
- A synthesised `error`/`skipped` row (a timeout, an `OSError` from `subprocess.run`, a worker that wrote no record) carries only `case/impl/backend/repeat/seed/status/error` (plus `case_config`/`env`/`protocol` on the timeout and `OSError` paths), not the `loadavg_*` fields a worker record carries.
- `test/unit/benchmarks/test_protocol.py` covers only the git fingerprint; the aggregation keys, the `reach` forms and the `--persist-note` round-trip have no regression test — the expectations to add are recorded in `## Test Strategy`.
- `cases.py`'s declared-target rule (below) is enforced by review, not by code: nothing rejects a case whose initial population already meets its `fitness_target`.
- The committed records themselves keep the recording host's absolute paths: `authoritative.json` and `xor3d_quality_2026-11-04.json` store the recording worktree's interpreter/`out_path` in `meta`, `iree.json` stores five `/root/.../worker_T1_A293/...` paths in its `error` tracebacks, and `gpu_rocm_2026-11-05.json` stores the recording worker's interpreter in `meta.command` (its rendered block never prints it); the report scrubs them at render time, the evidence file does not.
- Harness-internal quirks (unused `n_errors`/`meta.impls`, `OldAdapter.display`/`Adapter.display` read by nothing, bare `harness.*` imports, the hand-maintained `PARITY_TEST_COUNT`, the `inf`-to-`null` asymmetry) are recorded in `./harness/CONTEXT.md` `## Known Issues`.
## Constraints
- Python >= 3.11; harness dependencies are stdlib + `numpy` (plus `jax` on the old side only, via the `bench` extra).
- The compiled legs need `uv sync --extra iree`, which resolves IREE 3.13.0 (IREE 3.10/3.11 aborted in the HIP HAL on any while/scan loop, which is why an older session had no rocm row); `O2`/`O3` SIGSEGV inside `iree-compile` on this graph, so every shipped compiled record is the default opt level, `O0` or `O1`.
- Never edit `legacy_jax/` — a moving baseline makes every number meaningless.
- Never hand-edit a generated report or a committed record; a document that needs a scope line gets it from `--report-title`/`--report-note` at render time, and `--persist-note` stores it in the record so later renders keep it.
- Quote no number without the tree or session it came from: `RESULTS.md`, `THREADS.md`, `iree.md`, `BACKENDS.md`, `GPU.md` and `PERF_NUMPY.md` each describe a different tree, and only a fresh harness run may be described as HEAD.
- Nothing outside `benchmarks/` is read except the two implementation trees under test and the host fingerprint (`/proc/cpuinfo`, `/proc/meminfo`, `git rev-parse`/`git status` on this checkout); nothing outside `benchmarks/` is written.
- Files stay under ~1000 lines with one responsibility each: protocol / adapters / worker / reporter / report format / report sections / CLI / cases.
- A run that cannot work must fail loudly (`status="error"` with the traceback in JSON and a non-zero exit from the worker) — never a silently missing row.
## Test Strategy
There is no pytest suite in this node (`test/` is a sibling, read-only); its verification is running the harness, and every check below is cheap.
- `python benchmarks/run_benchmark.py --list` prints the 8-case matrix on an interpreter without `numpy` (exit 0); `--dry-run --impl both --cases xor_p100,cartpole_p100` prints both worker commands and skips `cartpole_p100/old` with a reason.
- Old-side smoke: `--impl old --cases xor_p100 --generations 5 --warmup 2 --repeats 1` gives one `ok` row (~30 ms/gen at pop 100) and the verdict `INCOMPLETE` because no new-side row exists.
- New-side failure path: `--impl new --cases xor_p100 --generations 2 --repeats 1` must render `status="error"` rows with the exception line and exit 1 — the CLI never crashes on a broken implementation.
- Unavailable-backend smoke (no IREE runtime): `--impl new --backend iree,numpy --cases xor_p100 --generations 2 --warmup 1 --repeats 1 --out $TMPDIR/x.md --json $TMPDIR/x.json` records the `iree` row as `error` and still measures and reports the `numpy` row; the matrix never aborts.
- Report smoke: `--impl both --backend numpy --cases xor_p100 --generations 2 --warmup 1 --repeats 1 --out $TMPDIR/report.md --json $TMPDIR/report.json` renders the headline, environment fingerprint and win/lose sections from those records, and both files are valid; write them into `$TMPDIR` so a smoke run never clobbers the committed `RESULTS.md`. The JSON must carry `loadavg_start`/`loadavg_end` on every run and the report's `Load average (1/5/15 min)` row must show them next to the document-build load.
- Fingerprint smoke: a report rendered while `RESULTS.md`/`THREADS.md`/`iree.md`/`results/*.json` are touched still renders `(clean — generated report artifacts are not counted)`; an uncommitted edit under `src/` or `benchmarks/harness/` flips `git_dirty` to true and names the path (`(dirty: src/... +N more)` for more than `GIT_DIRTY_PATH_LIMIT` paths). Verify with `--render-from-json benchmarks/results/authoritative.json --out $TMPDIR/re-render.md` on a clean tree and a 2-generation smoke from a deliberately dirtied source file, then restore that file exactly.
- Provenance smoke: every generated report under this node opens with a `--report-note` (or the default banner for `RESULTS.md` alone) that names its record's commit; the note must come from the record's `meta.report_note` or be passed again as `--report-note` on every render, because `--render-from-json` never rewrites the JSON and a one-off flag is dropped by the next re-render.
- End-to-end smoke that is known green on a clean `uv sync --extra bench`: `--impl both --backend numpy --cases xor_p100 --generations 2 --warmup 1 --repeats 1 --out $TMPDIR/smoke.md --json $TMPDIR/smoke.json` writes two `ok` rows, a `FAIL` timing verdict (2 generations are not a benchmark) and a report with `loadavg_*` on both runs; the explicit-skip path (`--impl old --cases cartpole_p100`) writes a JSON-only record and no report, and an unavailable `--backend iree` records an `error` row while the matrix continues.
- Re-render drift is now limited to host- and directory-dependent lines: rendering each committed record reproduces its banner note and every table cell, and differs only in the banner's re-render timestamp, the `Interpreter used:` basename and — for a `$TMPDIR` render — the companion pointers and footer path.
- Reach/annotation smoke: `--render-from-json benchmarks/results/authoritative.json --out $TMPDIR/a.md` must print `78 (2/3)` for `xor_p100`/old, `149 (1/3)` and `>152 (0/3)` on `xor3d_p100`, `>152 (0/3)` for `custom_pagie_p500`/new, the header `Speed-up range (worst–best)`, and no numeric cell that differs from the committed report.
- Target-suppression smoke: `--impl new --cases cartpole_p100 --generations 2 --warmup 1 --repeats 1 --out $TMPDIR/cp.md --json $TMPDIR/cp.json` records `quality.target: null` and `case_config.gens_to_target: false` and renders `n/a (no informative target)` in the gens-to-target cell (never `>N`).
- Note-persistence smoke: on a `$TMPDIR` copy of a record, `--render-from-json X --out a.md --report-note "TEST" --persist-note` then a bare `--render-from-json X --out b.md` must both carry the note, and the record's `runs` list must hash identically before and after; `--persist-note` without `--render-from-json`, and without `--report-note`, each exit 2 with a named error.
- Unit-test expectations the owner of `test/unit/benchmarks/test_protocol.py` must add (this node cannot edit `test/`): `protocol.aggregate()` writes `target`, `gens_to_target_reached` and `gens_to_target_repeats` next to the unchanged `generations_to_target`/`gens_to_target_all`; `report_format.reach` renders exactly `78`, `78 (2/3)`, `>152 (0/3)`, `n/a (no informative target)` (target recorded as `null`) and the legacy plain form (no `gens_to_target_all`/`target` key); `protocol.speedup_bounds` keeps `best = old_min/new_max` and `worst = old_max/new_min`; `cases.get_cases(["cartpole_p100"])[0].gens_to_target is False` and its `as_dict()` carries the key; and `--persist-note` rewrites only `meta.report_note` of a copy of `results/authoritative.json`.
- Companion-title smoke: `--report-title`/`--report-note` appear as the H1 and the italic note under the banner; a render without them is byte-identical to the pre-flag output (the flagless `RESULTS.md` render must not change apart from that note).
- Re-render smoke: `--render-from-json benchmarks/results/authoritative.json --out $TMPDIR/re-render.md` reproduces the whole report (headline with the range/overlap columns, per-repeat quality curves, memory paragraph, verdict) without spawning a worker, and the rewritten verdict matches the stored one except for the quality floor; a wrong schema, an unreadable file and a document without `runs` each exit 2 with a named error. `--list`/`--dry-run`/`--render-from-json` all run on `/usr/bin/python3` (no numpy).
- Companion pointers: a report rendered into `$TMPDIR` (no `BACKENDS.md`/`THREADS.md` next to it) must omit both pointers; copy the files next to it and the same render must include them, except the report's own file — a `THREADS.md` render never points at `THREADS.md`. This is an `os.path.exists` check on the report directory plus the own-name comparison, never a hard-coded claim.
- Reproduce-line smoke: the line under `# regenerate the committed report: the literal command of this run` must survive `shlex.split` → `shlex.join` unchanged, and its tokens must equal the recorded argv with the interpreter replaced by `python` and paths repo-relative; checking the committed `THREADS.md`/`iree.md` this way catches a record whose `--report-title`/`--report-note` were stored unquoted.
- `python benchmarks/spikes/forward_micro.py --mode unrolled` runs numpy-only, asserts the two prototype forms agree to `1e-5` and reproduces `FORMULATION.md` within ~±5%.
- Accelerator protocol smoke (each cheap, all into `$TMPDIR`): `python3 benchmarks/gpu_measure.py --list`/`--help` exit 0 on `/usr/bin/python3`; `run --case xor_p100 --target numpy --warmup 1 --generations 3` gives an `ok` row with `cross_check.status == "skipped"`; `--target iree-llvm-cpu --warmup 1 --generations 2` and `--target iree-rocm --warmup 1 --generations 2` each give an `ok` row (one `iree-compile` of the shape) and a `cross_check` pass with exact int keys; `--trace N` adds a `trajectory` record (`ok` with N generation rows and `first_key_divergence`/`first_float_exceedance` on a compiled target, `skipped` with a reason at `--trace 0` and on the `numpy` reference), a failing trace leg stays `error` inside an `ok` row, and `matrix --trace N` forwards the flag to every child; `matrix --cases xor_p100 --targets numpy,iree-rocm --out <copy of GPU.md>` writes both `ok` rows, renders both into the block and exits 0; an absent `iree` runtime still records the compiled rows as `error` while the numpy row measures; two `render` runs from the same record give the same block, that block is byte-identical to the committed interval between `GPU.md`'s two markers (`cp benchmarks/GPU.md $TMPDIR/gpu.md` then `render --json benchmarks/results/gpu_rocm_2026-11-05.json --out $TMPDIR/gpu.md` reproduces the whole file), its heading lists the record's own target labels (`## Measured: numpy vs iree-rocm`), and a wrong schema, a missing `records` list and a report without markers each exit 2 with a named error.
- Regression rule: a harness change must leave the old-side rows within ~10% of the committed `RESULTS.md`; a larger shift means the protocol moved and `RESULTS.md` is regenerated in the same commit.
