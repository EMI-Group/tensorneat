# results — generated run records
## Intent
Hold the machine-readable output of `../run_benchmark.py` — per-run `RunResult` records plus aggregated rows and the protocol/environment snapshot — and of `../gpu_measure.py` (one accelerator record per matrix session), so each committed report can be re-rendered without re-running the benchmark.
Six records are committed evidence and stay in git: `authoritative.json`, `threads1.json`, `iree.json`, `xor3d_quality_2026-11-04.json`, `gpu_rocm_2026-11-05.json` and `gpu_rocm_xla_2026-11-06.json`.
Every other `*.json` here (the default `latest.json` and anything else) is scratch output, git-ignored and safe to delete.
Nothing here is authored by hand: a record is only ever written by its producer (`../run_benchmark.py` or `../gpu_measure.py`), and a report is regenerated by re-running that producer's CLI, never by editing a record.
## Provenance: which record measures which tree
No committed *old-vs-new* CPU artifact measures the merged tree; each record speaks only for its own rows, tree and session, and nothing here may be quoted as a statement about HEAD.
A claimed number that is in none of these rows is a claim about HEAD and has to be measured, not quoted.

## Constraints
- `.gitignore` ignores `*.json` and re-includes exactly the six committed records; never drop a re-include while the report rendered from that record stays in git.
- Never edit a JSON record to make a report look better: regenerate it by re-running its producer (`../run_benchmark.py` or `../gpu_measure.py matrix`), and iterate report text with `--render-from-json` / `render`.
- `--persist-note` (on the harness side) is the only sanctioned write to an existing record and may touch `meta.report_note` alone: it re-reads the file and refuses to render if anything outside `meta` moved, so `runs`/`aggregated`/`verdict` and every measured number stay byte-identical.
- A committed accelerator record must carry the plugin's identity whenever it measured an `xla` target: a number measured against a different `.so` is a different experiment.
- The records keep the recording host's absolute paths (`meta` interpreter/`out_path`, `iree.json`'s traceback paths, the plugin path on the newer accelerator record); the report scrubs them at render time, the evidence file does not — so never hand-scrub a record either.
- Keep this directory free of caches and venvs — it is evidence output only.
