# rl — reinforcement-learning problems on evoxc

## Intent
Score a genome by the return of a batched episode rollout, with the environment dynamics written as evoxc ops instead of a JAX simulator.
Three environments ship: the discrete `CartPole` and the continuous classic-control tasks `Pendulum` and `MountainCarContinuous`.
Each one doubles as the reference recipe for any environment a user wants to add: no registry, no simulator dependency, just a step kernel and one loop, one file per environment.

## API Surface
- `cartpole.py: CartPole(BaseProblem)` — `__init__(max_step=500, repeat_times=1, gravity=9.8, masscart=1.0, masspole=0.1, length=0.5, force_mag=10.0, dt=0.02, x_threshold=2.4, theta_threshold=12.0, reset_scale=0.05, fitness_target=None)`; every knob is validated on the host and raises `TensorNEATError`.
- `pendulum.py: Pendulum(BaseProblem)` — `__init__(max_step=200, repeat_times=1, gravity=10.0, mass=1.0, length=1.0, max_speed=8.0, max_torque=2.0, dt=0.05, fitness_target=None)`; every knob validated on the host (`require_positive_int`/`require_positive` from `_common`), `fitness_target > 0` raises because every Pendulum reward is `-cost <= 0`, a non-finite `fitness_target` raises, and the attribute is stored as given.
- `mountaincar.py: MountainCarContinuous(BaseProblem)` — `__init__(max_step=999, repeat_times=1, min_position=-1.2, max_position=0.6, max_speed=0.07, goal_position=0.45, goal_velocity=0.0, power=0.0015, gravity=0.0025, fitness_target=None)`; unreachable geometry (`min_position >= max_position`, a `goal_position` outside the clipped track, `goal_velocity > max_speed`) raises as a configuration error, and so does `fitness_target > ATTAINABLE_CEILING` (`93.0`) or a non-finite `fitness_target`.
- `mountaincar.py: ATTAINABLE_CEILING = 93.0` — the highest return a reaching policy is defended to attain, exported in that module's `__all__` and deriving the `fitness_target` rejection (see the MountainCar section).
- `_common.py` — the host-side helpers all three environments draw from: `to_numpy(value)`, the owner-prefixed validators `require_positive_int(owner, name, value)`, `require_finite(owner, name, value)`, `require_positive(owner, name, value)` and `require_non_negative(owner, name, value)` (messages are `<Owner>: <name> must be ...`), `returns_of(total, pop_size, repeat_times)`, the `(B,) -> (P, R)` layout helper, and `prepared_query(act_fn, batch)`; the last two are **traced** (they emit ops), inlined into the caller's graph like `problem.base.finalize_fitness`.
  `require_positive` and `require_non_negative` are layered on `require_finite`, so a non-numeric knob (a string, a list, `None`) and a non-finite one (`NaN`, `+/-inf`) both raise `TensorNEATError` — never a bare `TypeError`/`ValueError`, and never a comparison a `NaN` silently fails.
  Each environment imports only what it uses: `pendulum.py` takes `require_positive_int`/`require_positive`/`require_finite` (every physics knob is strictly positive; `fitness_target` is finite), `mountaincar.py` adds `require_non_negative` for its `gravity` plus `require_finite` for its three geometry knobs, and `cartpole.py` takes all three validators plus `to_numpy`/`returns_of`; all three take `to_numpy` and `returns_of`.
  No module-scope `enp` call and no `@evoxc.defn` lives there.
- `CartPole`: `input_shape = (4,)` (`x, x_dot, theta, theta_dot`), `output_shape = (2,)` (two logits; `out[1] > out[0]` pushes right).
- `Pendulum`: `input_shape = (2,)` (`theta, theta_dot`), `output_shape = (1,)` (one torque logit, squashed inside the problem).
- `MountainCarContinuous`: `input_shape = (2,)` (`position, velocity`), `output_shape = (1,)` (one action logit, `a = tanh(logit)`).
- Both continuous problems own the action squashing, so a genome used with them must leave `output_transform` unset (identity); a bounded transform would rescale the logit before `tanh` ever sees it.
- Formulation gate: `Pendulum` ships two carry formulations selected on the host from the trace-time static `state.kernel_mode` (`common.schedule_accelerator.kernel_mode(state)`, `"host"` on the numpy leg, `"accelerator"` on a GPU-class device), so a graph contains exactly one of them; `CartPole` and `MountainCarContinuous` consult no mode at all and trace one formulation on every leg.
- `fitness_target` is validation-only in all three: `None` skips the check, a non-finite value raises, and a value above the environment's attained ceiling (`max_step` for `CartPole`, `0` for `Pendulum`, `ATTAINABLE_CEILING = 93.0` for `MountainCarContinuous`) raises.
- `evaluate(state, keys, act_fn, transformed) -> (P,)`: fitness is maximized, the mean over `repeat_times` of the episode return, `finalize_fitness`-ed last.
- `show(state, key, act_fn, transformed)`: host-side, one individual, builds its own graph over the single rank-0 key (`evoxc.build` + `evoxc.run`) and prints one line per repeat plus the mean return; returns `None`.
  The build takes `problem.base.build_options(state)` (`backend`/`device`/`compile_options`), so the report runs on the backend the run registered (`numpy` when the state registers none) and a backend that cannot run it raises instead of falling back.
  A non-finite return is reported, never converted to an integer: the step count, the goal indicator and the return columns all print the honest value (`n/a`, `nan`).
- `CartPole` trace-side helpers: `_rollout`, `_loop_cond`, `_loop_body`, `_constants`, `_advance`, `_death_mask`, `_terminated`, `_force_from_logits`, `_nan_rows`; validation and the host conversion are the shared `_common` names (`require_positive_int`/`require_positive`/`require_non_negative`/`require_finite` with owner `"CartPole"`, `to_numpy`, `returns_of`).
- `Pendulum` trace-side helpers: `_rollout` (reset draw + the `kernel_mode` switch → `(total, final_obs)`), `_packed_rollout` (the accelerator loop over the packed row), `_reset` (the single `U(-1, 1)` draw, scaled per column by the baked `reset_scale` row), `_loop_cond` (guards whichever carry its `packed` flag names), `_loop_body` (host carry), `_loop_body_packed` (accelerator carry), `_constants` (returns the `_PendulumConstants` NamedTuple), `_advance`, `_advance_rows` (the algebra at the two `(B,1)` state columns), `_transition_rows` (the algebra both carries share), `_angle_normalize`.
- `MountainCarContinuous` trace-side helpers: `_rollout`, `_reset`, `_loop_cond`, `_loop_body`, `_constants` (`_MountainCarConstants`), `_action_from_logits`, `_advance` (the `(B,2)` row façade the tests drive), `_transition` (the algebra on the two `(B,1)` state columns), `_stack_state` (the two columns joined into an observation row), `_goal_mask`, `_terminated` (rank-1 façade kept for host-side introspection and tests).

## Algebra

### Shared shape (all three)
`B = P * repeat_times` with `P = static_batch_size(transformed)`, **individual-major**: row `p * R + r` is repeat `r` of individual `p`, so `P = 4, R = 1` and `P = 2, R = 2` draw the same four initial states from one key and produce identical per-episode returns (verified for both continuous environments).
Initial states come from **one** `evoxc.random.uniform` from the single rank-0 key; the key is not threaded through the loop and `np.random` is never used.
The return accumulator rides in the carry and the loop emits no output: `evoxc.scan` would desugar to a `while` that carries a `(max_step, B)` stacked output and scatters one row per iteration, i.e. `B * max_step` of array traffic for a result the carry already holds.
The trip count is always static (`step < horizon`, from the int32 `horizon` in the bundle), never "while any episode is alive".
`returns_of` is the only place the `(P, R)` layout is assumed, and `evaluate` means over axis 1 after it.

### CartPole (`cartpole.py`)
Classic Gym `CartPole-v1` with Euler integration: `dt=0.02`, `g=9.8`, `masscart=1.0`, `masspole=0.1`, half-pole `length=0.5`, `force_mag=10`, dead when `|x| > 2.4` or `|theta| > 12deg` (`= 0.2095 rad`), reset `U(-0.05, 0.05)^4`.
Action: "push right" iff `out[1] > out[0]` (a tie pushes left, matching `argmax` index 0) computed with `enp.split` + `enp.greater`, so no integer/bool control flow and no `argmax` dtype handling.
One `evoxc.while_loop` over `max_step` timesteps with carry `(obs (B,4), alive (B,), total (B,), step ())`.
Step body: `total += alive` **before** the transition (the failing step still scores, matching Gym returns), then one fused Euler op on the whole row — `next_obs = obs + dt * (x_dot, xacc, theta_dot, thetaacc)` with `xacc`/`thetaacc` from the documented `temp`/`thetaacc`/`xacc` algebra — and death from that row against a `(1, 4)` constant `(x_threshold, +inf, theta_threshold, +inf)`: `dead = greater(max(|next_obs| - threshold_row, axis=1), 0)`, a bracketed per-column limit whose two velocity columns can never fail, so it equals `|x'| > 2.4 | |theta'| > 12deg` exactly.
The fused row op is bit-identical to the four scalar updates it replaced (element `j` is literally `obs_j + dt * deriv_j`, no reassociation) and the strict inequality survives `|obs_j| - t > 0`, so both steps are semantics-preserving op-count reductions, never physics changes.
State frozen after death via `enp.where(enp.expand_dims(alive, 1), next_obs, obs)` — no `cond`, every carried dtype/shape constant across iterations.
A traced tensor has no `__getitem__`: broadcast with `enp.expand_dims`, split columns with `enp.split`, never `x[:, 0]`.
Because episodes are frozen, an individual's return is its survival time: `max_step` is the fitness ceiling, so `fitness_target` must be `<= max_step`.
NaN logits act as push-left inside the rollout (`enp.greater` is false against NaN) but a NaN census (`evoxc.isnan(reduce_sum(logits, axis=1))`) is accumulated into `total`, so that individual's fitness is NaN → `-inf`.

#### IREE dispatch budget of the step block (measured statically, CPU only)
The count is read statically, never by running a device: dump the generation graph's StableHLO, `iree-compile --iree-input-type=stablehlo --iree-hal-target-backends=rocm --iree-rocm-target=gfx942 --compile-to=executable-configurations` (a pure CPU compile, iree-base-compiler 3.13.0), and count `stream.cmd.dispatch` per `cf` block of `util.func public @main`.
The reference geometry is `pop 100`, `species_size=20`, `survival_threshold=0.01`, `max_nodes=50`, `max_conns=100`, seed 42.
The rollout region is header `^bb4` (0 dispatches, `cf.cond_br` exit to `^bb9`) → the genome's per-query prelude `^bb5` → level-loop header `^bb6` (0) → the genome's level-loop body `^bb7` → this node's step `^bb8` → `cf.br ^bb4`, so one timestep is `^bb5 + ^bb7·L + ^bb8` and a generation is `max_step` timesteps.
`CartPole` costs **21 dispatches per timestep** at `L = 3`: `^bb5` 3 + `^bb7` 4 per level trip + `^bb8` **6**, i.e. **4 200** rollout dispatches per generation at `max_step=200`, in a graph of **446** static sites.
The step is one unconditional spelling — no `kernel_mode` gate — because it is both fewer dispatches and no extra numpy work than the split form: that form's materialisation cost, four `slow_memcpy` column copies plus the two `elementwise_100_f32` acceleration regions and the `elementwise_400_f32` derivative/concat region, does not exist here.
`^bb8`'s 6, with the op group each one carries:
1. `elementwise_100x2_i32xi32xf32` — the prepared pass's output read-out (the logit selection), the genome node's op materialised inside the step.
2. `elementwise_100x4_*` — one fused region holding the two one-lane `evoxc.slice`es of `theta`/`theta_dot`, the whole physics chain, the lane rotation (`evoxc.gather` against the baked `(1,0,3,2)` index), the two baked single-lane `enp.where` selects that overwrite lanes 1/3 with `xacc`/`thetaacc`, `obs + dt*deriv`, the force select and the reward/accumulator chain.
3. `reduction_100x4_f32` — `_death_mask`'s `max(|obs| − threshold_row)` fold.
4. `reduction_100x2_f32` — `_nan_rows`'s row sum of the logits.
5. `elementwise_100_i1xf32xi1` — the `evoxc.isnan` compare on that sum.
6. `elementwise_100x4_i1...` — the freeze select `where(alive, next_obs, obs)`.
The step block is at a floor of 6: each reduction costs its own dispatch because a reduction broadcasts into a different iteration space and cannot fuse (the death fold reads 4 lanes, the NaN row sum 2), the `i1` compare materialises because its result feeds the fused region, and `alive`/`reward` cannot join that region because they are loop-carried values that must be written first; the read-out is the genome node's.
Measured and rejected, each landing at or above the shipped count: 3 index gathers plus an `enp.concatenate` reassembly of the Euler row (13 dispatches in the step block); a freeze select on `dead` instead of `alive` (6, and it rests on an unproven invariant); `total = where(nan_rows, nan, total + astype(alive))` (6); gathering the force out of the logits instead of `enp.split` (6); `evoxc.gather` with baked `[2]`/`[3]` index constants instead of one-lane slices (the same 6 dispatches, but +5 numpy ops per generation against the shipped +3); packed `(B,2)` carries or dropping `alive` from the carry (analytically rejected — packing adds a per-timestep select, the trade the Pendulum record loses).
numpy control: 30 994 executed IR ops per generation against 30 991 without the three baked row-assembly constants, peak RSS and wall time unchanged inside the box's drift, bit-identical fitness.

### Pendulum (`pendulum.py`)
Gym `Pendulum-v1`: `theta=0` is **upright**, so the cost is small exactly at the unstable equilibrium.
Per timestep, all on the pre-transition state:
`u = max_torque * tanh(logit)`; `cost = angle_normalize(theta)**2 + 0.1*theta_dot**2 + 0.001*u**2`; `theta_dot' = clip(theta_dot + (3g/(2l)*sin(theta) + 3/(m*l**2)*u) * dt, -max_speed, max_speed)` — the clip comes **before** the angle update; `theta' = theta + theta_dot' * dt`; `total -= cost`.
`gravity_term = 3*gravity/(2*length)` and `torque_term = 3/(mass*length**2)` are precomputed host-side into the bundle, so the body never divides; the host oracle must use the same precomputed float32 values.
`angle_normalize(x) = x - two_pi * floor((x + pi) / two_pi)`, the floor-mod spelling of Gym's `((x + pi) % (2*pi)) - pi` (see Notes for why `evoxc.remainder` is not usable).
Reset: one `U(-1, 1)` block of shape `(B, 2)`, scaled per column by the baked `(1, 2)` float32 row `reset_scale = [pi, max_speed]` in one elementwise multiply (`theta = raw_0 * pi`, `theta_dot = raw_1 * max_speed`; each element is `raw * scale` with the operand the per-column spelling used, so the draw is bit-identical).
No termination and no alive mask: every episode is scored over the whole horizon, so the return is in `[-max_step * max_cost, 0]` (per-step cost is at most `pi**2 + 0.1*max_speed**2 + 0.001*max_torque**2 = 16.2736`), and `fitness_target` may only be `<= 0`.
The host carry `(theta (B, 1), theta_dot (B, 1), total (B, 1), step ())` of `kernel_mode == "host"` (the numpy leg and the byte-identical base kernel) keeps three float leaves at the cost's own rank, so a step needs no `slice` and no `reshape`, and the accumulator subtracts from the carried `(B, 1)` with one op.
The accelerator carry `(row (B, 3), step ())` of `kernel_mode == "accelerator"` holds `row = (theta, theta_dot, total)` as one float root, assembled by the single affine expression `row * keep_dims + next_speed * speed_row - cost * total_dim` against three baked `(1, 3)` rows (`keep_dims = [[1,0,1]]`, `speed_row = [[dt,1,0]]`, `total_dim = [[0,0,1]]`), bit-identical to the host step for finite values; its observation row is the leading `(B, 2)` slice of the carried row rather than a select, and a NaN cost additionally drags the `theta` column to NaN (`NaN * 0`), which the fitness never reads.
On the host carry the observation row the policy consumes is built once per step as **one elementwise select** against the baked `(1, 2)` boolean `obs_columns = [True, False]` — `enp.where(consts.obs_columns, theta, theta_dot)` — instead of an `enp.concatenate` of the two columns: same one op, but a concatenate lowers to one strided copy (one dispatch) per column while the select fuses into the observation producer, so the per-query region around the policy holds 4 dispatches.
Both formulations flatten `total` to `(B,)` once after the loop, and `obs_columns`/`reset_scale`/the three packed rows are Constants built once per rollout, outside the loop.
`_advance_rows(theta, theta_dot, logit, consts) -> (next_theta, next_speed, cost)` is the algebra at the two-column rank; `_advance(obs, logit, consts)` is its row-shaped face (two `slice` in, one `concatenate` and one `reshape` out), it returns the cost at rank 1 because `(B,) - (B,1)` would broadcast into a `(B, B)` matrix, and neither rollout loop calls it.
NaN: `tanh(NaN) = NaN` → `0.001*u**2` is NaN → `cost` is NaN → the accumulator is NaN → `finalize_fitness` gives `-inf`; verified empirically, so there is no NaN census.

#### IREE dispatch budget of the step block (measured statically, CPU only)
Counted with the method of the CartPole subsection, at the same reference geometry and `L = 3`.
The two carries are what the count separates, and the genome's level body is one dispatch wider per trip on the accelerator leg (5 against 4) — a genome/tensorization-side effect of `kernel_mode` present in the base tree too — so on that leg Pendulum's 21 is the count to compare against 22, never against the host mode's 19.
Host mode: `^bb5` 4 + `^bb7` 4 per level trip + `^bb8` **3** = **19** dispatches per timestep, i.e. **3 800** rollout dispatches per generation at `max_step=200`, in a graph of **445** static sites.
Accelerator mode: `^bb5` **3** + `^bb7` **5** per level trip + `^bb8` **3** = **21** dispatches per timestep, i.e. **4 200** per generation, in a graph of **414** static sites.
The same packed formulation without the per-query win is `^bb5` 4 + 5 + 3 = **22** per timestep (**4 400** per generation) in a graph of **415** static sites.
The accelerator step block is two `slow_memcpy` column slices plus one fused `elementwise_100x3_*` region, against the host block's three elementwise dispatches, one per carried float root (`theta'`, `theta_dot'`, `total'`): the whole-step fusion does not survive graph assembly, which is why the surviving win is the per-query prelude (`^bb5` 3 dispatches against the 4 of the formulation without it) and why the formulation is gated rather than unconditional.
The step block is at a floor of 3: one dispatch per loop-carried float root, and any cross-column data movement inside a carried row lowers to a `slow_memcpy` dispatch, so 2 is unreachable without an extra reduction and 1 is unreachable at all.
numpy control: host mode 27 391 executed IR ops per generation, identical to the base tree, with RSS and wall unchanged; the packed assembly costs the accelerator leg 805 ops (27 055 → 27 860, +3.0 %), which is exactly why it is gated.
Rejected: the `pack3` nested-`where` assembly (+1 006 ops against the shipped affine assembly's +805); op-spelling rewrites (`x*x` against `enp.square`, explicit `min`/`max`, a rank-1 `total` → +199 ops), all inert and all left out.

### MountainCarContinuous (`mountaincar.py`)
Gym `MountainCarContinuous-v0`, exact Gym ordering on the pre-transition state:
`a = tanh(logit)` (the **pre-clip** action, which is what Gym charges the penalty on); `force = clip(a, -1, 1)` (a no-op because `|tanh| <= 1`, kept for faithfulness); `velocity' = velocity + force*power - gravity*cos(3*position)`; `velocity' = clip(velocity', -max_speed, max_speed)`; `position' = clip(position + velocity', min_position, max_position)`; `velocity' = 0` where `position' == min_position and velocity' < 0` (exact, because `clip` returns the bound verbatim); `done = position' >= goal_position and velocity' >= goal_velocity`; `reward = (100 if done else 0) - 0.1*a**2`.
Reset: one `U(-1, 1)` draw of shape `(B, 1)` scaled to `U(-0.6, -0.4)` (centre `-0.5`, half-width `0.1`, derived from the module literals `_RESET_LOW`/`_RESET_HIGH`) plus a zero velocity column.
**Termination differs from CartPole**: `done` is a *success*, the terminal transition pays the `100` bonus once and the `0.1*a**2` penalty is charged on it too, and afterwards the state is frozen (`enp.where(enp.expand_dims(alive, 1), next_obs, obs)`) **and no further reward is accumulated** — so the accumulator is masked by the **pre-step** alive flag, because the frozen post-goal state still satisfies `done` and an unmasked bonus would be re-awarded every remaining timestep.
The mask is retired with one `enp.where(done, consts.false, alive)` (`consts.false` is the bundle's rank-0 in-trace bool), not a `logical_not` feeding a `logical_and`: same bool mask, one op instead of two.
Row assembly: the carry is the `(B, 2)` observation row, but the transition (`_transition`) runs on the two `(B, 1)` columns `_advance` splits out of it, and `_stack_state` rejoins them with `enp.where(consts.position_column, position, velocity)` over the `(1, 2)` boolean `[True, False]` rather than an `enp.concatenate` — numerically identical, and one elementwise op in the row's own domain instead of the per-column copies a `concatenate` lowers to on iree (see the dispatch budget below).
`_advance(obs, action, consts) -> (next_obs (B, 2), done (B,))` and `_loop_body(query, consts)` therefore keep the exact trees `test/unit/problem/test_mountaincar.py` drives, while the algebra itself is column-shaped.
Return bounds `[-(0.1*max_step), 100]` nominally, but `100` is not attainable: the bonus is paid once while `0.1*a**2` is charged on every scoring step of the climb, so `ATTAINABLE_CEILING = 93.0` is the highest admitted `fitness_target` and a target above it raises.
The derivation of that constant, stated in its docstring: the per-step velocity gain is at most `power + gravity = 0.004` (full force with `cos(3*position) = -1`), so reaching the `max_speed = 0.07` clip from rest takes at least `ceil(0.07/0.004) = 18` scored steps, and the shortest travel from the highest reset position (`_RESET_HIGH = -0.4`) to `goal_position = 0.45` is `0.85`, i.e. at least `ceil(0.85/0.07) = 13` more scored steps at up to `0.1` penalty each.
A real climb is longer (~106 steps, ~10.6 of accumulated penalty) and the best reaching policy measured on this box — the bang-bang `a = sign(velocity)` at `P = 8` — returns `90.8` (min `89.1`) at both 999 and 200 steps, so `93.0` is a small margin over the measured best and far below the nominal `100`.
A target below the ceiling can still be out of reach on a short horizon: a structurally minimal climb needs `18 + 13 = 31` scoring steps and a realistic one ~106, and the constructor docstring states that as a caveat rather than rejecting it (no horizon bound is provable beyond that).
Per-step traced ops are count-shaped, not element-shaped: keep `done` and the squared action rank-1 (`enp.reshape`) so no `(B,1)` operand meets the `(B,)` accumulator.
NaN: `tanh(NaN)` → the `0.1*a**2` penalty is NaN → the live step's reward is NaN → `-inf` through `finalize_fitness`; `enp.clip` is `clip(x, lo, hi) = minimum(maximum(x, lo), hi)`, and both ops propagate NaN, so the clip does not fold the poison away.

#### IREE dispatch budget of the step block (measured statically, CPU only)
Counted with the method of the CartPole subsection, at the same reference geometry, `max_step=999` and `L = 3`; `MountainCarContinuous` consults no `kernel_mode` and traces one formulation on every leg.
`MountainCarContinuous` costs **19 dispatches per timestep**: `^bb5` 3 + `^bb7` 4 per level trip + `^bb8` **4**, i.e. **18 981** rollout dispatches per generation at `max_step=999`, in a graph of **443** static sites.
`^bb8`'s 4, with the op group each one carries:
1. `elementwise_10x10_*` — the read-out gather, the `I_INF`→NaN guard, `tanh` and `_transition`'s whole physics (the `10x10` is the `(B, 2)` = `(100, 2)` row buffer rendered from its `memref<10x10x2xf32>`).
2. `elementwise_100_*` — `total'`: the bonus, the penalty, the pre-step alive mask and the accumulation.
3. `elementwise_100_f32f32xi1xi1` — `alive'`.
4. `elementwise_100x2_*` — `obs'`: `_stack_state`'s baked `(1, 2)` select plus the freeze.
The step block is at a floor of 4: one dispatch per carried array tensor (`obs (B,2)`, `alive (B,)`, `total (B,)`) plus one for the physics region, which is a multi-use producer (`math.cos` and the read-out gather are not clonable), while the cheap comparisons are cloned into every consumer region — the goal predicate appears three times although the trace computes `done` once, so materialising it buys no dispatch.
Reaching 3 needs the carried set to drop to two tensors, which is unavailable: `alive` is not recoverable from `obs` (the freeze keeps the pre-terminal observation), and the `(obs, alive, total, index)` carry with rank-1 `alive`/`total` is pinned by `test/unit/problem/test_mountaincar.py` and `_common.returns_of`.
The per-iteration overhead around the step costs **0** dispatches: the trip condition and the counter increment are host-level `arith` ops, not `stream.cmd.dispatch`, so only carried array tensors cost a dispatch.
Measured and rejected, all staying at 4: `alive_first` (`or(alive', and(done, alive))`), `alive_first_direct` (one extra select), `alive_first_and`, and `column_reward` (the whole reward chain in the `(B,1)` column domain).
Also not taken: dropping `clip(tanh, ±1)` (numerically a no-op and −2 ops per step) because it changes the documented Gym-order physics and moves no dispatch.
numpy control: 131 467 executed IR ops per generation, identical to the base tree, with identical RSS.

## Constraints
- Every arithmetic constant is an in-trace `enp.full((), value)` (float32) built **once per rollout, outside the loop** in the environment's `NamedTuple` bundle (plus the int32 `one_step`/`horizon`); a Python float literal would become f64 on the stablehlo path and break iree type unification, and `enp.full` inside the body would pay one Constant op per timestep.
- `evoxc.remainder` is **not** portable (floormod on numpy, fmod on iree); `angle_normalize` is written with `evoxc.floor`, which is bit-identical on both backends. `enp` has neither `floor` nor `remainder`.
- Use non-negative axes (`axis=1`) in `split`/`concatenate`, and broadcast rank-1 masks with `enp.expand_dims`; a traced tensor has no `__getitem__`.
- `enp.clip(x, lo, hi) = minimum(maximum(x, lo), hi)` accepts symbolic bounds, so no Python literal is needed for a bound.
- `_constants()` is built **once per rollout, outside the loop**: `enp.full` is a graph Constant op and the reference interpreter pays per traced op.
- Physics algebra is fixed op-for-op in all three: precomputing reciprocals (`1/total_mass`, `1/(2*l)`, …) or reassociating the float32 arithmetic changes which step a chaotic trajectory dies or reaches the goal on, so returns would stop matching the host-numpy oracles in `test/unit/problem/`.
- Control flow makes CartPole and MountainCarContinuous numpy / iree-llvm-cpu / xla only (TVM rejects `while`/`if`/gather/scatter) and the failure must surface as `evoxc.BackendError`, never a fallback. Pendulum is a `while_loop` too, so the same applies.
- `show` is host-side only (`evoxc.build` + `evoxc.run` on the key it is given), never called from a trace and never called with a schedule of more than one individual.
- Every report graph is built with `**problem.base.build_options(state)`, so `show` runs on the backend/device/compilation options the run registered and a problem used directly (a state registering none) reports from numpy; an unusable backend raises (`evoxc.BackendError`), never a silent numpy fallback.
- Reporting is finite-safe: a NaN-poisoned policy is a real outcome (its fitness is `-inf`), so no report may convert a return with `int()`/`round()` or test it against a bound without `math.isfinite` first — `CartPole` prints `survived n/a (NaN return)`, `MountainCarContinuous` prints `goal n/a (NaN return)`, and `Pendulum` prints `nan`, each with the return still formatted `{r:.2f}`.
- Every numeric knob and every `fitness_target` goes through a `_common` validator (`require_positive_int`, `require_positive`, `require_non_negative`, `require_finite`), so a configuration error is always `TensorNEATError` with a `<Owner>: <name> must be ...` message; a bare `float(...)` and a bare `TypeError`/`ValueError` on the construction path are ruled out.
- `returns_of` is the only place the `(P, R)` layout is assumed; adding an environment means a step helper + a `while_loop` + the same finish step, in one file per environment.
- Only `Pendulum` consults a formulation static: `_rollout` and `show` read `common.schedule_accelerator.kernel_mode(state)` once on the host and trace exactly one of the two carries, so no graph contains both; `CartPole` and `MountainCarContinuous` build one formulation on every leg.
- Files <= ~1000 lines (`cartpole.py` 744, `mountaincar.py` 849, `pendulum.py` 980, `_common.py` 214).
- Per-timestep IREE dispatch inventory at the reference geometry (`L = 3`): `CartPole` `^bb5` 3 + 4·L + `^bb8` 6 = **21** (446 static sites), `Pendulum` 4 + 4·L + 3 = **19** in host mode (445 sites) and 3 + 5·L + 3 = **21** in accelerator mode (414 sites, 22 without the per-query win on 415), `MountainCarContinuous` 3 + 4·L + 4 = **19** (443 sites).
  `^bb5` (the genome's per-query prelude) and `^bb7` (its level loop) are the sibling genome node's, so this node's own budget is `^bb8` 6 / 3 / 4.
  `L` is a **runtime** value — the population's own depth, the level `while`'s trip count — so a total shifts by that leg's per-trip count per `L`: instrumenting `Interpreter._run_block` over 20 `CartPole` generations at the reference geometry (the level body block executes `max_step × L` times) reads `L` 2 at the generation after setup, 3 at the median and 4 at the deepest.

## Measured cost
Rollout component only (`evaluate` traced alone, no genome forward, toy policy — `1.5*sin(theta) + 0.5*theta_dot` for Pendulum, `3*position + 2*velocity + 1` for MountainCarContinuous, `(tanh(theta) - x, 2*theta + 3*theta_dot)` for CartPole), one `evoxc.build` then 7 `evoxc.run`, build excluded, **best median of 3 fresh processes**; evoxc 0.1.0, numpy 2.5.4, iree-base-compiler 3.11 (llvm-cpu), one 20-core box — the Pendulum/MountainCar rows on CPython 3.12, the CartPole rows on CPython 3.14 (an earlier session; the same box on 3.12 reads ≈7 % lower).
The box drifts ±30 % between processes, so the ratios are the load-bearing numbers and single-run medians can move by 2× under contention.
`R` is `repeat_times`; the `build` column is the one-off per static shape.
The toy policies are genome-free callables, so `prepared_query` passes them through unchanged and no query preparation is charged to these rows; the Pendulum rows are the host carry (a state registering no `kernel_mode` reads as `"host"`).

The two continuous environments are cheap enough that the numpy interpreter's fixed per-op cost, not the element count, sets the time: 10× the population costs ≈1.07–1.09× (Pendulum/MountainCar at 200 steps) and 10× the horizon costs ≈2.55× (Pendulum 200 → 500) / ≈5.0× (MountainCar 200 → 999).
Their dynamics bodies are leaner than CartPole's: on the numpy leg a one-generation graph at pop 100 (`max_nodes=50`, `max_conns=100`, seed 42) carries a rollout body block 44 ops wide for Pendulum and 53 for MountainCar, of which 27 and 36 are this node's step algebra and the other 17 are the genome's per-query prelude and read-out that every rollout pays; Pendulum is the leaner one because it carries no alive mask, while MountainCar folds the goal test into the transition it already split.
iree is 3.4–10.0× faster than the numpy interpreter on both components, with a ≈0.65–0.70 s one-off build per shape.

### Per-timestep op budget (numpy interpreter, `P=100`, `R=1`)
The interpreter's fixed per-op cost sets the time, so the executed op count is the cost model: one `cartpole_p100` generation (`max_step=200`) executes **30 994** IR ops at 7.9–8.8 µs/op on this box, and the count is linear in the horizon with no quadratic term.
At the committed protocol of `benchmarks/PERF_NUMPY.md` pass 2 (150 generations, 3 warmup, 3 repeats, numpy) `cartpole_p100` measures **275.24 ms per generation**, 111.0 MiB peak RSS and 0.46 s build.
Of a CartPole timestep's ops ~80 are the forward pass (the level loop's 76, the level `while` itself and the three NaN-seed constant/broadcast ops `forward_prepared` emits per query), 5 are the two loop conditions plus the output read-out, and the remainder is this node's force/dynamics/reward/carry update with its six-dispatch step block.
A rollout prepares its policy query once with `_common.prepared_query(act_fn, batch)` before the loop, so the genome's per-pass operands are derived once per generation instead of once per timestep.
`prepared_query` returns `act_fn.prepare(batch)` for the pipeline's `_NetworkActFn` and passes a genome-free `act_fn` (a unit suite's policy, a user kernel) through unchanged, which is what keeps `evaluate`/`show` working with a plain callable.
The 58-op prelude it hoists (`_padding_safe_attrs`, `_hit_conn_attrs`' `(P,N,K,CA)` gather, `_slot_index`, `_output_row_mask`, `_depth_limit`, the NaN seed) is loop-invariant, so it is derived once per generation rather than once per timestep of every environment.
`repeat_times > 1` is the tiled-sample case of the evaluate path: the prepared pass is derived once for `B = P * R` rows while the schedule and the payload stay at `P`, so the genome's sample expansion (`genome/window.py::by_samples`, `NodeStepMixin._sample_count`) is paid once per generation rather than once per timestep.
At `R=1` (`samples == 1`) that expansion is the identity and emits no op, which is why `R=1` and `R=4` cost the same op count per timestep.
Op-count attribution of one `cartpole_p100` generation: 88 % of the ops execute inside the rollout region and 12 % outside it (transform, speciate, tell and the graph entry); leaf kernel bodies are ≈42 % of the wall time and interpreter per-op work ≈58 %.
Comparability: `xor_p100` is ≈3 900 ops / ≈37 ms because one generation runs **one** population forward pass at `P*S=400` rows, while CartPole runs **200** sequential forward passes of ~80 ops each plus this node's step block per timestep — the ~10× is the 200 policy queries, not a per-gene or per-connection blow-up.

Pipeline level (`pop_batch_size` unset, one generation per `step`, numpy backend): the genome `transform` + `forward` inside `act_fn` is 80–90 % of a generation's evaluate share and this node's rollout is the rest — 6–18 % of it for `CartPole`, 9.9 % for a six-node-hidden `Pendulum` and 17.5 % for `MountainCarContinuous` — so a continuous-control generation is genome-forward-bound, not rollout-bound, and `../CONTEXT.md` holds the per-cell pipeline rows.
A Pendulum generation with a **single-layer** genome instead of the 6-node hidden layer costs ≈228 ms at `P=100/max_step=200`, i.e. the hidden layer roughly doubles the genome forward — worth it for the fitness it buys (see Notes).

Numeric agreement (`P=100`, one key, same toy policies): iree vs numpy per-individual fitness differs by `max_rel` 1.2e-6 (Pendulum 200 steps), 4.1e-7 (MountainCar 200) and 1.8e-6 (MountainCar 999) — float32 rounding only, no structural divergence.
Against a host-numpy **float32** transcription of the documented recurrence fed the graph's own initial states, both environments are bit-identical (`max_abs = 0`) at `max_step` 60, 200 and 999; against a **float64** Gym transcription the same runs differ by `max_rel` 1.2e-6 (Pendulum 200 steps) and 9.9e-7 (MountainCar 999 steps).
Cross-backend fitness is therefore reproducible to float32 rounding but never bitwise; no test may assert cross-backend trajectory equality.

The compiled leg is launch-bound rather than dispatch-bound at this scale: `backend="iree"` (llvm-cpu) at `max_step=200` reads a 237.9 ms median step with one 7.8–8.0 s build per shape.

## Notes for Agents
- `CartPole.show` computes the survival length only for a finite return (`math.isfinite`), so a NaN-poisoned policy prints `survived n/a (NaN return), return nan` instead of the `ValueError: cannot convert float NaN to integer` a bare `int(round(...))` raises; the `final state` and `mean return` lines print `nan` in the same case.
- Dead in `src/`: `_CartPoleConstants.masscart` (`cartpole.py`, built in `_constants`) is never read — only the derived `total_mass` is — and `_terminated` (`cartpole.py`, `mountaincar.py`) has no caller outside `test/unit/problem`, where it is the rank-1 façade the host-side checks use.
- Duplication: the three `show` methods repeat the same ~45-line skeleton (`TensorSpec` → `report` closure over `_rollout(..., 1)` → `build`/`run` → `to_numpy` → per-repeat print), and the three `_rollout`s repeat `consts → batch → prepared_query → reset → init → while_loop → return`; they differ only in carry arity, the constant bundle and the printed lines, so the one-file-per-environment rule is what keeps the two blocks copied.
- **`evoxc.remainder` is not backend-consistent**: the numpy backend implements floor-mod (numpy `remainder`), while `stablehlo.remainder` — and hence `iree` — is `fmod` (sign of the dividend). A pendulum `angle_normalize` written with it wrapped `-3pi` to `-3pi` instead of `-pi` on iree and inflated the cost by 2.4× while the numpy side looked perfect. The floor form `x - two_pi*floor((x + pi)/two_pi)` is bit-identical on both. This is an `evoxc` doc/implementation mismatch (`evoxc/ops/elementwise.py` documents "sign of the dividend" but numpy does floormod) — out of scope here, worth an upstream report.
- **MountainCarContinuous's reward is deceptive**: `a -> 0` (any small-weight policy) returns exactly `0` (no bonus, no penalty), an aggressive constant policy returns `-0.1*max_step` (`-99.9` at 999, `-20` at 200), and only a bang-bang energy-pumping policy reaches the goal. Measured at `P=8`, `R=1`: `a = sign(velocity)` returns **90.8** (min 89.1) at **both** 999 and 200 steps — the horizon does not change a solving return, which also proves the `100` bonus is paid exactly once, while no-control returns `0` and push-right/push-left return `-0.1*max_step`; the environment therefore discriminates policies at 200 steps. NEAT nonetheless converges to the idle policy: `pop=100`, `species_size=10`, 12–20 generations, `max_step` 200/300/999, with and without `init_hidden_layers=(6,)`, all ended at `-0.007 … -0.0` (never the goal bonus). That is a property of the task, not of the kernel — pick a target near `-0.5` for a demo that terminates, or budget far more generations for the bonus.
- **Pendulum needs a hidden layer to learn quickly**: `pop=100`, `species_size=10`, `max_step=200`, `init_hidden_layers=()` plateaus at `-527` (best of 40 generations, seed 42), while `init_hidden_layers=(6,)` reaches the `-300` target at generation 5 of 20 with a training max of `-271.30` in 2.7–2.9 s wall (the shipped `examples/rl/pendulum.py` configuration, measured on this box; see `examples/rl/CONTEXT.md`). The 6-node layer costs ≈2× the genome forward.
- Recommended demo configurations, measured end to end on `backend="numpy"`, seed 42, `NEAT(pop_size=100, species_size=10, survival_threshold=0.1)` with `DefaultGenome(num_inputs=2, num_outputs=1, node_gene=BiasNode(tanh, sum))` and no `output_transform`:
  - Pendulum (the shipped `examples/rl/pendulum.py`): `init_hidden_layers=(6,)`, `Pendulum(max_step=200, fitness_target=-300)`, `generation_limit=20` → target at **generation 5**, training max `-271.30`, **2.7–2.9 s** wall including startup (per-generation 0.23–0.40 s, build 0.28–0.30 s); `show` reports `-595.12` for the same genome.
  - MountainCarContinuous (the shipped `examples/rl/mountaincar.py`): `init_hidden_layers=()`, `MountainCarContinuous()` at its 999-step default with no problem-level `fitness_target`, `Pipeline(..., fitness_target=float("inf"))` (the pipeline's unreachable target, never a problem knob), `generation_limit=10` → the generation limit, best mean return `-0.00` (the idle policy), **11.6–11.8 s** wall at 0.63–1.24 s per generation (build 0.28 s); see the deception note above for why the goal bonus is out of reach at this budget.
- A NaN arriving **after** an episode has terminated is dropped by `MountainCarContinuous` (the accumulator is masked by the pre-step flag, and accumulation genuinely stops); `Pendulum` never terminates, so every NaN it sees lands. A NaN present while the episode is live always poisons it to `-inf`.
- `MountainCarContinuous.show` reports the goal as `return > 0` rather than `return >= 100 - eps`: the `0.1*a**2` penalty accrues for the whole climb, so a solving episode returns ≈89–91 (hence `ATTAINABLE_CEILING = 93.0`), never ≈100.
  A non-finite return compares false, so the indicator reads `goal n/a (NaN return)` with the return still printed, instead of claiming the goal was missed.
- CartPole specifics worth not re-deriving: the `_loop_body` insertion order is load-bearing (`_nan_rows` selects the NaN into `total` **before** `alive` is updated, so a poison arriving on the step an episode dies still lands); `_terminated` stays rank-1 and is kept for host-side tests, and it is the thin façade over `_death_mask(obs, consts)`, which `_advance` calls on the row it just produced; `evoxc.scan` is **not** export-blocked on iree for this kernel (its output is rank-1, never a rank-3 stack), `while_loop` is simply the cheaper form because it drops the stack; the `(1, 4)` death threshold row is a `evoxc.constant(evoxc.from_numpy(...))` built once per rollout in `_constants` (`enp.full` takes a scalar fill, not a row), and it is the only baked constant of this problem; on `backend="numpy"` keep `max_step` small (cost is ≈0.35 ms per step per 100 individuals, linear in the horizon and nearly flat in the population).
- `_common.py` validators take the **owner name first** (`require_positive_int("Pendulum", "max_step", value)`) so the message shape matches `CartPole`'s original text exactly, which is why all three environments share them; `cartpole.py` passes `"CartPole"` and its suite pins the resulting `<Owner>: <name> must be ...` strings verbatim.
  `require_positive`/`require_non_negative` delegate the conversion and the finiteness test to `require_finite` and only own their comparison, so a non-numeric or non-finite knob reports `"{owner}: {name} must be a finite number, got {value!r}"`, while a finite out-of-range one keeps the pinned `must be positive`/`must be non-negative` text.
- This node's reference oracle for the two continuous environments is a float32 host transcription (in `test/unit/problem/`, owned by the test agent), the same policy the CartPole suite uses; ordering decisions that a test can break: the Pendulum clip happens before the angle update, the MountainCar penalty uses the **pre-clip** action, the min-position velocity reset uses exact float equality, and the bonus is masked by the pre-step alive flag.
- `backend="iree"` runs a full `Pipeline` end to end (`test/backends/test_iree_pipeline.py` drives `Pipeline(backend="iree")` through `setup` plus two `step`s), but the iree numbers above stay component measurements: on llvm-cpu a compiled pipeline is far slower per generation than the numpy interpreter (`benchmarks/BACKENDS.md` holds the measured ratios and the per-shape `iree-compile` cost).
- `_common.to_numpy` duplicates `common/tools.to_numpy`: the latter duck-types a `.numpy()` method (returning an `ndarray` unchanged), the former checks `isinstance(value, evoxc.Tensor)`. Both are host-only (the `show` report path) and all three environments use the `_common` one, while `problem/func_fit/func_fit.py` imports `common.to_numpy`; consolidating the pair is a pointer for the `common` owner, not a change to make in this node.
