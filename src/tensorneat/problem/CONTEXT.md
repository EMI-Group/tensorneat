# problem — task / fitness layer

## Intent
Turn a batch-first transformed genome into one scalar fitness per individual, entirely inside an evoxc trace.
Two families: supervised function fitting (`func_fit/`, dataset fixed at construction) and reinforcement learning (`rl/`, a batched episode rollout `while_loop`ed over a static horizon).
Three RL environments ship, all of them evoxc kernels with no simulator behind them: `CartPole` (discrete control — two logits and a survival-time return), `Pendulum` (continuous torque — one logit squashed to `max_torque * tanh`, a negated cumulative cost) and `MountainCarContinuous` (continuous force with a sparse goal bonus paid once).
Nothing here imports a simulator, `jax` or `torch`: problems own the *algebra* (tiling, reduction, dynamics), the backend owns execution, and a problem is pure host-side configuration (`StatefulBaseClass`) plus plain-Python helpers inlined into the caller's graph.

## API Surface
- `tensorneat.problem` re-exports exactly `BaseProblem`, `FuncFit`, `XOR`, `XOR3d`, `CustomFuncFit`, `CartPole`, `Pendulum`, `MountainCarContinuous`; `problem/__init__.py` is the whole public surface.
- Supervised: `FuncFit(error_method="mse")`, `XOR(error_method="mse")` (S=4, I=2), `XOR3d(error_method="mse")` (S=8, I=3) and `CustomFuncFit(func, low_bounds, upper_bounds, method="sample", num_samples=100, step_size=None, seed=None, error_method="mse")`; `CustomFuncFit` validates its box at construction (all `TensorNEATError`) and `method="sample"` draws `num_samples` rows in total (`./func_fit/CONTEXT.md`).
- `CartPole(max_step=500, repeat_times=1, gravity=9.8, masscart=1.0, masspole=0.1, length=0.5, force_mag=10.0, dt=0.02, x_threshold=2.4, theta_threshold=12.0, reset_scale=0.05, fitness_target=None)` — `input_shape (4,)` `(x, x_dot, theta, theta_dot)`, `output_shape (2,)` (two logits, `out[1] > out[0]` pushes right), return ceiling `max_step`.
- `Pendulum(max_step=200, repeat_times=1, gravity=10.0, mass=1.0, length=1.0, max_speed=8.0, max_torque=2.0, dt=0.05, fitness_target=None)` — `input_shape (2,)` `(theta, theta_dot)` with `theta = 0` **upright**, `output_shape (1,)` (one torque logit), return ceiling `0` (every reward is `-cost <= 0`), so `fitness_target > 0` raises.
- `MountainCarContinuous(max_step=999, repeat_times=1, min_position=-1.2, max_position=0.6, max_speed=0.07, goal_position=0.45, goal_velocity=0.0, power=0.0015, gravity=0.0025, fitness_target=None)` — `input_shape (2,)` `(position, velocity)`, `output_shape (1,)` (one action logit), nominal return ceiling `100` (the one-time goal bonus) but attainable ceiling `ATTAINABLE_CEILING = 93.0` (the `0.1*a**2` penalty of the ~106-step climb), so `fitness_target > 93.0` raises.
- The two continuous problems own the action squashing — `u = max_torque * tanh(logit)` and `a = tanh(logit)` — so a genome used with them must leave `output_transform` unset; a bounded transform would rescale the logit before `tanh` ever sees it.
- `fitness_target` is validation-only in every RL environment: `None` skips the check, a value above that environment's ceiling raises `TensorNEATError`, and a non-finite or non-numeric value (a `bool`, a string, `NaN`/`±inf`) raises the same error through `require_finite`; the attribute is stored exactly as given.
- `problem.rl._common` is the shared host-side helper module — `to_numpy`, the validators `require_finite`/`require_positive`/`require_non_negative`/`require_positive_int` (messages `<Owner>: <name> must be ...`), and the in-trace helpers `returns_of(total, pop_size, repeat_times)` and `prepared_query(act_fn, batch)` (`act_fn.prepare(batch)` once per rollout) — with no dynamics and no module-scope `enp` call, so adding an environment never edits it; everything else per environment (helper names, validation text, `show` report format, per-dispatch attribution) is in `./rl/CONTEXT.md`.

## Protocol (`base.py`)
- `evaluate(self, state, keys, act_fn, transformed) -> fitness (P,)` — fitness is **maximized** and the body runs inside an active trace; `keys` is **one** evoxc key (rank-0 int64 from `evoxc.random.key(seed)`), never a `(P,)` batch, because evoxc has no batched key type and random ops are not vmappable, so a population draws a whole `(P, ...)` block from one key.
- `evaluate` and `show` are plain (undecorated) helpers inlined into the caller's graph, never `@evoxc.defn`: one defn may not call another and the Python callable `act_fn` reaches them by closure.
- `act_fn(batch, *input_shape) -> (batch, *output_shape)` with batch on axis 0, where `batch` may be `P * S` (func fit tiles the dataset, individual-major) or `P * R` (rollout repeats), not necessarily `P`; the problem hands over the whole tiled batch in **one** call and `host_payload._NetworkActFn` regroups it at the trace-time chunk budget, while the schedule and the payload stay at their native `P` rows (the three RL problems pass exactly `P * repeat_times` rows, so `repeat_times=1` makes the per-pass expansion the identity).
- `transformed` is the batch-first schedule from `Genome.transform`; the only thing a problem may read from it is `static_batch_size(transformed)` (the static leading dim of its leaves), because problems cannot otherwise know `P`.
- `input_shape` / `output_shape` are **per-sample** shapes (`XOR` → `(2,)` / `(1,)`), so `input_shape[-1]` equals `algorithm.num_inputs`.
- `setup(self, state=None) -> State` comes from `StatefulBaseClass`; only `FuncFit` overrides it (dataset-budget validation, then `super().setup`), and no shipped problem registers keys or tensors.
- `show(self, state, key, act_fn, transformed)` is **host-side** (never called from a trace): it evaluates a batch of one through `build_options(state)` (`base.py`, in `__all__`, which reads `backend` — default `"numpy"` — plus `device` and `compile_options` off the `State`), so a report comes from the backend the run trained on and a directly used problem reports from numpy, never a silent fallback.
  Each RL environment builds its own one-individual graph over the rank-0 key and reads the return and final observation out of its rollout carry, reporting finite-safely (`survived n/a (NaN return)`, `goal n/a (NaN return)`, a plain `nan` column for `Pendulum`), and it rebuilds the opaque schedule inside that trace with `evoxc.tree_unflatten(evoxc.tree_structure(transformed), list(arrays))` — never a positional `type(transformed)(*leaves)` — so a flat `Transformed` and HyperNEAT's nested `SubstrateSchedule` both round-trip at any static `P`.
- `show_details(self, state, key, act_fn, transformed)` is a host-side no-op hook called by `Pipeline.auto_run` when `show_problem_details=True`.
- `finalize_fitness(fitness)` (`base.py`) is the **single** NaN → `-inf` gate, applied by every shipped problem as its last op (`evoxc.isnan`, a rank-0 `-inf` constant, `evoxc.select`: 3 ops), so a network that poisons itself with NaN can never win selection.
- A problem is always traced: whether a kernel compiles is the backend's business, and `evoxc.BackendError` propagates unchanged (the legacy `jitable` flag does not exist).

## Device Placement
No problem registers a tensor, builds a graph or traces anything in `setup`; datasets stay host numpy on the instance and enter the graph only at trace time via `FuncFit._dataset_constants` (`evoxc.constant(evoxc.from_numpy(...))`), so nothing here calls `.to(device)`.
`build_options(state)` is the subtree's only device-aware surface — it feeds `evoxc.evaluate` in `FuncFit.show` and `evoxc.build` in the three RL `show`s — while the generation graph carrying `evaluate` is built by `Pipeline.step` from `Pipeline._build_options` (real device for the generation graph, `None` for a host-reporting call), so a problem inherits the pipeline's placement and has no device knob of its own.
Host read-back is CPU-side by construction (`common.tools.to_numpy` transfers a non-CPU tensor to `Device("cpu", 0)` first while `rl/_common.to_numpy` still assumes a CPU-kind result), which is why the pipeline hands every `show`/`show_details` a `device=None` host view; static-shape reads are device-agnostic because they int symbolic `shape` entries.

## Function fitting algebra (`func_fit/`)
- Dataset: `inputs (S, I)` and `targets (S, O)` as host numpy, baked at trace time as `evoxc.constant(evoxc.from_numpy(...))` — the only constants this node creates, always `(S, I)`/`(S, O)` and never pre-tiled (XOR: 48 B, XOR3d: 128 B); they travel inside the compiled artifact, so `FuncFit.MAX_DATASET_NBYTES = 1 << 20` (evoxc's `EVOXC_LARGE_CONSTANT_BYTES`) is enforced by `validate_dataset()` at construction, in `setup()` and again at bake time, and exceeding it raises `TensorNEATError`.
- Tiling is **individual-major**: `tiled = evoxc.tile(inputs, (P, 1))` (numpy `tile` semantics) puts sample `s` of individual `p` at row `p*S + s` — one op — then **one** `act_fn` call over the whole `(P*S, I)` batch, then `reshape` back to `(P, S, O)`; `host_payload._prepared_query` only regroups that block at the chunk budget, because `genome/window.py::by_samples` expands the sample-invariant operands inside the pass (`./func_fit/CONTEXT.md`).
- `err = pred - targets` broadcasts the `(S, O)` targets over the population axis, and each `error_method` reduces over sample *and* output axes exactly like the legacy `jnp.mean` (`mse`, `rmse`, `mae`, `mape`, whose zero-target inf is legacy behaviour and is kept); the fitness is `finalize_fitness(-loss)`, so an unconnected/dead topology's NaN loss becomes `-inf`.
- `XOR` (S=4, I=2) and `XOR3d` (S=8, I=3) are literals; `CustomFuncFit` samples the box from a seeded `np.random.default_rng(seed)` (`method="sample"`) or a cartesian grid (`method="grid"`, `step_size`) and builds targets host-side with `np.apply_along_axis(func, -1, inputs)`, so a run is reproducible without touching the global `np.random` state.

## Chunk Budget (tiled evaluate)
`host_payload._prepared_query` regroups one tiled block into unrolled group passes of `host_payload.eval_chunk_rows(device_kind, max_nodes)` rows, prepares each group once at trace time and concatenates the outputs in individual-major row order; the regrouping is bit-identical because every forward op is row-local and the one population-wide quantity, the level `while_loop`'s depth bound, is a per-batch maximum.
On CPU (`device=None` or `"cpu"`) the budget is `EVAL_CHUNK_ROWS = 12_500` tiled rows — the measured optimum for the interpreter, which is memory-bandwidth bound and keeps each group's entry-block live set until the generation returns.
On a non-CPU device it is `max(12_500, DEVICE_EVAL_CHUNK_BYTES // (4 * max_nodes))` with `DEVICE_EVAL_CHUNK_BYTES = 1 GiB`, never below the CPU budget: there the group loop is a *dispatch sequence* unrolled at trace time, so a shipped func-fit batch (`custom_pagie_p500`: 250 000 rows at `max_nodes=50`) is one unchunked pass instead of 20 copies of the forward.
The budget is a host-side static read at trace time and is appended to `Pipeline._shape_signature`, so a CPU-built executable is never reused for a device leg (or the other way round).
Both sides slice through `_slice_batch`, which requires every non-scalar leaf to carry `pop_size` on axis 0 and raises `TensorNEATError` on a leaf whose leading axis cannot be established.

## CartPole algebra (`rl/cartpole.py`)
- Classic Gym `CartPole-v1` with Euler integration: `dt=0.02`, `g=9.8`, `masscart=1.0`, `masspole=0.1`, half-pole `length=0.5`, `force_mag=10`, dead when `|x| > 2.4` or `|theta| > 0.2095 rad` (12 deg), reset `U(-0.05, 0.05)^4`; `input_shape (4,)` = `(x, x_dot, theta, theta_dot)`, `output_shape (2,)` = two logits with "push right" iff `out[1] > out[0]` (`enp.split` + `enp.greater`, a tie pushes left), so the problem owns the discrete decision and the genome must not set an `argmax`-style `output_transform`.
- One `evoxc.while_loop` over `max_step` with carry `(obs (B,4), alive (B,), total (B,), step ())`, `B = P * repeat_times`, individual-major; `total += alive` before the transition (the failing step still scores), the Euler row and the death test share one fused op against a baked `(1, 4)` bracket, and `enp.where(enp.expand_dims(alive, 1), next_obs, obs)` freezes the state — no `cond`, static trip count, constant carried dtypes.
- Because episodes are frozen an individual's return is its survival time, so `max_step` is the fitness ceiling and `fitness_target > max_step` raises; randomness is one `evoxc.random.uniform(key, (B, 4), low=-reset_scale, high=reset_scale)`, and NaN logits push left but are censused into `total`, so that individual's fitness is NaN → `-inf`.
- Physics is fixed op-for-op (a reassociated or reciprocal-precomputed float32 chain changes which step a chaotic trajectory dies on and breaks the host-numpy oracle in `test/unit/problem/test_cartpole.py`), and a traced tensor has no `__getitem__`, so lanes come from `evoxc.ops.slice`.
- IREE cost: the step block is **6** dispatches, so a timestep is `3 + 4·L + 6` = **21** at `L = 3` (4 200 rollout dispatches per generation at `max_step=200`) and numpy executes 30 994 IR ops per generation; the step is one unconditional spelling (no `kernel_mode` gate), fewer dispatches and no extra numpy work than the split form (`./rl/CONTEXT.md` holds the attribution and the rejected variants).

## Pendulum algebra (`rl/pendulum.py`)
- Gym `Pendulum-v1` with Euler integration: `dt=0.05`, `gravity=10`, `mass=1`, `length=1`, `max_speed=8`, `max_torque=2`, `theta = 0` **upright**, reset one `U(-1, 1)` block of shape `(B, 2)` scaled per column; `input_shape (2,)` = `(theta, theta_dot)`, `output_shape (1,)` = one torque logit squashed inside the problem to `u = max_torque * tanh(logit)`, so `output_transform` stays unset.
- One `evoxc.while_loop` over the static `max_step` with no alive mask, every term on the pre-transition state: `cost = angle_normalize(theta)**2 + 0.1*theta_dot**2 + 0.001*u**2`, `theta_dot' = clip(theta_dot + (gravity_term*sin(theta) + torque_term*u)*dt, ±max_speed)` (clip before the angle update), `theta' = theta + theta_dot'*dt`, `total -= cost`; `angle_normalize(x) = x - 2*pi*floor((x + pi)/(2*pi))` because `evoxc.remainder` is floor-mod on numpy but `fmod` on stablehlo/iree.
- Two carries ship, selected at trace time by `state.kernel_mode` through `common.schedule_accelerator.kernel_mode(state)` (default `"host"`): the host carry `(theta, theta_dot, total, step)` at the cost's own `(B,1)` rank and the accelerator carry `(row (B,3), step ())` with `row = (theta, theta_dot, total)` assembled by one affine expression; both run the same physics helper, so they cannot drift, and the packed one is gated because on numpy it costs +805 executed ops per generation (27 860 against 27 391).
- Return bounds: a per-step cost is at most `pi**2 + 0.1*max_speed**2 + 0.001*max_torque**2 = 16.2736`, so the fitness lives in `[-max_step*max_cost, 0]` and `fitness_target > 0` raises; NaN poisons through the action penalty (`tanh(NaN)` → `0.001*u**2` → the accumulator) rather than a census.
- IREE cost: the step block is 3 dispatches, so a timestep is `4 + 4·L + 3` = **19** in host mode and `3 + 5·L + 3` = **21** on the accelerator leg at `L = 3`; `repeat_times` repeats are individual-major (`row p*R + r`) and `evaluate` means `returns_of(total, P, R)` over axis 1.

## MountainCarContinuous algebra (`rl/mountaincar.py`)
- Gym `MountainCarContinuous-v0` with Euler integration: track `[-1.2, 0.6]`, `max_speed=0.07`, `goal_position=0.45`, `goal_velocity=0.0`, `power=0.0015`, `gravity=0.0025`, reset a `U(-0.6, -0.4)` position plus an exact zero velocity; `input_shape (2,)` = `(position, velocity)`, `output_shape (1,)` = one action logit squashed inside the problem to `a = tanh(logit)`, so `output_transform` stays unset.
- Exact Gym order on the pre-transition state (`force = clip(a, -1, 1)` is a no-op kept for faithfulness, the velocity is clipped before the position integrates, and the min-position reset is tested with exact float equality because `clip` returns the bound verbatim), `done = position' >= goal_position and velocity' >= goal_velocity`, and the reward `where(done, 100, 0) - 0.1*a**2` is charged on the **pre-clip** action like Gym.
- **Termination differs from CartPole**: `done` is a *success* — the terminal transition pays the bonus and its penalty, and the accumulator is masked by the **pre-step** `alive` flag because the frozen post-goal state still satisfies `done` and an unmasked bonus would be re-awarded every remaining timestep.
- Return bounds `[-(0.1*max_step), 100]` nominally, so the gate is `ATTAINABLE_CEILING = 93.0`: a `sign(velocity)` policy returns `90.8` (min `89.1`) at both `max_step` 999 and 200, because the bonus is paid once while the penalty accrues over the ~106-step climb (`./rl/CONTEXT.md` holds the derivation).
- NaN poisons through the action penalty and survives the clip (`enp.clip` propagates NaN), so a live step poisons the accumulator with no census, while a NaN arriving only *after* termination is genuinely dropped; `show` reports "goal reached" as `return > 0` and prints `goal n/a (NaN return)` for a non-finite return.
- IREE cost: the step block is 4 dispatches, so a timestep is `3 + 4·L + 4` = **19** at `L = 3` (18 981 rollout dispatches per generation at `max_step=999`); the floor argument is in `./rl/CONTEXT.md`.

## Measured Cost (this box, numpy reference backend unless stated)
This session's per-generation medians on this tree (2026-11-06, this worktree): numpy `xor_p100` **33.04 ms**, `xor_p500` **112.68 ms**, `xor_p1000` **177.43 ms**, `custom_pagie_p500` **847.13 ms**, `cartpole_p100` **248.70 ms**; the same five cells on iree+rocm are **17.42 / 13.24 / 16.29 / 16.18 / 150.41 ms**.
`benchmarks/PERF_NUMPY.md` stays the committed record of the earlier numpy passes (their own trees, same-session A/B pairs and peak-RSS figures); the box drifts ±30 % between sessions, so a cell is comparable only within one session.
The reference interpreter's cost law is **op count times per-op overhead**, and the per-op price is element-volume dependent: `cartpole_p100` executes **30 994** IR ops for 248.70 ms (≈8 µs/op) while `xor_p500` executes **7 592** for 112.68 ms (≈15 µs/op, its tensors are population-sized).
On iree+rocm a generation costs `max(host submission, device)`: a flat graph is ≈63 µs of fixed cost plus ≈2.2–2.5 µs per dispatch, one `while` iteration costs ≈50 µs because its condition is read back to the host, and `Tensor.to(cpu)` costs ≈47–60 µs per leaf.
So the numpy interpreter still wins every cell except the RL rollout, the leg's worst case (150.41 ms on rocm against 248.70 ms on numpy), where each of the `max_step` iterations pays the host read-back on top of its 19–21 dispatches.
Function fitting: the evaluate *segment* (transform + tiling + `genome.forward` over the tiled batch + loss) is ≈15–30 ms of an `xor_p500` generation, so `tell`/speciation dominates, and tiling + loss alone is 0.15 ms (XOR pop 500) with `evaluate` tracing 14 IR ops.
The rollout *component* alone (`evaluate` traced alone, no genome forward) is 3.4–10.0× cheaper on iree-llvm-cpu once built (a 0.06 s numpy build against 0.65–1.24 s per shape on iree), and it is linear in `max_step` and nearly flat in `pop` (10× the population is ≈1.07–1.09×) because the fixed per-op cost sets the time.
At pipeline level the rollout is only 6–18 % of a CartPole evaluate share and the genome forward is the rest, so a continuous-control generation is genome-forward-bound too; `./rl/CONTEXT.md` is the authoritative per-cell table and the rows here are the compact subset.
`Pipeline` builds and runs end to end on `backend="iree"` (`test/backends/test_iree_pipeline.py` is the gate), so the shipped default stays `numpy`.

## Constraints
- Compute path uses only `evoxc.numpy as enp` plus top-level `evoxc.{isnan, select, tile, floor, from_numpy, constant}`; there is no eager mode, so never call `np.*` on a traced value.
- `enp` gaps to remember: no `isnan`/`isfinite`/`tile`/`take`/`take_along_axis`/`einsum`/`floor`/`remainder` (tiling is `evoxc.tile`, wrapping `evoxc.floor`, the rest compose from `broadcast_to`, `reshape`, `split`, `concatenate`, `where`, `select`).
- Never wrap an angle with `evoxc.remainder`: it is floor-mod on numpy but `fmod` on stablehlo/iree, which silently made iree Pendulum returns 2.36× wrong while numpy looked perfect; `x - two_pi*floor((x + pi)/two_pi)` is bit-identical on both.
- Rank hygiene whenever a `(B, 1)` action meets a `(B,)` accumulator: reshape the squared action and the goal mask to rank 1 (numpy broadcasting would silently build a `(B, B)` total), and broadcast `(B,)` masks with `enp.expand_dims` before `enp.where`.
- `MountainCarContinuous`'s terminal reward must stay deferred behind the pre-step `alive` mask, otherwise the frozen post-goal state re-awards the `100` bonus every remaining timestep.
- `enp.clip` is `minimum(maximum(...))` and propagates NaN, so a NaN continuous action survives the clip: never add a fallback that would fold the poison away, and never "sanitise" a clipped action.
- `enp.zeros/ones/full/empty` are **graph** constants that materialise their whole array (the concrete creators of the same name live at top level `evoxc.*`); create them inside the traced function, never at module scope, and never with a shape that scales with the population or the horizon.
- Scalar float literals become f64 constants on the stablehlo/iree path, so every arithmetic constant in a kernel is built with `enp.full((), v)` to stay float32; each environment bundles them once per rollout, outside its loop.
- Static-shape hygiene for compiler backends: non-negative axes in `concatenate`/`split` (`axis=1`, not `axis=-1`) and loop outputs kept rank-1 — a rank-3 stacked output needs a rank-3 `scatter` that the v1 stablehlo exporter rejects.
- `show`'s `act_fn` must predict over **traced** tensors (its schedule is rebuilt in the same trace): `Pipeline._constant_act_fn` satisfies that, a host-bound `functools.partial(algorithm.forward, ...)` raises `evoxc.TraceError`.
- No Python control flow over traced values: horizon, dataset size and population are static config, and the only loops here are the three RL `while_loop`s, each with a static trip count (`step < horizon`).
- Errors: constructor/config validation raises `tensorneat.common.errors.TensorNEATError`; shape/dtype/backend errors from evoxc are never caught or re-wrapped.
- Files ≤ ~1000 lines; the tiling + reduction lives once in `func_fit/func_fit.py`, each RL environment is one self-contained file, and the genuinely generic RL host helpers live once in `rl/_common.py`.

## Test Strategy
- `test/unit/problem/` (numpy, no optional dependency) is the node's real suite: `test_func_fit.py` pins the tiling order (`p*S + s`), every `error_method` against a numpy oracle, the NaN → `-inf` mapping and the XOR/XOR3d literals; the three RL suites hold host-numpy dynamics oracles and pin the load-bearing orderings (death at `|theta| > 12 deg` with the state frozen, the velocity clip before Pendulum's angle update, the pre-clip MountainCar penalty, the exact min-position velocity reset, the one-time bonus masked by the pre-step alive flag), the ceilings, per-key determinism, the `<Owner>: <name> must be ...` validator text and the NaN → `-inf` paths; `test_problem_api.py` pins shapes, `static_batch_size` on a fake schedule and the `TensorNEATError` config paths.
- `test/parity/` (needs the `bench` extra) diffs the func-fit fitness of a fixed random network against `benchmarks/legacy_jax/tensorneat_legacy/problem/func_fit` for `XOR`, `XOR3d` and `CustomFuncFit(method="grid")`, float32, `rtol≈1e-5`; there is no RL parity oracle (the legacy RL problems were deleted), so the unit-test host transcriptions are the reference.
- Beyond the suites: `Pipeline` end to end on numpy (`setup`/`step`/`auto_run`/`show`) through the shipped `examples/func_fit/` and `examples/rl/` scripts, plus `test/release_gate_no_jax.py`.
- Coverage gaps: the chunk budget is pinned only on its CPU branch (`test/unit/test_host_payload.py` and the two `test/integration` chunking suites monkeypatch `EVAL_CHUNK_ROWS`; nothing exercises `eval_chunk_rows` with a non-CPU kind or asserts the budget in `Pipeline._shape_signature`), and neither the dataset budget (`MAX_DATASET_NBYTES`/`validate_dataset`) nor the `evaluate` op count has a test.

## Known Issues
- The HyperNEAT report path is structurally sound here but untested: `HyperNEAT._query_substrate` derives its batch from the payload's leading dimension, `static_batch_size` walks the nested `SubstrateSchedule` leaves (all `P`-first) and `FuncFit.show` rebuilds the container with `tree_unflatten`, yet no test runs `show` or `evaluate` on a `SubstrateSchedule` — the suite's only `show` coverage is `XOR` and `CartPole`.
- `finalize_fitness` maps NaN only, so a `+inf`/`-inf` fitness passes through unchanged; no shipped problem can produce `+inf` fitness (func-fit `mape` makes the *loss* `inf`, so the fitness is `-inf`), but "NaN or infinite fitness is mapped to `-inf`" holds for NaN alone.
- `CartPole` poisons on a NaN logit at any step, including steps after the episode died (the frozen observation is re-queried every remaining timestep), while `MountainCarContinuous` drops a NaN arriving after the goal; the pair is asymmetric and only the per-environment docstrings say so.
- Untested in `test/unit/problem/`: `Pendulum.show` and `MountainCarContinuous.show` never run, no `show` runs with `repeat_times > 1` or a NaN-poisoned genome (so the finite-safe `n/a`/`nan` paths are pinned by nothing), the `require_finite` rejection of a non-numeric and of a non-finite knob is never exercised, and the `CustomFuncFit` box validation and `cartesian_product`'s `TensorNEATError` paths are never hit.
- The RL environments control-flow on purpose, so they run on numpy / iree-llvm-cpu / xla only: TVM rejects `if`/`while`/gather/scatter, an unlowerable kernel raises (`evoxc.BackendError`), and cross-backend RL fitness is not bitwise reproducible (numpy and iree round float32 differently, so a sensitive policy can differ by ±1 step; agreement is `max_rel ≈1e-6`), so no test may assert cross-backend trajectory equality.
- `MountainCarContinuous`'s standard reward has an idle optimum of exactly `0.0` — an action near zero pays neither the `100` bonus nor the `0.1*a**2` penalty — so a tabula-rasa run converges there instead of to a solving policy: a `sign(velocity)` bang-bang policy nets ≈`90.8` while NEAT at pop 100 ends at `-0.007 … -0.0`, so target `≈-0.5` for a demo that terminates.

## Notes for Agents
- Cross-node findings (not editable from here):
  - `genome/default.py`'s forward value seed is `genome/window.py::fill` — one element plus a `broadcast_to`, materialised at the evaluated row count — so it puts no population- or sample-scaled NaN constant into a func-fit graph.
  - `common/tensorization.py` bakes 104 population-scaled constants (3.43 MB at P=200, 8.56 MB at P=500).
  - `problem/base.py::finalize_fitness` costs 3 ops where `evoxc.nan_to_num(x, nan=-inf)` would cost 1; not taken (inf semantics differ from numpy's).
  - `rl/_common.to_numpy` duplicates `common/tools.to_numpy`; both are live (the three RL `show`s use the copy, `func_fit.py` the original), so consolidating them is a sibling-node decision.
  - The per-timestep genome cost (`^bb5` prelude and `^bb7` level loop at 4–5 dispatches per trip) is the sibling genome node's; `genome/CONTEXT.md` holds that inventory and the level-loop refutations.
- On numpy, keep `max_step` small for every RL environment (cost is linear in the horizon, ≈0.35 ms per step per 100 individuals for CartPole, ≈0.23 for Pendulum, ≈0.30 for MountainCar) and expect a generation to be genome-forward-bound, not rollout-bound; `./rl/CONTEXT.md` holds the recommended demo configurations (Pendulum needs a 6-node hidden layer to reach ≈`-271` at generation 5; MountainCarContinuous converges to the idle policy, so aim at `-0.5`).
- Re-measure with the dev harness pattern (`problem.evaluate` traced alone with a trivial `act_fn` for this node's own cost; a `step` with `evaluate` monkeypatched to zeros for the evaluate share), never with a single-shot pipeline run, because build (0.5–1.2 s) dominates one generation at small budgets.
  For executed-op counts, wrap `evoxc.backends.numpy.interpreter.Interpreter._run_block`, key each block by `id(block)` and accumulate `(executions, len(block.ops))`, clearing the table between the build step and the measured one; a `forward_prepared` monkeypatch returning zeros isolates the environment share.
