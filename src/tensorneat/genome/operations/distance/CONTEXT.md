# distance — compatibility distance: pair-wise, digest merge, dense single-centre, grouped k-centre

## Intent
Answer one question per parent pair, batch-first: how different are these two genomes?
The result feeds speciation, so it must be symmetric, exactly `0` at identity, `0` (never NaN) for an empty pair, and normalised by the larger gene count so pairs of different sizes stay comparable.
Speciation measures centre genomes against the whole population twice per generation, so the population side is packed and sorted **once** (the digest) and only the centre side is per-call work.
This node offers the same arithmetic in four shapes, all ending in one scalar tail (`DefaultDistance._scalar_distance`), which is what makes them bit-identical rather than merely close:
- the pair-wise `__call__` (contract unchanged; used by parity tests and by callers holding two explicit parents);
- the two-phase `prepare` / `measure` **merge**, whose population half is prepared once per generation;
- inside `measure`, a **dense key-table fast path for a batch-1 centre** (`dense.py`), resolving the alignment with gathers instead of a sort;
- a **grouped `k`-centre** call against `group_digest(digest, k)`: `k * P` centre rows measured in one call, bit-identical (`tobytes()`) to `k` separate `P`-row calls — verified but wired into no production path (see `## Grouped route`).

## API Surface
`BaseDistance.__call__(state, genome, node_keys1, node_attrs1, conn_keys1, conn_attrs1, node_keys2, node_attrs2, conn_keys2, conn_attrs2, *, consts=None) -> (P,) float32` — validates both parents field by field (matching shapes, key rank 2 or 3, attribute rank 3, keys and attributes agreeing on `(P, M)`; a violation raises `ConfigError`) and returns `gene_distance(node family) + gene_distance(conn family)`.
`BaseDistance.prepare(state, genome, node_keys, node_attrs, conn_keys, conn_attrs, *, consts=None) -> DistanceDigest` — one pass over the population, returns the reusable digest.
`BaseDistance.measure(state, genome, centre..., digest, *, consts=None) -> (R,) float32` — one or more centre genomes against every digest row; the centre batch is `1` (broadcast, dense fast path when enabled) or `P` on a plain digest, and exactly `group * P` on a grouped one.
`grouped.group_digest(digest, group) -> GroupedDigest` — tiles a plain digest `group` times (inside the active trace, once per digest a caller reuses); `group` must be a positive `int` (`ConfigError` naming it otherwise).
`grouped.GroupedDigest` — `(node_keys, node_attrs, node_count, node_key_cols, conn_keys, conn_attrs, conn_count, conn_key_cols, node_statics, conn_statics, pop_size, group)`; the ten tensor/statics field names are `DistanceDigest`'s, so `measure`'s merge body reads either digest type unchanged, and `pop_size`/`group` are static ints (trace-local metadata, never a graph-boundary value).
`grouped.validate_centre(name, payload, digest) -> rows` and `grouped.validate_family(...)` are the host-only shape checks of the grouped route — the plain route calls the same `validate_family` from `base._validate_digest`, so the two wordings cannot drift.
`BaseDistance._single_centre_enabled(genome) -> bool` is the host-side twin of the hook's static gate: `False` in the base class, `dense_single_centre and dense.enabled(node gene) and dense.enabled(conn gene)` in `DefaultDistance`.
`BaseDistance._measure_single_centre(pool, state, genome, payload, digest)` is the hook: `None` in the base class, the dense route in `DefaultDistance` while `dense_single_centre` is `True` **and** both gene families pass the static gate.
`BaseDistance._merge_both(pool, state, genome, payload, digest)` is the one spelling of the row-wise route (both families, one `evoxc.add`), shared by the plain and grouped paths.
`BaseDistance.gene_measure(...)` and the private `_measure_family(pool, ...)` are the per-family drivers: `digest.measure_alignment` then `distance_from_alignment`. `gene_measure` is public with **no in-library caller today** (it starts its own `ConstantPool`).
`DefaultDistance(compatibility_disjoint=1.0, compatibility_weight=0.4, dense_single_centre=True)` — both weights finite and non-negative (`ConfigError` at construction); `dense_single_centre=False` forces the row-wise merge everywhere.
`DefaultDistance._scalar_distance(cnt1, matched, cnt2, attribute_distance, pool)` is the single scalar tail: `(non_homologous * compatibility_disjoint + attribute_distance * compatibility_weight) / max(cnt1, cnt2)`, the denominator floored at `1.0` so an empty pair is `0.0` with no second `select`.
`DistanceDigest(...)` (19 fields, node family first) and `FamilyDigest(...)` (9 fields) live in `digest.py`; `field_names` reports `_fields`, and `test/unit/genome/test_distance_digest.py` pins that literal order, so a new digest concern belongs in a **new** class (`GroupedDigest`), never a field.
`digest.prepare_family(state, gene, keys, attrs, *, key_span, consts=None, dense=False, tail=None)`, `digest.measure_alignment(gene, keys, digest_keys, digest_key_cols, *, statics=None, consts=None) -> AlignedGenes` and `digest.match_rows(...)` are the per-family entry points; `layout.dense_width`/`dense_slot`/`dense_rows` are the table geometry.
`digest.match_rows` and `layout.dense_slot` are kept-public entry points with **no in-library caller today** (`__all__` members documenting the alternatives `measure_alignment`/`dense_rows`, which the live route consumes).
`dense.enabled(gene, genome) -> bool` and `dense.measure_centre(pool, state, genome, distance, payload, digest) -> (P,) float32 | None` are the fast path, whose per-generation statics travel in `digest.<family>_layout` (`DenseLayout`) and whose `cnt2` pair travels in `digest.tail_counts (2, P) int32`.
`AlignedGenes(rows, homologous, count, matched)` is the merge's result: `rows (R, M) int32` redirected to `0` where a gene has no homologue, `homologous (R, M) bool`, `count (R,)` the centre's real genes, `matched (R,)` its homologue count.
`consts` is an optional `ConstantPool`; pass one per top-level kernel entry so identical rank-0 constants cost one op instead of one per use site.
`prepare` and `measure` are **plain traced helpers**, never `@evoxc.defn` (a defn cannot call a defn), so the caller's graph owns them; a digest is a pytree and may be captured in a closure across a trace.

## Merge algebra (`digest.measure_alignment`)
A gene row folds into one `int64` composite, positionally and most significant first in base `_KEY_BASE = 2**31`: a node key is itself, an `(in_key, out_key)` connection key is `in * 2**31 + out`.
`2**31` is the whole non-negative `int32` key range, so the fold is injective for **every** legal key, and it never consults `key_span`.
`key_span` (`S`) bounds only the dense table (and the execution schedule); it must never be used as an injectivity bound.
Digits are not gated per column: `2**31` bounds every legal digit, so no fold can overflow, and an absent row needs no per-digit special case because the payload contract makes *every* key column `I_INF`, which folds to the side's padding sentinel by construction.
The fold is unrolled as `multiply`/`add` steps rather than a weighted `reduce_sum` over the key axis: an innermost-axis integer reduction costs an order of magnitude more than the elementwise pair it replaces.
The **centre side of a multi-column key family folds with a single `dot`**: `_pack_centre` contracts the key axis of `cast(keys, int64) (R, M, 2)` against `fold_i64 (2, 1)` `[2**32, 2]`, so `k0 * 2**32 + k1 * 2` — exactly the positional fold with the tag scale applied — lands in 4 traced ops (cast, dot, reshape, `not_equal`) instead of 11.
The cast in front of that `dot` **stays**: a mixed-dtype `dot` (`int32 × int64`) is accepted by the trace and by the numpy interpreter but is **not exportable** — the StableHLO writer forwards `dot` operand dtypes verbatim (`backends/stablehlo/writer.py::_emit_dot`) and emits an invalid `stablehlo.dot_general`, with no `lower()`-time error, so only an actual export reveals it.
`multiply` is the one op where mixed dtypes are safe: the writer equalises elementwise operands with a `stablehlo.convert`, which is why the node family's single key column folds as `multiply(int32_keys, tag_scale_i64)` in **one** op (see `## Cost`).
Two folded columns are all an `int64` composite can hold (`2 * 31 = 62` bits), so a gene with more columns (`OriginConn`'s `historical_marker`) folds its first two (one `slice` to `_prefix`) and **verifies** the rest row for row (`_key_row_matches` against `digest_key_cols`), keeping homology equal to full-tuple key-row equality.
The low bit of the sort key is the side tag (population `1`, centre `0`); each side's padding rows collapse onto their own sentinel: `_PAD_CENTRE` — the fold of an all-`I_INF` row, `2**63 - 2**32 - 4` — and `_PAD_POPULATION = _PAD_CENTRE - 2`.
Defining the centre sentinel *as* the fold of an absent row is what lets the `dot` path skip its `select`: an absent row already lands on `_PAD_CENTRE`, and the mask is read off the folded value.
It must not be `int64` max: max equals the next composite after a padding row and would manufacture a false homologue at the last merged position.
Injectivity plus the tag make a homologous pair exactly an adjacent `(centre, population)` pair whose composites differ by one; the parity is what proves the neighbour is a real population gene, so no separate tag test is needed.
The merge concatenates the **digest side first**, the centre second and one **trailing column** of `_PAD_CENTRE` third: the merged index of a population gene *is* its digest row, the tail reads its row table straight off the successor, and every centre gene has a successor position in range.
Sequence per family: `concatenate` to `(R, 2M + 1)`, one **stable** `argsort`, its inverse via a second **stable** `argsort` of the permutation, then two centre-width gathers (the successor's merged index and the composite it carries).
Nothing later is `2M`-wide: the homology test, the row table and both counts stay at the centre's own width `M`.
The inverse permutation is the measured formulation: `argsort(order)` is two ops while scattering the ranks costs four to eight, and the stable `argsort` is also 1.05 → 0.29 ms at pop 1000.
The trailing column is why the successor gather needs **no** `minimum` clamp and no in-range mask: `_PAD_CENTRE` is the merged row's maximum, so no centre gene sits at the last position.
`evoxc.slice(x, start, limit)` takes **lengths**, not end indices, which is why the centre slice is `((0, count), (pop_size, count))`.

## Traced op census (static, `xor_p500` generation 0, `evoxc.trace` of the generation kernel)
`measure_distance` traces to **exactly 6 `reduce_sum` and 4 `argsort` per call** (no `reduce_max`, no `scatter`, no `constant`), and `prepare_distance` to 4 `reduce_sum`, 2 `argsort` and 50 `constant`s, so one `xor_p500` generation executes **244 reduces and 162 sorts** from this node: 4 + 40×6 and 2 + 40×4.
The 6 reduces of a call are, per gene family, `cnt1 = reduce_sum(valid)` (`digest.py:760`) and `matched = reduce_sum(homologous)` (`:761`), both `(R, M) bool → (R,) int64` at `axes=(1,)`, plus the attribute term `reduce_sum(select(homologous, |Δattr|, 0))` (`default.py:388`) as `(R, M) float32 → (R,) float32`; `cnt2` rides in `digest.tail_counts` and costs no reduce.
Their width is the **gene axis `M`, never the merge width**: `(R,50)` and `(R,100)` at `max_nodes=50`/`max_conns=100`, rank 2, `axes=(1,)` — so an accelerator profile's `reduction_500x201x201_*` / `reduction_500x101x101_*` families are **not** these `reduce_sum`s (they are the count-mode `argsort` expansion; see `## Compiled-backend dispatch census` below).
The 4 sorts per call are one `argsort((R,101|201) int64, stable=True)` (`digest.py:713`) plus its **`int32`** inverse `argsort(order, stable=True)` (`:720`) per family; `prepare` adds one stable `int64` `argsort` per family (`:530`) over `(R,50)` / `(R,100)`.
Both `measure` bodies sit in the caller's two `species_size`-iteration scans, and `evoxc.scan` inlines step 0 at the enclosing level, so the main block carries 16 distance reduces (4 from `prepare` + 6 from each scan's inlined first iteration) while each scan body carries 6.
`measure` emits no `scatter` on the merge route, so the dense route's scatters (`layout.reorder`, the owner/attribute table writes) are absent from the traced pipeline graph entirely.
`cnt1` is **row-invariant under the live call site's centre tiling** (`algorithm/neat/_kernels.py::single_payload` broadcasts one row to `P`), so 2 of the 6 reduces per call are redundant there (80 of the 240) and both are integer, so computing them on one row and broadcasting is bit-identical; authorising that needs a caller-side declaration, because a generic `P`-row centre may hold `P` different genomes.
Casting the two bool reduces' operand to `int32` before the sum is value-identical (counts ≤ `max_nodes`/`max_conns`) and halves their element bytes on a backend whose int64 reductions dominate.
`xor_p500` (`species_size * pop_size = 10 000 > GATED_ROWS = 6 000`) is on the **ungated** caller path, `DistanceRows.matrix` for scan 1 and `compute_row` for scan 2, i.e. 20 + 20 `measure` calls and no `gated_row` wrapper (`algorithm/` owns that seam).
## Sort semantics (`stable=True` is a performance rule, not a tie rule)
Every `argsort` in the merge and the digest passes `stable=True`, and on the reference interpreter that is where the time goes: numpy's stable kind is timsort, which detects the runs the data already contains.
The digest side of the merge is ascending by construction, so the merged sort sees one sorted run of `M` beside the centre's `M` shuffled values: **1.43 → 0.28 ms** per `(1000, 200)` `int64` block at `M = 100`, and the inverse permutation **1.05 → 0.29 ms**.
`prepare_family` gains for the same reason: 1.51 → 1.25 ms (node) and 1.43 → 1.22 ms (conn) at `P = 1000`.
This is safe rather than lucky because none of these sorts has a *meaningful* tie: a homologous pair differs by one, real composites are unique inside a genome, and the only equal values are padding rows, whose attributes are `NaN` on both sides and which can never pass the homology test.
Stability also pins tie order to input order and matches a compiled backend's count-mode `argsort`.
Sort cost is **superlinear in row width, not in element count**: one `(500, 301)` `int64` `argsort` is dearer than `(500, 101)` + `(500, 201)` together, which is why fusing the two families' merges loses and why the grouped route is a wash in milliseconds.

## Compiled-backend dispatch census (`xor_p500`, `--iree-hal-target-backends=rocm --iree-rocm-target=gfx942`, IREE 3.13.0)
The generation graph compiles to **372 `hal.executable.export`s / 372 unique symbols / 226 unique dispatch base names**, and this node's cost on such a target is **the `argsort` expansion, not the reduces**: every count-mode argsort on `(P, M)` emits 8 `(P,M,M)` blocks and 4 wide reduces — two `add dims=[0]` over `(M,P,M)` → `(P,M)` (the stable rank) and two `minimum dims=[2]` over `(P,M,M)` → `(P,M)` (the inverse permutation of the matched index, init `M`, and of the key column, init `INT64_MAX`) — plus one `(P, M, 2M+1)` successor fold, and `digest.py:720`'s int32 `argsort(order)` repeats all four.
At `P=500` these land as `reduction_500x101x101_*` and `reduction_500x201x201_*` (3 `_i64` + 1 `_i32xi32xi64` + 1 `_i32xi32xi64xi64xi64` each), `reduction_500x50x101_i64` / `reduction_500x100x201_i64` (the successor fold) and, once per generation from `prepare`, `reduction_500x50x50_i64` / `reduction_500x100x100_i64` (3 each); all are `iree_gpu.pipeline<TileAndFuse>` with `workgroup_size = [64,1,1]` and `lowering_config = {reduction = [0,0,1|3], thread = [1,1,0], workgroup = [64,1,0]}`, i.e. the reduction axis is tiled across a 64-thread workgroup and **not** serialised into one workgroup (only rank-0-result reduces get `pipeline<Distribute>` + `workgroup_size=[1,1,1]`, and none of those is this node's).
Element volume per generation: 40 `measure` calls × 2 argsorts × 4 reduces × 20.2 M (`M = 201`) ≈ **6.5 G** int64/i32 element touches on the conn family plus ≈1.6 G on the node family, against ≈12 M for the six real per-call `reduce_sum`s (`(500,50)`/`(500,100)`, single-stage — `result_elems = 500 ≤ 1024`, so `split_reduce` never fires).
Root cause is `evoxc`'s count-mode sort emission, and **it cannot be switched off from a call site**: `backends/stablehlo/writer.py::_count_argsort_active` returns True whenever `_region_depth > 0` **or** `_select_inline_depth > 0`, whatever `sort_emission` says, and `_count_sort_active` applies the same rule to the values-sort path ("one rule for every sort emission site"); only a flat top-level block follows the mode (and under `"auto"` still switches to count at extent `>= 32`).
Every live `measure` call except the caller's `scan` iteration 0 is emitted **inside the `evoxc.scan` body**, so `sort_emission="pair"` reaches at most 1 of 20 calls, and the region rule is a **correctness** workaround rather than an optimisation: iree 3.11.0 mis-executes a 2-operand `stablehlo.sort` whose index operand is not a region argument (a loop-carried value sorted in a body and then gathered with the returned index yields the UNSORTED input, measured upstream on a minimal `argsort` + `gather` loop body), and the count composition emits no `sort` op at all.
So the O(M²) fan is removable only by removing the **sort** from the per-call body — which is what the dense route does — never by changing the sort's emission mode.

## Dense single-centre route (`dense.py`)
A genome is a sparse table of `(key, gene)` rows and NEAT keys are small integers, so a **centre** can be scattered into a table indexed by the key itself and **gathered** at the population's own dense index: node slot `= node_key` (width `S + 1`), connection slot `= in_key * S + out_key` (width `S * S + 1`), the trailing slot being the **dump slot** every absent or out-of-range row reads and writes.
Per family per call: `dense_rows` (2–8 ops) → one `concatenate` of the `(M, 1) float32` centre row index with the `(M, A)` attributes into one update block → **one** `scatter` into the merged `(width + 1, 1 + A) float32` table at `slot` → **one** `gather` of that table at the population's `dense` block → the owner column sliced and cast back to `int32` (`owner_at`) → `matched = owner_at < count`, ANDed with exact marker equality when the gene has columns past `_FOLDED_KEYS` → `gene.distance` against the attribute columns of the same gathered block → reorder the per-population-gene distances into the centre's own row order (one flat scatter at `owner_at`, or at `select(matched, owner_at, count)` when a marker column exists) → `reduce_sum`.
**One table, one scatter — a portability requirement, not a cost dodge.** `evoxc`'s StableHLO writer emits an `i32 → i64` `convert` of every `scatter`'s index operand (`_emit_scatter_rank1`/`_emit_scatter_row` → `_emit_to_i64`, then a negative-index clamp and a `(K,1)` reshape), and upstream IREE common-subexpressions two *identical* converts into one value; its StableHLO → Linalg conversion then wants an `i32` index for each `scatter` and inserts two conflicting materialisations, so `iree-compile` dies on `failed to legalize unresolved source materialization from ('tensor<50x1xi64>') to ('tensor<50x1xi32>') that remained live after conversion`. Measured on a scratch harness of `evoxc.scatter(zeros(W), idx, upd, axis=0)` graphs exported through `evoxc.backends.stablehlo.export` and compiled with `iree-compile --iree-hal-target-backends=llvm-cpu`: one `scatter` compiles, three with three **distinct** index tensors compile, three sharing one index tensor fail, and an "distinct" index that canonicalises back (`add(idx, 0)`, `select(true, idx, idx)`) fails too; rank of the destination, destination width and index count are irrelevant.
A gene with trailing marker columns is therefore resolved by **gathering** the centre's own key rows at the owner index — `center_markers (M + 1, marker_columns)` = the centre's trailing key columns with the layout's zero `marker_pad` row appended, gathered at `owner_at` (always in `[0, M]`, because every unowned cell holds `count`) — never by a marker table of its own, which is what shared the slot index with the owner scatter before.
So each family emits exactly **two** scatters at **different** index expressions: the merged table (at `slot`) and the reorder buffer (a flat `(P*(M+1),)` index of `offsets + column`).
The dense route was six scatters per `measure` call (owner, attribute table and marker table per family) and could not be compiled on any backend; it is four (`scatter_152x5xf32`, `scatter_25500xf32`, `scatter_22502x2xf32`, `scatter_50500xf32` at `xor_p500`) and compiles on llvm-cpu and rocm — see `## Test Strategy`, `iree` compile status.
That reorder is the bit-identity requirement: the tail sums over the *centre's* rows, in the centre's row order, exactly like the merge, so the float summation order is unchanged.
The marker-column `select` is a correctness requirement: a `(in_key, out_key)` slot says nothing about `historical_marker`, so a population edge sharing the endpoints with a different marker is not homologous and must not write its `|Δweight|` into that centre row (before the redirect: 20 / 3662 / 1471 mismatched rows at pop 100 / 500 / 1000; after: 0).
Counts: `matched` from the in-range mask, `cnt1` from the centre's present rows (`key != I_INF`, the predicate the digest's `count` uses), `cnt2` from the digest's `count`.
Duplicate key rows inside one genome are outside the payload contract; the dump redirect makes them a last-writer-wins scatter instead of a crash.

## Static gate (never a runtime branch)
`dense.enabled(gene, genome)` is `True` while the family's merged centre table fits `_DENSE_MAX_BYTES = 8 MiB` of float32 (`width * 4 * (1 + attr_width)`) and the width stays inside `int32`.
A trailing marker column costs no table cell, because markers are resolved by a gather over the centre's own key rows rather than by a table of their own.
`S = 150` (`max_nodes = 50`, `max_conns = 100`) gives `22 501` connection cells (≈0.2 MB); `S = 500` (≈2 MB) qualifies; `S = 1000` (8 MB) is borderline and larger spans fall back to the merge — the dense table grows with `S²` while the merge grows with the gene axis `M`.
**Both** families must qualify, or neither does: a partially dense `measure` would have to broadcast the centre payload for the other family, and the row-wise merge is then the honest route.
The switch is on by default because it is *free where it does not apply*: `measure` takes the dense route only for a batch-1 centre and falls back to the merge otherwise.

## Precondition: gene keys inside `[0, key_span)`, validated on host data and reported as `node_oor`/`conn_oor`
The dense table cannot address a key outside `[0, S)`, so such a gene is **unmatched** — exactly like `common.tensorization` drops it from the execution schedule — while the merge and `execute_distance` still match it against the same out-of-range key in the other genome.
The two routes therefore agree on every payload whose keys respect the bound and can differ by up to one gene pair per family otherwise.
`prepare_family` sums `present & ~real` over the gene axis into `FamilyDigest.oor`, carried as `node_oor`/`conn_oor` (`(P,) int64`, `int64` because `evoxc.reduce_sum` returns it); cost is two traced ops per family, four per generation, nothing per `measure` call, and it is computed whether or not `dense.enabled` holds.
`measure` **validates** the precondition whenever `_single_centre_enabled` holds and a leaf is host data: `_host_array` answers `None` for an `evoxc.SymbolicTensor` and otherwise reads the leaf with `common.tools.to_numpy`, so a host digest, a host centre, or both are checked while a traced one is skipped silently.
The population side is checked through `node_oor`/`conn_oor` (a non-zero count lists the individuals and their counts), the centre side through its own present keys, each with `genome.key_span` and the two remedies — keep every allocated structural key inside `[0, key_span)`, or construct `DefaultDistance(dense_single_centre=False)`, whose merge matches any key exactly.
The validation is pure NumPy, adds **zero** traced ops, and runs before the hook emits an op, which is what lets a host call answer `TensorNEATError` instead of a backend `TypeError`.
Inside a trace a value-dependent raise is impossible, so the guard is a host-call guarantee only.
The live allocator already satisfies it: `algorithm/neat/_keys.py::node_keys_for_split` wraps every allocated key into `[max_nodes, key_span)`, and the digest's own counters measure `node_oor == conn_oor == 0` at **every generation 0-39** of eight cells (XOR `p500` seeds 0/1/42/43/44, `p100` seed 0, `p1000` seed 0, XOR3d `p500` seed 42) with the worst present node and connection key **149** against `key_span = 150`, so no live payload reaches this guard.

## Digest fields (batch-first, static shapes)
`node_keys (P, N) int64` / `conn_keys (P, E) int64` — **injective** packed composite per gene row, ascending with the padding sentinel last.
`node_attrs (P, N, NA) float32` / `conn_attrs (P, E, CA) float32` — the attribute rows permuted into that same order, so the merge gathers them positionally; absent rows keep their NaN attributes.
A gene family with no attribute column (`attr_specs = ()`) contributes an empty `(P, M, 0)` block: `_gather_rows` returns it unchanged (a zero-width row has exactly one permutation, itself).
`node_count (P,) int32` / `conn_count (P,) int32` — real (present) genes per individual, the length of the valid prefix.
`node_key_cols (P, N, NK) int32` / `conn_key_cols (P, E, CK) int32` — key columns in the same order, the exact-match oracle for a gene whose key width exceeds `_FOLDED_KEYS`; for a narrower key the fold is already injective, so the field keeps the *unpermuted* key table and the merge never reads it.
`node_statics` / `conn_statics` (`layout.MeasureStatics`: the six merge scalars, `fold_i64 (2, 1)`, the `(P, 1)` trailing `pad_column_i64`, the two `(P, 1) int32` stride tables `offsets`/`offsets_plus_one` of a `2M + 1`-wide merged row, and an `AttrStatics` sub-bundle) — appended last, built once in `prepare_family`, and the reason `measure` traces neither a constant nor an index table.
`node_dense (P, N) int32` / `conn_dense (P, E) int32` — dense key-table slot of each gene, permuted into the digest's order; `node_real`/`conn_real (P, M) bool` — the in-range mask; `node_oor`/`conn_oor (P,) int64` — the precondition diagnostic.
`prepare` writes no RNG and touches no host memory, so a digest is valid for one generation and cacheable for the whole speciate pass.
The centre is *never* prepared: `measure` packs the centre's key rows itself (`_pack`, `_pack_centre`, or `dense_slot` on the fast path).

## Per-trace constant pool (`consts.py`)
`ConstantPool` memoises the rank-0 `int32`/`int64`/`float32` constants a kernel entry needs (`i32`/`i64`/`f32`, keyed by `repr` so `-0.0` and `0.0` stay distinct), because `enp.full((), v, dtype=...)` emits one `constant` op per call and evoxc never deduplicates them.
One pool belongs to **one trace**: a `SymbolicTensor` belongs to one builder, so a pool must never be module-global or cached across `evoxc.build` calls; every entry point starts a private pool when the caller passes none.
Reusing a pooled tensor as several operands is legal and is exactly what collapses the duplicates (503 → 163 `constant` ops per generation when the pool landed).
The pool carries **signed dtypes only** — no unsigned helper exists, and none may be added.
The remaining constants live in `prepare` (50 of its 163 op nodes): `int32` sort/index sentinels, the `int64` fold scalars and the static index tables; `measure` emits none, and `group_digest` emits none of its own either (it reuses the plain digest's scalars).

## Grouped route (k centres per `measure` call) — verified, not wired
Every op of the merge, the aligned-attribute gather, `gene.distance` and the scalar tail is **row-local** (`concatenate(axis=1)`, `argsort(axis=-1)`, flat `gather` on a `p * stride` index block, `reduce_sum(axes=1)`, elementwise masks, `maximum` on the counts), so a `(k * P, M)` centre against a `k`-times-tiled digest is exactly `k` separate `P`-row measurements, in the same per-row float summation order.
What hard-coded `P` was only the static scaffolding — `build_statics`' `offsets`, `offsets_plus_one`, `pad_column_i64`, `AttrStatics.base` and `attrs_rows` — plus the two validation predicates.
`group_digest(digest, k)` therefore does two things and nothing else:
- tiles each of the eight digest arrays with **one** `evoxc.concatenate((x,) * k, axis=0)`, which is legal with a repeated operand and lowers to one `stablehlo.concatenate` (`k == 1` returns the operand unchanged, zero ops);
- rebuilds both statics with `layout.build_grouped_statics`, which reuses every rank-0 scalar / `fold_i64` / `zero_f32` / `tail` from the plain digest and derives only the rows-scaled tables at `rows = k * P`.
Row `j * P + p` of the result is `distance(centre row j * P + p, population individual p)`, so a caller must hand over the `k` centre batches **concatenated on axis 0** (`k` copies of a `P`-row block, one per species slot).
`measure` dispatches on `isinstance(digest, GroupedDigest)` straight to `_merge_both`: no dense route and no broadcast on that path (its batch is `k * P >= 1` by construction and the dense route needs a plain digest).
`validate_centre` raises `ConfigError` naming both shapes plus `group`/`pop_size` when the centre batch is not exactly `rows`, and also when the grouped digest's own leaves disagree.
Measured op counts (numpy, `DefaultGenome(2→1, max_nodes=50, max_conns=100)`, `NEAT(pop_size=P, species_size=20)`, identical at pop 100 and pop 500):
| cell | ops |
| --- | --- |
| `group_digest(k=1)` | 16 |
| `group_digest(k=2/4/P)` | 24 |
The grouped body's traced op count is the plain merge's and is **independent of `k`** (94 on the pre-fusion tree, 93 after the `_pack`/`_tagged` fold) — that is the point of the form: one 93-op body amortised over `k` centres instead of `k` bodies.
A single grouped `k=4` call is cheaper than the four plain calls it replaces (2.16 vs 4.00 ms at pop 100, 8.68 vs 9.52 ms at pop 500), so the kernel's own arithmetic is not what holds the route back.
**No production path calls it.** `algorithm/neat` measures one population-shaped centre per `measure_distance` call — 40 calls per generation on the dense path — and the one wiring that was measured, two centres per call over the dense path's whole scan-1 table at `k = 2`, is rejected on wall time and memory rather than on op count: on `xor_p500` it cuts dispatched ops 7 592 → 6 589 (−13 %), but the 2× wider `(2P, …)` merge intermediates make the call memory-bound, at peak RSS 233.8 → 253.2 MiB (+8.3 %).
Its numpy wall time is bimodal at process level: a fast mode at 152–165 ms (−2…−5 %) against a slow mode at 196–253 ms (+30…+45 %), and 7 of 13 fresh default-environment processes land in the slow mode; the same binary with `MALLOC_MMAP_THRESHOLD_=1073741824 MALLOC_TRIM_THRESHOLD_=1073741824` (brk allocation) is stable at 152 ms against 159–162 ms for the ungrouped form.
`k = 4` loses on both axes (+15 % wall, +30.5 % peak RSS for 6 004 ops), and the variant that additionally pre-measures a second centre table costs +58 % wall at `k = 2`.
So the grouped form buys **op count and call boundaries**, but its wide buffers trigger an allocator mode that flips a −2…−5 % fast path into a +30…+45 % slow one, which a default environment cannot rule out; it becomes the right trade only for a dispatch-bound backend (`iree`/`rocm`) once that leg is validated, and any wall-clock claim has to be measured at the live call site inside its `scan` body, never from the kernel alone.

## Cost law of this node
The reference interpreter charges a roughly fixed **~13 µs per executed IR op** on rank-0/small operands and **0.065–0.10 ms per narrow `(R, M)` pass** at pop 500, so op count is the budget for narrow passes and element width is the budget for the wide `(R, 2M + 1)` passes.
`constant`, `reshape` and `arange` are each one full op, and evoxc never deduplicates constants.
A per-call body runs ~`2 * species_size` times per generation, so **anything that does not depend on the centre belongs in `prepare`**: every rank-0 scalar, every per-individual flat index block and every flat view of a population block travel in `FamilyDigest.statics`.
Ops inside a region pay per trip, so the rule is doubly binding inside the caller's `scan`.
The rejected alternative — a private `ConstantPool` and per-call `enp.arange`/`batch_offsets` inside `measure` — costs 536 rank-0 constant ops plus 160 `batch_offsets` and 160 attribute-index ops per generation, ~20 % of this node's bucket.
What is *not* hoistable is anything derived from the centre payload: `_pack`, the merge, the aligned attribute gather and the scalar tail stay per call.

## Dense versus merge at the live call site (measured; `algorithm/` owns the switch)
`measure` picks its route from the centre's **batch width**, and the live pipeline sends a population-shaped one: `algorithm/neat/_distance.py::DistanceRows.row` / `_kernels.py::single_payload` tile each species slot's single centre row to `pop_size` rows before the call, so every one of the ~40 calls per generation takes the merge.
Measured on a real evolved seed-42 XOR payload with keys inside `[0, key_span)` (build excluded, `REPS = 12`, `ROUNDS = 15`, interleaved two-process A/B, three alternating rounds): the batch-1 dense route is **+15 traced ops and 2.2–2.4× faster in milliseconds** than the tiled merge (163 + 108 vs 163 + 93 ops; dense 1.35–1.44 ms against merge 3.10–3.32 ms, both trees in the same session), because it drops every `int64` merge block and both sorts. The pre-merged-table tree measures 1.35–1.44 ms dense against 3.10–3.19 ms merge (2.21–2.32×) on the same rounds, so the route's advantage is unchanged.
Op count therefore misleads on this comparison: the interpreter's per-op charge is not constant across block widths.
`tobytes()` identity holds for a tiled centre: the tiled merge, the batch-1 dense route and `execute_distance` return the same `(R,)` vector on every measured cell (both gene families, default and `OriginNode + OriginConn`), so the swap is value-preserving wherever `node_oor == conn_oor == 0`.
Projected generation-level effect if `algorithm/` passed the batch-1 centre instead of tiling it (40 calls, `species_size=20`): **−320 executed ops/generation** (−640 tiling ops, +320 for the dense body) and **≈ −50 ms at pop 500 / −92 ms at pop 1000**.
The obstacle is *not* the kernel and, on this tree, not the `key_span` precondition either: the digest's `node_oor`/`conn_oor` sums are **0 at every generation 0-39** in eight cells measured 2026-11-05 — XOR `p500` seeds 0/1/42/43/44, `p100` seed 0, `p1000` seed 0 and XOR3d `p500` seed 42 — with `key_span = 150` and the worst present key **149** (node and conn) in every cell, so the live allocator stays inside the span and the earlier `oor = 2 / 4` reading does not reproduce.
On those live payloads the three centre shapes agree: batch-1 dense, batch-1 merge and batch-`P` merge are `tobytes()`-equal to `execute_distance` on all 10 generations at P = 100/500/1000 (64 000 compared rows, 0 mismatches, 0 raises, `max |Δ| = 0.0`), and the per-call cost reproduces the table (1.385 vs 2.758 ms at pop 500, 2.035 vs 4.499 ms at pop 1000; one `prepare` + 6 `measure`, 2 warmup + 9 timed, marginal = (median total − median prepare)/6).
So the dense route is value-preserving at this call site and no longer portability-blocked: its graph compiles on `llvm-cpu` and on `rocm` (see `## Test Strategy`, `iree` compile status), so the remaining obstacle is only the species pass's centre tiling, which `algorithm/` owns.
A batch-1 centre is never worse even when the dense gate fails: `measure` then broadcasts it itself (`_broadcast_payload`, 12 ops) instead of the caller's 16.

## Constraints
- **No unsigned dtypes in a graph — `iree`'s declared dtype set has none** (`float16/float32/float64/int8/int16/int32/int64/bool`), so a `uint32`/`uint64` operand, result, constant or graph-boundary value makes that backend refuse the whole graph. Use **same-width signed carriers**: a range test is `logical_and(greater_equal(key, 0), less(key, S))` on `int32`, the same truth value for every `int32` while `0 <= S < 2**31` (guarded statically in `layout.dense_width`). The `>= 0` half is not decoration: a negative structural key must land in the dump slot exactly as `I_INF` does.
- Trace-time kernels only: no `jax`/`torch`/`numpy.random`, no `vmap`/`scan`/`while_loop`/`cond`, no Python loop over individuals or over pairs, no eager NumPy. Nothing here is differentiable and nothing draws RNG, so repeated calls are bit-identical.
- `prepare`/`measure`/`group_digest` must stay plain helpers (not `@evoxc.defn`) — they are called inside the caller's graph, and a defn cannot call a defn. `DistanceDigest`/`GroupedDigest` must stay pytrees of tensors so they can be captured in a closure inside a trace; a grouped digest's `pop_size`/`group` ints are metadata only and never cross a graph boundary.
- The fast/slow decision is **static** (gene geometry, `key_span`, the `dense_single_centre` switch, the digest class). No traced value ever drives Python control flow, and a partially dense `measure` is impossible by construction.
- Never use `evoxc.gather(..., axis=1)`: it costs 105 ms at `(P=1000, M=100)`. Every row permutation here is a flat gather with a `p * R + col` index block, and the one scatter that reorders values into centre order is a raw `evoxc.scatter` on a flat index because every index is already inside `[0, M]`.
- `evoxc.scatter` takes **rank-1 indices per axis**: a `(M,)` index scatters an `(M, A)` update block along axis 0, and a per-row index needs the flat spelling.
- Never build an `O(M^2)` per-pair comparison matrix: `(P, 100, 1) < (P, 1, 100)` is 3.3 ms and a `(P, 100, 100)` reduce is 4.4 ms.
- Never derive a composite radix from `key_span`: the composite uses `2**31` for injectivity, and the dense table derives its *slot* from `key_span` only because it is an address, not an identity.
- Every `int64` block is element volume that shows up in the wall clock: `(P, 2M)` int64 is 6.4 MB at `4P = 4000`, `max_conns = 100`, and the merge holds two of them plus the `int32` permutation — which is why the connection family costs twice the node family at the same op count, and why the dense route wins on exactly that family.
- `measure` holds one `(R, M, A)` temporary per call (plus one `(R, M+1)` on the dense route) and a grouped call holds the same shapes at `k * P` rows; peak RSS at pop 1000 is ~2.1 GiB (pop 500: ~1.1 GiB), so a new full-size temporary in this path is a real regression even when it saves ops.
- **Population-scaled seeds go through `genome.window.fill`, never `enp.zeros`/`enp.full`** (`DenseLayout.base` `(P·(M+1),)` and `DenseLayout.zeros` `(P,)` were the last such constants in this node); only genuinely static tables (`key_span`-scaled `(width,)`, index `arange`s) keep `enp.zeros`/`enp.full`.
- Mixed-dtype operands are allowed for **elementwise** ops only (`multiply`, `add`, `subtract`, `maximum`, `select` — the StableHLO writer inserts the `stablehlo.convert`), and never for `dot` or `concatenate`, whose operand dtypes the writer forwards verbatim (invalid MLIR, no `lower()`-time error).
- The attribute distance is masked/redirected so it never reads a non-homologous slot (a `NaN * 0` product would poison a sum), and int option columns contribute `!=` (`1` per changed option) rather than `|id1 - id2|` — that rule lives in `BaseGene.distance`.
- `attr_width == 0` is a supported configuration, not an error case: `_gather_rows` returns the empty `(P, M, 0)` block unchanged, `distance_from_alignment` and `dense._family_terms` skip the attribute term, so such a family's distance is its structural disjoint/excess term alone. Every row stride built from an attribute width must sit behind a static width branch — `enp.arange(0, n, 0)` is a `ZeroDivisionError` on the reference backend.
- Disjoint and excess genes are counted by one term (`cnt1 + cnt2 - 2h`); the non-empty guard rides on the denominator (`maximum(float32(max(cnt1, cnt2)), 1.0)`).
- Key tables are accepted as `(R, M)` or `(R, M, K)` via `alignment.key_rows`; rank-0 integer constants come from the pool because a Python literal would widen an `int32` tensor to `int64`.
- Errors: a parent shape mismatch, a wrong key width, a digest built for another gene axis, a centre batch the digest does not accept (plain: not `1`/`P`; grouped: not `group * P`) raise `ConfigError` (`TensorNEATError`); a host-resident leaf breaking the dense route's key precondition raises `TensorNEATError`; `evoxc` errors propagate unchanged.
- Files ≤ ~1000 lines (`base.py` 993, `digest.py` 951, `layout.py` 725, `default.py` 524, `grouped.py` 373, `dense.py` 353, `consts.py` 107).
  `layout.py` owns every per-generation static of the fast path *and* the digest's static table geometry, which is what keeps `digest.py` under the budget; `digest.py` is one job (the fold, the sentinels, the merge and the digest fields) and is at its ceiling, so a new concern belongs in `layout.py`, `dense.py`, `grouped.py` or a new file; `base.py` carries the two-phase drivers, the `_merge_both` body, the hook pair and the host-side key validation; `grouped.py` carries the grouped digest, its builder and its validation (most of its bytes are docstrings).

## Bit-identity argument (four routes, one tail)
`__call__`/`gene_distance`, `prepare`+`measure` (merge), `prepare`+`measure` (dense) and `prepare`+`group_digest`+`measure` differ only in how the homologue table is produced — `alignment.find_homologous`, `digest.measure_alignment`, the dense key table, or the same merge on tiled rows — and all four feed `_scalar_distance`.
For the dense route: `matched` and the per-gene attribute distances are the *same multiset* as the merge's (a slot is shared exactly when the key tuples are equal), the per-gene values are written back into the centre's own row order before the reduction, and the same `gene.distance` runs on the same rows, so even the float summation order is identical — required because float addition is not associative.
For the grouped route: the tiled statics carry each group's own `p * stride` offsets, every op is row-local and the one population-wide quantity (nothing — the digest rows are per-individual) does not exist, so each row computes exactly what the corresponding plain call computes.
The only escape is a key the dense table cannot address (`>= key_span`), documented above as that route's precondition.

## Test Strategy
`test/unit/genome/test_distance_digest.py` is the shipped regression spec for the digest pair (9 tests, no skips): one module-scoped evolved population (seed-42 `Pipeline` XOR, `pop_size=100`, `species_size=5`, `max_nodes=50`, `max_conns=100`, 2 `step`s, both `DefaultDistance` variants), pinning `prepare`+`measure` `tobytes()`-equal to `execute_distance` on the batch-`P` centre, the batch-1 dense centre and the `dense_single_centre=False` merge (one test per shape, plus one crossing all three), self-distance exactly `0` for every individual and `0` for an empty pair (never NaN), two independent digests measuring `tobytes()`-identically, the digest static contract (`node_count`/`conn_count` lead with the population axis, `tail_counts` equals the two counts, `node_oor`/`conn_oor` equal a host recount) with a `ConfigError` for a centre that disagrees with the digest, and the op budget: marginal `measure` ≤ 120 traced ops against the measured 93 and `prepare` ≤ 210 against 163.
One more test pins the payload invariant the `dot` fold relies on: an absent gene row carries `I_INF` in **every** key column, checked on a real evolved payload for both shipped key layouts (`DefaultConn`, `OriginConn`'s `history` column), because a row with a live trailing column would fold to a live composite and count as a real gene.
The grouped route has **no shipped test yet** and is wired into no production path: its coverage is a `$TMPDIR` harness (real evolved seed-42 XOR payload, 477 assertions, `DefaultDistance()` dense-on, `dense_single_centre=False`, `OriginConn` with three key columns and mixed markers, a zero-attribute connection gene, `k` in `{1, 2, 4, P}`, every group `np.array_equal` to the matching plain P-row call, plus `ConfigError` for `P`/`3P`/`1` centre rows and for `group_digest(…, 0 / -1 / 2.0 / True)`).

## Rejected (measured, so nobody re-derives them)
A **galloping / `log2 M`-step binary search** of each centre composite in the digest's sorted block: ~81 ops against the merge's 41 and **14.06 ms vs 8.60 ms** per wide conn `measure` at pop 1000.
The **narrow per-step spelling** of it (`(P, M)` `lo`/`hi`, ~5–6 dependent ops per step): **211 ops / 4.241 ms against 94 / 2.449 ms** at pop 500, and not bit-identical — the gather at step `i+1` reads step `i`'s `select`, so ~65 dependent ops serialise at ~13 µs each, dearer than the ~0.35 ms the two inverse `argsort`s cost.
**An exact key→row lookup instead of the per-call sort** is not representable for arbitrary `int32` keys, which is why the two `argsort`s are the *price of exactness*: a direct node table needs 16 GiB, a connection table `2**62` cells, and any bounded in-graph hash collides and would report two different genes as homologous.
**Splitting the routes per family** (the node family's homologue test on its `int32` column): 5 ops / ~85 µs against 4 ops / 83 µs, and it would permute `node_key_cols` into the digest — behind on both counts.
A **scatter-derived inverse permutation**: 7 vs 2 ops and 1.05 vs 0.29 ms in isolation, and still behind in the merged body — `_scatter` copies the whole `(P·L,)` base, measured **+8 ops and +0.36 ms per call (+15 %)** against `argsort(order)`.
**`masked_flat_scatter` for the dense attribute reorder**: 18 ops of redirect against 7 for the raw flat scatter.
**A `key_span`-derived composite radix**: aliases genes the moment `algorithm/` allocates a key outside the span.
**Dropping the two `cast(argsort(...), int32)`**: saves 2 ops per family per call but makes three index blocks `int64`, measured ~10 % more milliseconds.
**Folding `(P, M, 1)` key columns through `_pack` to save one `reshape` per column**: `valid` must come back `(P, M)`, so the saved reshape is paid again on the mask.
**Stacking both families' scalars to trace the tail once**: 3 `concatenate`/`reshape` pairs for one op (22 → 21).
**Hashing an out-of-range key into the dense table** (`key % width`): trades a documented precondition for silent collisions.
**Dropping the node family's `_tagged` `select`** the way the `dot` path does: safe (−1 op) but sub-threshold on its own; it is *not* shipped.
**Folding the node family's single key column through `dot`**: a `(P, M, 1) @ (1, 1)` matmul replaces two ops with a cast, a dot, a reshape and the same `not_equal` — more ops plus an `int64` temp.
**Making the centre-side `dot` serve the digest side**: the digest half must stay in sorted order (the run `stable=True` exploits) and its composite is one per generation.
**Removing the trailing padding column and clamping the successor instead**: equal in ops but the clamp needs its own `+ 2M - 1` static and an out-of-range mask, which measured as the larger graph.
**An elementwise `_pack_centre` fold in place of the `dot`**: bit-identical but **2.8×** the `dot` (0.687 against 0.245 ms per connection centre pack at pop 500).
**One fused sort for both gene families** (conn composites shifted into the negative half, one `argsort`): bit-identical and −7 traced ops, yet **+10 %** per call at pop 500 and **+15 %** at pop 1000, because sort cost is superlinear in row width.
**Dropping the side tag so the node family sorts raw `int32` keys**: `np.argsort` of an `int32` `(P, 101)` block is 0.91× its `int64` counterpart, and the reformulation nets −2 ops on one family and +1 on the other — ~2 % of a call, below the risk.
**The remaining value-identical op diet** (slice the `int64` inverse permutation before the `int32` cast; skip the disjoint `multiply` at `compatibility_disjoint == 1.0`; drop the node `_tagged` `select`; skip the weight `multiply` at `compatibility_weight == 1.0`): 94 → 91 traced ops, **−2.5 % / −2.8 %** per call at pop 500 and −2.5 % at pop 1000 — below the wave's 3 % bar.
`_pack_centre` alternative spellings: the `bitwise_left_shift` fold is −3.8 % but `stablehlo.ops.status('shift_left') == 'deferred'`, so it cannot ship; the `multiply` spelling is 0.8 % worse than the `dot`.
**A mixed-dtype `dot`** (`int32 × int64`, dropping `_pack_centre`'s cast): accepted by the trace (1 op) and by numpy, but **not exportable** — `_emit_dot` forwards operand dtypes verbatim and no `lower()`-time check catches it, so it would only fail at `iree-compile`. Rejected on portability, not on ops. The one mixed-dtype fold that *does* ship is the node family's `multiply(int32_keys, tag_scale_i64)` (see `## Cost`), because the elementwise writer inserts the convert.
**`evoxc.tile(x, (k, 1, …))` as the grouped tiling spelling**: it exists and is `v1`, but `concatenate` of `k` repeats is also exactly one op, so `tile` buys nothing.

## Known Issues
No open correctness or contract issue in this node: `measure` (all four routes) is bit-identical to `execute_distance` on every payload, every graph's StableHLO export carries no deferred op and no unsigned dtype, and the shipped suites are green.
The one open *portability* issue is the dense route's graph, which fails `iree-compile` on its `i64` scatter index (see `## Test Strategy`, `iree` compile status); the numpy reference is unaffected and the merge route compiles on every backend measured.
The route, not the kernel, holds this node's remaining cost: the live call site tiles each species centre to `pop_size` rows, so all ~40 `measure` calls per generation take the sort-bound merge instead of the sort-free dense route.
The grouped form removes the per-call scaffolding but not the sort, and it is wired into no production path: at `k = 2` on `xor_p500` the dispatch win (−13 %) is outweighed by +8.3 % peak RSS and a wall-time mode that is 30–45 % slower in 7 of 13 fresh numpy processes (see `## Grouped route`), so a caller must measure its own arrangement rather than assume `k > 1` is a speed-up.
The grouped route has no shipped unit test (see `## Test Strategy`), and neither `grouped.py` nor its two entry points appear in `docs/source/` yet.
`digest.py` and `base.py` sit close to the 1000-line rule; the next concern in either belongs in `layout.py`, `dense.py` or `grouped.py`.

## Cross-node needs (measured here, owned elsewhere)
`algorithm/neat/_distance.py` (`DistanceRows`) is where the remaining duplicated `constant` ops live: `prepare`/`measure` already accept a `consts=` pool and `measure` emits none of its own, while `prepare` emits 50 `constant`s once per generation. Threading one `ConstantPool` per generation is worth ≲40 ops per generation from this node.
`algorithm/` should keep structurally allocated keys below `genome.key_span` (or carry a raised span in the shape signature): that is what makes the dense route exact for every payload, and it is the same fix that stops the execution schedule from silently dropping evolved genes.
The largest remaining win outside this node is the batch-1 centre at the live call site (−320 ops and ≈ −50 / −120 ms per generation at pop 500 / 1000); its `key_span` precondition is satisfied on live payloads (`oor = 0` over 8 cells × 40 generations), so the blockers are the species pass's centre tiling and the dense graph's `iree` compile failure, and `DistanceRows.row`/`matrix` must keep accepting both widths either way.
For the grouped route (a verified option no production path calls), `algorithm/`'s caller must hand over the `k` species centres **concatenated on axis 0** in slot order (`k * P` rows) and slice the `(k * P,)` result back into `k` blocks; inside a `scan` body it should keep one iteration per group of `k`, not unroll the groups, and it has to beat the allocator mode the wide buffers provoke before it ships.
`genome/gene/base.py:50` reads attribute columns with one kept-axis slice plus one reshape per column (132 + 132 traced ops per generation at pop 500/1000), the largest remaining block inside `measure`.
