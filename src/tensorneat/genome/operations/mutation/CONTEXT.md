# mutation — plan-based structural and value mutation, batch-first

## Intent
Turn one population-wide RNG key into an edited gene payload: four structural operations — add-node, delete-node, add-conn, delete-conn — each with its **own independent per-individual gate**, followed by attribute mutation of every existing gene.
The stage split exists because the structural stage is integer-key twiddling over the payload while the value stage is float arithmetic delegated to the gene objects; `BaseMutation.__call__` runs both from one `split_n(key, 2)`.
One call may apply up to **four** structural changes to one individual — at most one *per operation* — because the four gates are independent Bernoullis; that is the frozen legacy library's chaining and the reason the stages compose sequentially instead of through one merged plan.
Nothing here allocates keys: `new_node_keys (P,)` and `new_conn_keys (P, 3)` arrive caller-allocated.
That allocation is **not** guaranteed fresh: `algorithm/neat/neat.py::_new_gene_keys` bases it on the pre-crossover parent population while the payload mutated is the crossover child, so a child can already own the key it is handed (see Known Issues); `plan_add_node` therefore validates the allocation it receives.

## Cost model (drives every design choice here)
The backend is the evoxc reference numpy interpreter, so a traced op costs **dispatch (~13 µs) plus array traffic (~0.2 µs per 1 000 elements at pop 1000)**: both op count and element volume are budget.
Measured consequences that shape this node:
- Rank-0 constants are real ops: a per-use `i32(...)`/`enp.full((), ...)` is ~10 µs each, so every repeated constant is hoisted into `EditContext` and shared by the stage that reads it.
- A full-payload op on `(P, E, CK)` (300 k elements) costs ~60–80 µs at pop 1000, so a helper that flattens/reshapes the same array four times is four times the traffic.
- For the recurrent `(P, tries, E)` slabs the **contiguous innermost reduce is the cheaper one** on this box (2 M elements: `axes=2` 0.82 ms vs the transposed `axes=1` 1.65 ms; `equal` 0.68 vs 1.11 ms) — the opposite of the incoming-window rule in `../../CONTEXT.md`, so do not transpose these slabs.
- A broadcast key match against the node table is the one formulation to avoid: `(P, 2E+2, N)` is 10.1 M elements at pop 1000 (plus an int32 cast and `argmax`), which cost 21 of the 23 ms the cycle predicate used to take.
- Guarding one plan is cheap when the reduce is over the node or connection axis (tens of elements per row): the add-node validation is `(P, N)` + `(P, E)` equality/reduce pairs, 11 traced ops, unmeasurable in wall time.
- A `select` pays for the *whole* array, an indexed write pays for the cells it writes: two row writes on `conn_keys (P,E,2)` + `conn_attrs (P,E,1)` cost 8 ops / 1.00 ms as `select`s and 20 ops / 0.42 ms as one flat `scatter` (probe at pop 500). So "one op per write slot" is not automatically the cheap shape — measure before assuming op count decides, and prefer `scatter` when a slot writes at most a couple of rows out of a large array (the op price is ~13 µs, the traffic price of a `(500,100,2)` pass is ~0.4 ms).
- **Op count does not predict wall clock across populations**: the four-stage kernel executes **594** traced ops today (578 without the heritability exemption, 589 with it applied to all four stages; the frozen `de943ca` one-plan-per-call baseline is 432), is 1.16× that baseline's wall time at pop 500 (dispatch-dominated) and 0.82× at pop 1000 (traffic-dominated, six interleaved process pairs each). Budget both, and never conclude from an op delta alone.
- Ablations that size the blocks (pop 500, same-process A/B against an identity stub, pre-change kernel): `closes_cycle` 3.91 ms / 127 ops (inside it `_row_of` 3.03 ms / 79 ops), the two node-array writes 0.59 ms / 6 ops, the connection scatter 0.44 ms / 20 ops.
- Rule of thumb: an executed op pays ~13 µs of dispatch plus its own kernel work whatever its operands (a rank-0 constant, a `reshape`, a `slice` and a `broadcast` are each a whole op), an op inside a region is re-paid on every trip (~35 µs of region overhead per trip on top), a full-size operand adds traffic on top of the dispatch, and population-scaled seeds stay one element plus `broadcast_to` so the graph constant pool stays flat. Cut ops where the operand is small, cut traffic where the operand is `(P, E, ·)`, and trade a full-size `select` for a `scatter` even at +20 ops.
- The rank-0 RNG draws are the one block that is neither dispatch nor traffic: one `uniform`/`normal` on a rank-0 key costs **0.05–0.42 ms each and is independent of the output shape**, the kernel issues **13** of them, and `masked_random_row` accounts for three — draw order bit-exactness forbids removing or reordering them.

## Four-stage sequential composition
`mutate_structure` runs the four stages **in sequence**, in the fixed order add-node → delete-node → add-conn → delete-conn, one iteration of a Python `for index in range(_OPERATION_COUNT)` loop per stage.
Each stage: rebuilds `EditContext` against the payload the previous stage produced (`_edit_context`), wraps it with the call's shared uniform bounds (`_stage_context`), plans exactly **one** operation (`_plan_operation(index, ...)`), turns that plan into one single-operation `Edit` (`_stage_edit(index, ...)`), and writes it with `plan.apply(..., write_nodes=..., clear_conn=...)`.
The static per-stage write flags are `_STAGE_WRITES = ((True, True), (True, True), (False, False), (False, True))`: add-node writes a node row and needs the clearing pass (its slot 0 is the consumed edge), delete-node writes a node row and clears through slot 0 plus its detach mask, add-conn touches no node row and clears nothing (its slot 0 is the "no write" row), delete-conn clears exactly one connection row and no node row.
Conflict rules are deliberate and match the frozen legacy chaining: delete-node may delete the node add-node just created, delete-conn may consume an edge add-node or add-conn just created, and add-conn's duplicate / `max_in_degree` / cycle tests see the post-add-node and post-delete-node graph.
A stage that fires but whose candidate is refused (no candidate, duplicate edge, self-connection, cycle, capacity, `max_in_degree`, a colliding caller allocation) is a bit-exact no-op for that individual, and nothing is ever partially applied.
`plan.apply` is one writer for all four stages: the node write is one row-index comparison against the slot's row broadcast over the attribute axis (a row equal to the array's own length matches nothing, which is the "no write" case — no dump row, no flat index block), the connection clearing pass is one `select` per connection array merging slot 0 with the delete-node `drop` mask, and slots 1..n go through one flat `scatter` over `slots × W` trailing dump cells (`_scatter_slots`) because a `select` per slot would pay whole-array traffic.
A stage whose `Edit` has zero scatter slots (delete-node, delete-conn) skips the scatter entirely, and a stage that statically cannot write a node row (`write_nodes=False`) or clear a connection row (`clear_conn=False`) never traces those passes.
The two node arrays share their row layout, so `apply` builds the row comparison once and broadcasts it; the two connection arrays share theirs, so the stacked `(P, slots, 1)` row/validity block feeds both the key and the attribute scatter.

## API Surface
`BaseMutation.__call__(state, genome, key, node_keys, node_attrs, conn_keys, conn_attrs, new_node_keys, new_conn_keys) -> GenomeTensors` — shape-validates the key tensors (`ConfigError`), then `mutate_structure` → `mutate_values`.
`BaseMutation.mutate_structure(...)` is four per-stage plan→apply steps; it splits its key into `_OPERATION_COUNT + 1` keys (four operation keys in stage order, the gate key last), resolves the four gates once, and skips a stage wholesale when its probability is `0`.
`BaseMutation.mutate_values(...)` equals calling `genome.node_gene.mutate` / `genome.conn_gene.mutate` once each on the full attribute tables and re-masking the rows that were NaN before.
`BaseMutation.structural_probabilities -> (node_add, node_delete, conn_add, conn_delete)` is the gate order a subclass must supply, and the extension points are the four plans with unchanged signatures: `plan_add_node(state, genome, key, context, node_keys, conn_keys, conn_attrs, new_node_keys, gate)`, `plan_delete_node(state, genome, key, context, node_keys, conn_keys, gate)`, `plan_add_conn(state, genome, key, context, node_keys, conn_keys, new_conn_keys, gate)`, `plan_delete_conn(state, genome, key, context, conn_keys, gate)`.
`_plan_operation(index, ...)` is a static Python `if` chain over the four stage numbers, so a stage traces only its own plan; `_stage_edit(index, ...)` is the matching static chain that builds that stage's single-operation `Edit`.
`plan.apply(edit, context, node_keys, node_attrs, conn_keys, conn_attrs, write_nodes=True, clear_conn=True)` — the two keyword flags are static specializations of the same machinery, and a `slots == 0` edit is supported (no scatter).
`_StageContext` wraps one stage's `EditContext` with the call's shared rank-0 `(low, high)` uniform bounds and delegates every other attribute read to the wrapped context, so the plans keep reading `context.<field>` unchanged.
`DefaultMutation(conn_add=0.2, conn_delete=0.2, node_add=0.1, node_delete=0.1)` — each probability in `[0, 1]` else `ConfigError`; `RecurrentMutation(*, p_recur=0.1, max_conn_tries=20, **kwargs)` overrides `plan_add_conn` only, so it inherits `plan_add_node` and therefore the split validation.
Each plan reports its own `ok` flag **and** its candidate rows/values; it never writes the payload, so a refused operation is a batch-wide no-op by construction.
`arrays.py` is the read-only flat-index toolkit: `first_row`/`random_row`/`masked_random_row` return a `(row, hit)` pair (no `I_INF` sentinel and no sentinel `select`), `take_rows`/`take_block_at` gather row blocks from a static base index, `uniform_bounds` builds the shared rank-0 `(0.0, 1.0)` float32 pair, and `column_base`/`row_offsets`/`graph_constant`/`i32`/`flatten` build the static blocks; writing lives in `plan.apply`, so this module exports no writer. `recurrent.py` imports `first_row`, `i32`, `row_offsets`, `take_rows` from it — keep those names and signatures.
`degree.py` is the **diagnostic audit**, exported from the package as `in_degree(node_keys, conn_keys) -> (P, N) int32`, `max_in_degree(...) -> (P,) int32` and `violation(node_keys, conn_keys, limit) -> (P,) int32` (node rows strictly over `limit`).
It is trace-time only (call it from a graph, never as eager NumPy), it reads presence the way the write path does (`src key != I_INF`), it reports duplicate node keys as a union (both rows count every edge into that key — the same fold the schedule performs), and it is **never called by `execute_mutation`**: its `(P, N, E)` intermediate is 15 traced ops / 0.3–2.1 ms at pop 100–1000, i.e. diagnostic budget, not generation budget.
It is the standalone public degree kernels with **no internal caller**: the operators enforce `max_in_degree` inline (`EditContext.in_degree_limit` compared against each destination's present row count), so nothing inside `mutation/` imports this module — its only references are the `mutation/__init__.py` re-export (public API) and the autodoc stubs in `docs/`.

## Gate semantics (the load-bearing rule)
One `evoxc.random.uniform(gate_key, (4, P), low, high, dtype=float32)` draw per `mutate_structure` call, compared against a `(4, 1)` `float32` constant column of the four probabilities: `gate[i][p] = drawn[i, p] < p[i]`, so **each row is its own Bernoulli decision** and an individual may fire any subset of the four operations (up to all four).
The rows are the operations in stage order `(node_add, node_delete, conn_add, conn_delete)` and each gate costs one axis-dropping `getitem` of the draw, so the four gates are four ops and no reshape.
Draw order is the reproducibility contract and is unchanged: `__call__` splits the call key into `(structure_key, values_key)`, `mutate_structure` splits `structure_key` into five (`4` operation keys then the gate key), and stage `i` draws from `keys[i]` while the gate uses `keys[4]`.
`uniform_bounds()` is hoisted **once** per call and shared by every stage's draws; a Python float bound would embed one `float64` `constant` per draw (and `0.0`/`1.0` are exact in `float32`, so the draws are bit-identical).
At most one change **per operation per individual**, so up to four per individual per generation; no mutual exclusion, and an individual whose gate is off writes the "no write" row and comes out bit-for-bit identical (`-0.0`, NaN included).
The stage order is structure → values → restore, the last step exempting exactly the rows the **add-node** stage wrote, so attribute mutation never re-draws the three rows a split creates (identity edge, copy edge, new node) while a newly added connection still takes its weight from this call's value stage (the pre-change and legacy behaviour).
A probability of `0` is a true identity — the stage is elided at trace time, keeping even its cycle predicate out of the graph; a probability of `1` always attempts (and can still be refused); `network_type` outside `{"feedforward", "recurrent"}` raises `ConfigError`.
Analytic for the defaults `0.1/0.1/0.2/0.2`: `P(no gate) = 0.5184`, `P(exactly one) = 0.3744`, `P(any) = 0.4816`, `P(two or more) = 0.1072` — the measured attempt rates and what those attempts actually achieve are in Known Issues.

## Structural rules
- Add-node preserves the split topology: the consumed connection becomes `old_src -> new -> old_dst`, the new node takes `node_gene.new_identity_attrs`, the identity edge `conn_gene.new_identity_attrs` (weight `1`), the copy edge the consumed connection's recorded attributes, and both new edges take the *first two rows that are free before the delete*. It is refused when there is no candidate connection, no free node row, or fewer than two free connection rows (`copy_row` has no hit) — a half-splittable genome is left untouched.
- Add-node **validates the caller's allocation**, because a split is the only write that can grow a destination's in-degree: it refuses the split when `new_node_keys` already equals a present node key (a duplicate key would fold two node rows onto one schedule slot) and when the consumed edge's destination is already at `genome.max_in_degree` incoming rows.
  The destination's post-write in-degree equals its pre-write count (the consumed row `in_key -> out_key` is replaced by the copy edge `new -> out_key`), so that second test is a no-op on every legal payload and only refuses to add an edge to a destination that is already over `K`; the new node itself always ends with in-degree `1`.
  Both tests fold into the plan's `ok` (`(P, N)` and `(P, E)` equality + reduce, 11 traced ops total, no new rank-0 constant), so a refused split leaves the payload bit-identical apart from the value stage.
- Add-conn draws a source (inputs and outputs allowed) and a destination (inputs refused) from one `(P, 2, N)` mask block with `_fetch_two`'s single `argmax`, plus an "every slice has a candidate" test (`reduce_max` over the node axis, then `reduce_min` over the two slices); a `reduce_min` over both axes would ask whether *every node row* is eligible and would refuse add-conn population-wide.
- Add-conn refuses an absent endpoint, a duplicate `(in_key, out_key)` pair, a destination already at `genome.max_in_degree` incoming edges, and — for `network_type == "feedforward"` — a cycle (`cycle.closes_cycle`), all against the payload the add-node and delete-node stages left behind.
- Delete-node never names an input row or an output row (`context.deletable_node`) and detaches every touching connection through the `Edit.drop` mask, which `apply` merges into the same clearing pass as slot 0; delete-conn clears exactly one row.
- New rows always go to the first free row of the matching array; the `historical_marker` column is written only when `genome.conn_gene.uses_historical_marker`, and `new_conn_keys` columns stay `0` = add-node identity edge, `1` = add-node copy edge, `2` = add-conn edge.
- `RecurrentMutation.plan_add_conn`: one `(P, max_conn_tries, 2)` `randint` tableau plus one `(P, max_conn_tries)` `uniform` `p_recur` decision; acceptance = present endpoints & destination is not an input & not a duplicate & in-degree ok; the first accepted attempt wins by a reduce over the attempt axis (never `cond`); **one** `closes_cycle` call on the chosen edge then enforces the `p_recur` requirement. `p_recur == 0` draws no `p_recur` uniform, degenerates to `DefaultMutation`, and elides the cycle predicate (next section). `max_conn_tries` bounds the tableau's element volume, not its op count.
- Padding never enters the recurrent confirmation slabs: a padded connection row is `I_INF` in *every* key column while an accepted candidate has two finite keys, so key equality alone excludes padded rows and the `present_conn` factor is redundant there (the `exists` term still gates a candidate whose endpoint *is* `I_INF`).

## Cycle predicate (`cycle.py`)
`closes_cycle(node_keys, conn_keys, src_keys, dst_keys)` answers "would `src -> dst` close a cycle?" as `src` reachable from `dst`, by one `while_loop` monotone frontier growth on a **flat** frontier with one trailing dump column (three `O(P·E)` ops per hop — `gather`, `select`, `scatter` — plus the one-op growth test, once per real hop).
Key resolution is a **merge join**: every query and every node folds its key and payload into one injective `int64` composite, the `(P, N + Q)` merge (`Q = 2E + 2`) is sorted once, an inclusive suffix count of the node tags gives the rank of the first node at or after each position, and one flat `gather` reads the row; the low field keeps queries in `[0, Q)` and nodes in `[Q, Q + N)` in ascending row order, so that first node is the *smallest* row carrying the key — the same row the previous `argmax(argmax(match))` produced.
That first node is read back and compared with the query: the hit test is one `equal` of the two composites shifted right by the period width, because every low field is below one period, so the shift discards exactly the low field and two entries agree above it exactly when they carry the same key (no `int64` difference, `abs` and radius constant any more).
The answer store is a `total`-wide row per individual rather than `query_count + 1`: the low field is already a per-individual cell number in `[0, total)`, so the scatter lands the answers in the query half with no `minimum` clamp.
That suffix count is a Hillis–Steele **log2-doubling** — `ceil(log2(N + Q))` static shifts of one `pad` + `slice` + `add` each, in `int8` flags while `max_nodes <= 127` — because `cumsum` is a StableHLO v1 export deferral; every op of the predicate is v1-exportable and `evoxc.backends.stablehlo.export` succeeds on the graph.
No dense key→row table is possible: the algorithm allocates node keys as `max_node_key + 1 + arange(P)`, so a real pop-100 run reaches keys 225–249 with `key_span=150` and keeps growing; keys must be treated as arbitrary `int32`.
The frontier is monotone non-decreasing (a `scatter` only sets bits) and the node count bounds it, so the loop carries only `(frontier, growing)` and `growing` alone terminates it: no iteration counter, no `step < max_nodes` cap, no int32 seed.
Both boundary terms are folded outside the region: the seed is a one-hot `equal` against a static `(width,)` index, `logical_and`-ed with `dst_hit`, over the flat `(P, width)` frontier (`dst_row` is in `[0, node_count)`, so the dump column starts `False`), and `select(edge_valid, src_flat, dump_flat)` folds a missing endpoint into the gather index, so the dump column always reads `False` and the per-hop `logical_and` disappears.
**IREE release gate (not an optimisation knob): the seed must be that one-hot comparison, never a boolean `scatter`.** A `scatter` whose result is the `while_loop` init makes `iree-compile` (IREE 3.11, llvm-cpu) SIGSEGV on the generation graph (`BackendError: iree-compile failed`, IREE `Error code: -11`, `libIREECompiler.so` stack) — while the same scatter inside the loop body, and the same kernel compiled standalone, both compile, so per-kernel compilation proves nothing.
Isolation: reverting the join's shifted-key hit test, its rank clamp, its `total`-wide store, the `select` validity fold or the loop's carried-bool condition each still crashed; reverting only the seed fixed it, and a materialised `enp.zeros` operand or a no-op `logical_or` after the scatter crashed as well (so it is the scatter-as-init, not the splat operand, that trips the compiler).
The gate is `pytest test/backends` with the `evoxc[iree]` extra installed (`iree-base-compiler` 3.11.0), run from the repo root: **3 passed**.
Cost of the choice: the one-hot seed is bit-identical on the frontier (verified on random cases with `I_INF` endpoints, self-loops, duplicate keys and absent nodes, plus an evolved pop-500 payload), **2 traced ops cheaper** than the boolean `scatter` seed it replaced (124 vs 126 on the standalone `closes_cycle` graph at pop 500 / `max_nodes=50` / `max_conns=100`) and 3.66 vs 3.82 ms per isolated `closes_cycle` call, so pop-500 `Pipeline.step` is unchanged (152.80 vs 152.92 ms/gen median over 8 interleaved process pairs; the pre-wave form is 151.14 and 143 ops).
The seed no longer uses `fill`: a splat constant feeding the scatter crashes just as well (`enp.zeros` was measured), so the shape of the cleared operand is not the trigger.
Result: **124 traced ops** on the standalone `closes_cycle` graph at pop 500 / `max_nodes=50` / `max_conns=100`, counted recursively over `module.functions[*].entry_block` and every `op.regions` body with terminators excluded (127 with the three of them included), at 3.6 ms pop 500 and ~7.2 ms pop 1000: the largest single file in the kernel, a merge join over `P·(N + Q)` elements instead of a 10.1 M-element broadcast match.
The per-file ledger below reports 121 for the same code because it attributes by `op.location`, and books the kernel's two `window.fill` broadcasts to `window.py`.
Its measured internals at pop 500: `_row_of` 3.03 ms (the two sorts 0.32 + 0.07, the log2-doubling scan 8 `pad` + 8 `add` ≈ 0.51, the transpose-back `scatter` 0.34, the `int64` gather 0.14) and the loop region ~0.1 ms, because `while_loop` costs ~35 µs per trip beyond its body and the gen-5 payload needs exactly **one** trip.
Measured and dropped here: a pre-padded scan (one `pad` + two `slice`s instead of 8 `pad`s) costs +2 ops / +0.04 ms, a `>=`-style hit test and a padded node array each add a full-size pass, and merging the two sorts needs the compaction scan it was meant to save.
The `rank` lookup clamps to `node_count - 1` instead of reading a trailing sentinel row: `rank == node_count` implies the query's key exceeds every node key, so the read-back node carries a different key and the shifted-key hit test rejects it.
The call site is **statically gated** on `genome.network_type == "feedforward" or self.p_recur > 0.0`: those are the only two consumers (the acyclicity veto for a feedforward genome, and the `p_recur` requirement built only when `p_recur > 0`), so a recurrent genome traces neither the region nor its ops (`RecurrentGenome` pop 1000: `DefaultMutation` **301 ops / 14.9 ms**, `RecurrentMutation(p_recur=0.0)` **330 / 17.3**, `p_recur=0.1` **469 / 25.0**).
A feedforward genome's add-conn can close a cycle, so that branch keeps the predicate unconditionally, and it is traced once per call — inside the add-conn stage only, because that is the stage that can add an edge.

## Constraints
- Trace-time kernel only: no `jax`/`torch`/`numpy.random`, no `vmap`/`scan`/`cond`, no Python loop over individuals (the stage loop is a static Python loop over four configurations), no eager NumPy; `sort`/`argsort` are legal (the mutation never enters the `grad` graph), and `cumsum` is not used anywhere — it is a StableHLO v1 export deferral, so the one suffix count (`cycle.py`) is a static log2-doubling instead.
- Randomness is one rank-0 key per call, split with `evoxc.random.split_n`; draws are batched over the population, never per individual, and the draw order is part of the contract (see the bit-identity gate).
- Each of the four stages rebuilds its own `EditContext` from the payload it starts from; that rebuild (~20 traced ops a stage) is the price of the composition and must not be hoisted into one context shared across stages, because a previous stage can move or clear a row.
- A row fetch returns `(row, hit)` rather than an `I_INF` index (`arrays.first_row`/`random_row`), so a gate is a plain `logical_and` chain and the empty-row index is `0` — never a sentinel `select` plus a rank-0 constant.
- Padded rows keep their sentinels in both arrays: `I_INF` keys, NaN attributes; no operator may pair an `I_INF` key with finite attributes or a finite key with NaN attributes.
- Capacity invariants are hard: `max_nodes`, `max_conns`, `max_in_degree`. A refused operation is a no-op for that individual, never a partially applied write.
  `max_in_degree` is enforced at the write that could grow it: add-conn compares the destination's present row count against the limit before writing, add-node refuses a colliding allocation and a destination already over the limit, and the delete operations can only remove rows.
- Rank-0 constants and static index blocks are built **once** per stage (in `EditContext`, or as a folded `graph_constant`) and shared: a per-use `enp.full((), v, int32)` is one traced op each.
- Zero-width attribute tables (`attr_width == 0`) work: `_scatter_slots` early-returns on `width == 0` and the write path uses row-index selects, so nothing builds a `0`-stride arange.
- Errors: configuration problems raise `ConfigError` (`TensorNEATError`); `evoxc` shape/backend errors propagate unchanged.
- Files ≤ ~1000 lines: `base.py` (874) owns the key splits, the gate draw, the four-stage composition, `_plan_operation`/`_stage_edit` and the value stage; `default.py` (463) the four `DefaultMutation` plans, `_fetch_two` and the split validation; `plan.py` (469) the plan datatypes, `EditContext`, `Edit` and the single `apply` writer; `arrays.py` (292) the flat-index read primitives and `uniform_bounds`; `cycle.py` (336) the merge-join reachability predicate; `recurrent.py` (279) the recurrent add-conn; `degree.py` (119) the diagnostic in-degree audit.

## Measured cost (numpy reference interpreter)
Reference payload for every row: `DefaultGenome(num_inputs=2, num_outputs=1, max_nodes=50, max_conns=100, mutation=DefaultMutation(), crossover=DefaultCrossover(), distance=DefaultDistance(), output_transform=ACT.sigmoid)`, one warmup + 5 timed `evoxc.run`, one fresh process per cell, build excluded.
Traced ops are counted recursively over `module.functions[*].entry_block` and every `op.regions[*].blocks[*]` body with terminators excluded.

| kernel / cell | pop | traced ops (before → now) | median ms before → now | ratio (6 interleaved pairs) |
| --- | --- | --- | --- | --- |
| `execute_mutation` | 500 | 432 → 578 → **594** | 19.85 → 23.11 | **1.16×** (1.11–1.20) |
| `execute_mutation` | 1000 | 432 → 578 → **594** | 37.37 → 30.67 | **0.82×** (0.78–0.99) |

The reference baseline is `git archive de943ca` with its `src` first on `PYTHONPATH` (asserted via `tensorneat.__file__`).
Every pair is one baseline process followed by one this-tree process, alternating, six pairs per population; per-pair ratios are load-bearing, absolute milliseconds drift with the box load (this box is shared and was 2+ cores busy).
Op count and wall clock therefore disagree: `+146` traced ops cost ~3.2 ms at pop 500 (≈22 µs an op) and nothing at pop 1000, where the four-stage form's smaller per-stage writes win instead.

Per-stage traced ops at pop 500 (each row = that probability `1.0`, the other three `0.0`, cumulative with the base):

| configuration | traced ops | increment |
| --- | --- | --- |
| all four `0.0` (key split + gate draw + value stage) | 96 | — |
| add-node only | 233 | +137 |
| delete-node only | 163 | +67 |
| add-conn only (includes the 121-op cycle predicate) | 326 | +230 |
| delete-conn only | 144 | +48 |
| defaults `0.1/0.1/0.2/0.2` | **578** | = 96 + 137 + 67 + 230 + 48 exactly |

The increments are exactly additive, so the four stages cost their own ops and nothing is shared across them.
The baseline's scaffold was 127 ops dearer (a plan for all four operations regardless of configuration) with far smaller per-stage increments (36 / 13 / 155 / 5), i.e. this kernel trades a shared merged plan for four independent contexts and writes.

Per-file op ledger at pop 500 for the **578-op four-stage kernel without the exemption** (`execute_mutation`, recursive over `regions`; `op.location` is the *creation* site, so a shared helper's ops count under the file that emits them): `cycle.py` 121 + `base.py` 118 + `arrays.py` 117 + `plan.py` 83 + `blocks.py` 69 (gene-side, not this node) + `default.py` 63 + `window.py` 6 + 1 unattributed = 578, against 121 / 70 / 57 / 41 / 69 / 63 / 10 / 1 = 432 before.
The exemption machinery costs **16 ops on top** (11 for the post-loop all-stage form, 5 more for the stage-scoped masks inside the add-node stage), all of them `(P, N)`/`(P, E)` predicates in the stage that already has the index blocks, so `Pipeline.step` is unchanged within noise.
The +146 over the baseline therefore sits in `base.py` +48 (stage dispatch, `_stage_edit`), `arrays.py` +60 (four `EditContext` rebuilds instead of one) and `plan.py` +42 (four `apply` calls instead of one), partly offset by `window.py` −4.
By op name the same 578 ops are `constant` 123, `reshape` 85, `logical_and` 33, `select` 32, `add` 27, `cast` 25, `slice` 25, `random_key_mix` 24, `gather` 21, `equal` 21, `less` 18, `concatenate` 16, `reduce_max` 15, `multiply` 12, `pad` 12, `not_equal` 11, `logical_not` 11, `random_uniform` 10, `argmax` 10, `broadcast` 10 and a long tail — half the graph is rank-0 constants, views and one-element broadcasts, which is why the dispatch floor is what it is.
Op count is not the verdict when a `select` trades for a `scatter`: the scatter rewrite of `plan.apply` added 19 static ops and removed 0.75 ms, because a `select` over `(P, E, 2)` costs 13× a dispatch.
Whole-generation context: one pop-500 `Pipeline.step` builds a graph of **2 318** traced ops (2 172 before, same counter and same split), so the mutation's +146 is the whole delta and the kernel is ~25 % of the generation's static ops (578 of 2 318).
The end-to-end A/B at pop 500 (XOR, seed 42, `NEAT(pop_size=500, species_size=20, survival_threshold=0.01)`, `setup()` then 3 warmup + 10 timed `step` calls, median per process, six interleaved pairs) is **flat within noise**: median ratio **0.99** (173.34 ms here against 175.79 ms on the `de943ca` baseline), every pair inside 0.93–1.03.
The kernel is ~25 % of a generation's static ops and is 1.16× its baseline at pop 500, so the per-generation cost is not measurable; the fitness trajectory does change, because the RNG consumption per generation differs (`best_fitness` after 13 generations: −0.245 here, −0.201 on the baseline, seed 42 pop 500 XOR).
Element volume, recurrent add-conn at pop 1000: two `(P, max_conn_tries, E)` bool slabs (2 M elements each) and nothing else of that size — the int32 cast of the in-degree slab, the two `present_conn` factors and the second output-key equality are gone, and endpoint/attempt gathers run on the `(P·tries)` blocks.

  Reproduced end to end at `DefaultGenome(num_inputs=3, num_outputs=1, max_nodes=16, max_conns=100)` + `OriginNode`/`OriginConn` + `NEAT(pop_size=500, species_size=10, survival_threshold=0.01)` + `XOR3d`, seed 6: generation 53, slot 65, allocation 112 while the child already owns key 112 → a duplicate node row, an identity edge into a destination already at `max_in_degree=4` → `edge_overflow=1` → `Pipeline.step` raised.

  The local guard converts this into one skipped split per collision; the source fix is to base the allocation on the crossed payload (or a population-wide maximum).
- **Allocated keys outrun `key_span`** (outside this node): `key_span` defaults to `max(max_nodes, num_inputs + num_outputs) + max_conns` (116 here, 150 at `max_nodes=50`) while the allocator reaches 1 974–8 117 over 250 generations — at generation 53, 494 of 500 allocated keys are outside the span, and `common/tensorization.py::key_slot_table` treats an out-of-span key as a *miss* without setting `edge_overflow`, so those node rows and every edge touching them silently vanish from the evaluated phenotype.
  Genome/algorithm owners: either allocate below the span or carry a raised span in the shape signature (`tensorneat/genome/base.py` default, `algorithm/` allocation).
- Add-node does not preserve the network output — measured worst |Δoutput| 2.36e-01 on a fixed payload. It is a property of the gene-side identity row (`../../gene/node/default.py::new_identity_attrs` keeps `aggregation_default`/`activation_default`, which are not identity), not of this node; owner of `../gene/`: the inserted node needs the identity aggregation and an identity activation.
- The heritability exemption is **stage-scoped and add-node only** (`_EXEMPT_WRITES = (True, False, False, False)`): `_mutate_structure` returns a `_StructuralWrite` (the payload plus `node_rows`/`conn_rows` masks) and `__call__` restores `structured.*_attrs` over exactly those rows after the value stage.
  The mask is a key-table difference between the add-node stage's **input** and its own output, so it names the rows that stage wrote and no later stage's; a cleared connection row is additionally masked out (`key != I_INF` in the stage's output key table) because a later stage may reuse the freed row for a fresh add-conn edge, which must still be mutated in this call.
  Measured (one evolved pop-100 XOR3d gen-10 payload, one forced add-node, 1000 RNG keys, 100 000 splits): the new node row, the identity edge and the copy edge are **100 % / 100 % / 100 %** exact after the call (the pre-exemption tree: 62.7 % / 10.1 % / 9.9 %), the identity edge carries `weight = 1.0` in 100 % of splits.
  A newly added connection ends the call with a non-zero weight in **89.05 %** of cases on both this tree and the pre-exemption tree (86 36 new edges over 200 keys each, identical edge count and identical fraction), against **0 %** when the exemption covered the add-conn stage — so the add-conn stage must not be exempt: `gene/conn/default.py::new_zero_attrs` starts an edge at `weight = 0.0`, and under the elite pin an inert edge can persist in an elite lineage indefinitely.
  Delete-node and delete-conn need no exemption: a cleared row turns `I_INF`/NaN and the value stage's own padding mask already keeps it.
- A structural *deletion* is exempt from that restore by construction: a cleared row turns `I_INF` and NaN, so it matches no written-key difference and the value stage's own padding mask keeps it.
- The cycle predicate is traced and executed on every generation where `conn_add > 0`, even when no individual's add-conn gate is set: the gate is a traced value and cannot drive Python control flow. Only the statically dead case (`conn_add == 0`, or `recurrent` + `p_recur == 0`) is elided.
- The frontier seed is an IREE safety constraint, not a style choice: a boolean `scatter` as the `while_loop` init SIGSEGVs `iree-compile` 3.11 on the generation graph (construct, evidence and cost in the cycle-predicate section). `closes_cycle` compiles standalone either way, so only `pytest test/backends` catches a regression — do not "optimise" the seed back to a scatter.
- `RecurrentMutation`'s `closes_cycle` runs on the *chosen* attempt only rather than gating the choice per attempt: a must-cycle attempt that does not close a cycle is rejected instead of being skipped in favour of a later attempt, which biases sampling slightly (fewer accepted recurrent edges) to keep `max_conn_tries` out of the op budget.
- `RecurrentMutation`'s confirmation slabs are `O(P · max_conn_tries · max_conns)` bools; `max_conn_tries` (default 20) is the volume lever at pop ≥ 500 (tries 20 → 1 is ~1 ms at pop 1000 now), not an op lever.
- `p_recur == 0` still splits the key into `attempt_key`/`recur_key` although no `p_recur` draw happens; removing the split would change `attempt_key` and therefore the draws, so it is not behaviour-neutral.
- The remaining reducible margin is now the composition itself: `EditContext` is rebuilt four times (+60 ops in `arrays.py`), `_stage_edit`/`apply` run four times (+42 in `plan.py`), and the cycle join stays the largest single block (121 ops). Collapsing stages is only legitimate when the collapsed stages write provably disjoint rows — the delete-conn/add-node and delete-node/add-node interactions above are exactly the cases where they do not.
- The node-write `select`s are at their floor: measured against a `scatter` alternative they are break-even (~20 ops ≈ 0.26 ms vs 2 selects), and sharing the row mask between the two node arrays is the only form that avoids a second comparison.
- **Two neighbouring records are stale and are outside this node's write scope** (reported upward instead of edited): `../../CONTEXT.md`'s run-level bit-exactness digests cannot reproduce any more by design (the mutation trajectory changed, and so does every generation after the first), and `../CONTEXT.md`'s "Deviations" bullet that describes the four structural operations as mutually exclusive through one shared draw no longer describes this code.

## Graph constants
`ghost`/`never` sentinels, the identity/zero rows, the "no write" row and the cycle predicate's scatter targets are all `...window.fill(...)` (one element plus `broadcast_to`), not materialised `(pop_size, …)` fills.
`execute_mutation` bakes **15 097 / 45 497 / 83 497 B** of graph constants at P=100/500/1000 (123 `constant` ops, the largest a `(P, 1, 2)` int32 `column_base` block repeated per `EditContext`), against 6 735 / 17 935 / 31 935 B for the `de943ca` baseline; every seed the stages add goes through the same `fill`/rank-0-constant route, and the write path's dump cells are `graph_constant` data of `slots × W` entries per array per stage, not population-scaled.
The four `EditContext` rebuilds are what re-materialise the population-scaled index blocks, so a future single shared context (legal only where a stage cannot move a row) is the lever on this budget as well as on the op count.
`fill` is a real traced broadcast: a shape feeding `reshape` or `scatter` must be passed exactly, while symmetric-broadcast consumers (`select`, `clip`, arithmetic) may still grow it.
