# ./unit/problem — the problem layer's algebra, protocol and reporting suites

## Intent
Prove that each problem under `../../../src/tensorneat/problem/` computes the fitness its docstring promises, on the numpy backend, with no optional dependency and no genome.
A problem is host-side configuration plus plain kernel helpers, so every case drives the real `evaluate`/`show` (or a documented in-trace helper) with a *genome-free* `act_fn` — a plain Python closure over `evoxc.numpy` ops, inlined into the graph by the shared runner — and asserts on the returned `(P,)` fitness, on the helper's values, or on the printed report.
Assertions are closed forms, the independent numpy references of `../support/oracle.py`, hand-derived arithmetic, or identities; never the implementation's intermediate state.
Every assertion is able to fail: the "this reduction differs from the other three" and "the budget boundary moves by one element" cases assert the *difference*, not a truth that holds for any input.

## Oracles used (never the kernel under test)
`support.oracle.func_fit_loss` (the reduction over the sample *and* output axes) and `support.oracle.cartpole_rollout` + `cartpole_params` (the only CartPole oracle, since the legacy RL problems are gone).
`test_pendulum.py` and `test_mountaincar.py` carry their own host-numpy rollouts (`_pendulum_rollout`, `_mountaincar_rollout`, each with a `_physics`/coefficient helper) instead of extending `../support/oracle.py`, which sits at its own size budget as a sibling node.
Each rollout is one function parameterized by `dtype`, so the float32 and float64 runs use the *same* recurrence, constants and ordering and the `rtol=1e-5` comparison only checks float32 rounding — that pair is therefore **not** an independent oracle for the *equations*.
That independence comes from `_one_step_by_hand` in each of the two modules: the published transition written out with explicit numeric coefficients (`3*g/(2*l)`, `3/(m*l**2)`, `0.0025*power`, …), float64 arithmetic, the floor-mod wrap and the clips spelled inline, and every per-case expectation recorded as a numeric literal with full precision.
`test_pendulum.py` pins four such transitions at `theta = 0.5, -2, 4, -3.5` with `theta_dot = 0, 3, -1, 7.9` and logits `1, -1, 0.5, 30` (the last one also saturating the velocity clip at `8.0`), against `_advance` traced through `run_in_graph`; `test_mountaincar.py` pins four at `position = 0.1, -0.5, 0.44, 0.4` with `velocity = 0.01, -0.02, 0.05, 0.001` and actions `0.5, -1, 1, 0.2` (the third reaching the goal from `0.44`).
A coefficient typo in the source moves the kernel away from a number computed without it, and a typo in the transcription moves the transcription away from both the literals and the kernel.
Closed forms where one is cheap: `mse = 0.25`, `rmse = mae = 0.5` for a constant `0.5` predictor on XOR; `91/8`, `22/8` and `(467/60)/8` for a `(0.5, -1)` predictor on the two-output grid; `-2.5` for the row-index predictor's first individual; `mape = 1` for a zero predictor on a strictly positive dataset; the `k = 9` survival count of a constant policy from rest; `finalize_fitness`'s `[nan, -1.5, 0, 3, +inf] -> [-inf, -1.5, 0, 3, +inf]`; MountainCar's exactly `0.0` for the idle policy and `100 - 0.1*tanh(logit)**2` for one body step that reaches the goal; Pendulum's `6.245` and `1000` one-step costs and its `16.2736` per-step ceiling.
Identities where no absolute value exists: `inputs.shape == (S,) + input_shape`, and the `B = P * repeat_times` identity in `test_repeat_times_averages_individual_major_rows`.

## How the suite runs the code
`evaluate` is a plain helper inlined into the caller's graph, so `run_evaluate` closes over the problem, the `State` and the `act_fn` and passes only tensors: `run_defn(lambda *arrays: problem.evaluate(state, evoxc.random.key(key_seed), act_fn, FakeSchedule(*arrays)), *fields)`.
The schedule is passed **field by field** and rebuilt inside the trace — the shared runner treats only top-level arrays as data, so a namedtuple argument would be baked as a static whose fields are numpy arrays.
The key is rebuilt from an integer `key_seed` inside the trace: a rank-0 `evoxc` key has no `__array__`, and a stateless key is a compile-time constant anyway.
`run_in_graph` is the escape hatch for the in-trace helpers that are not the whole protocol (`finalize_fitness`, `static_batch_size`, CartPole's `_force_from_logits`/`_terminated` with `_constants()`, Pendulum's `_advance`/`_angle_normalize`/`_reset`, MountainCar's `_advance`/`_terminated`/`_reset` and its `_loop_body` carry).
`static_batch_size` is also correct on a host numpy schedule, which is how its rejection paths are reached without a trace; the error also escapes `evoxc.build` unchanged when raised inside one, and both routes are asserted.
`show` needs no graph: it is a host-side report, so its cases call it directly with the `state`, an `evoxc_key` and a `fake_schedule`, and read `capsys` — a NaN-poisoned policy prints `nan`/`n/a` columns instead of raising, and a bogus registered backend raises from the build before a single line is printed (asserted as empty stdout).
`act_fn` closures are pure `enp` — a traced tensor has no `__getitem__` and there is no eager mode — and the fake schedule is the only thing a problem may read from `transformed`.

## The fake schedule
A problem may read exactly one thing from `transformed`: `static_batch_size(transformed)`, the static leading dimension of its leaves.
`conftest.FakeSchedule` is therefore a two-leaf namedtuple (`weights (P, k) float32`, `scores (P,) int32`) with deliberately un-schedule-like field names, so a problem test cannot accidentally depend on the genome's schema and a problem failure stays distinguishable from a genome failure.
Degenerate schedules (leaves that disagree about `P`, rank-0 leaves, an empty schedule, a non-tensor leaf) are built inline where the shape under test is visible in the test body.

## Making CartPole comparable to a host oracle
`reset_scale = 0.0` is a legal configuration (only a negative scale is rejected) and makes every initial state exactly `(0, 0, 0, 0)`, so the numpy oracle can be fed the same `obs0` the graph draws; with the default `reset_scale` the draw comes from `evoxc.random` and is not reproducible host-side, so those tests assert relations between runs (determinism, divergence, averaging strictness) instead of absolute values.
A constant policy survives exactly 9 steps from rest in *both* directions (the dynamics are symmetric under `(x, theta, force) -> (-x, -theta, -force)`), so the `repeat_times` layout test cannot distinguish rows by direction: `_split_row_policy` uses rows that push constantly (9) and rows that balance the pole for the full horizon (20 at `max_step = 20`).
`B = P * repeat_times` depends only on the product, so `P = 4, R = 1` and `P = 2, R = 2` draw the same four initial states from the same key — that identity pins the individual-major `(P, R)` layout without any analytic return value.

## Recovering `obs0` for Pendulum and MountainCar
Neither environment exposes a user reset knob — Pendulum hard-codes `theta ~ pi*U(-1, 1)` and `theta_dot ~ max_speed*U(-1, 1)`, and MountainCar derives its `U(-0.6, -0.4)` draw from module constants — so no configuration pins the initial state and the draw still has to come from `evoxc.random`.
`_reset_observations(run_in_graph, evoxc, env, batch, key_seed)` retraces the environment's own `_reset` in a one-op graph with the key rebuilt from the integer `key_seed` inside the trace, and takes the host result — the same `run_evaluate` rebuilds the identical key, so the oracle is fed exactly the states the graph starts from.
That is why the agreement is bit-exact in float32: the oracle runs the documented dynamics on the same numbers, in the same order.
A state-dependent policy needs the oracle to see the state it acted on, so the rollouts return `(total, states)` and the policy is evaluated per step from `states[:, t]`, mirroring what `act_fn` sees inside the loop.
Both environment oracles are written for batch 1 (`(1, 2)` observations, `(1, 1)` logits); `P > 1` cases assert relations (layout, determinism, divergence, bounds) rather than absolute values.

## Behaviour this suite pins (gotchas worth knowing before editing it)
`mape` divides by the target, and both corners are asserted: a non-zero prediction on a zero target is `+inf` loss, while a *zero* prediction on a zero target is `0/0 = NaN`; each reaches `-inf` fitness through different arithmetic, so a "fix" that replaced `0/0` with `0` would turn the second test red.
CartPole demotes NaN logits to `-inf` fitness through the explicit `evoxc.isnan` guard (`_nan_rows` → `_any_repeat` → select NaN before `finalize_fitness`), while the decision site still reads NaN as "push left"; one poisoned repeat demotes the whole individual.
CartPole's fitness is a mean of 0/1 rewards, so it is always finite outside the NaN case and lies in `[0, max_step]`; `max_step` is a hard ceiling and `fitness_target > max_step` is rejected at construction.
Pendulum's per-step cost is `angle_normalize(theta)**2 + 0.1*theta_dot**2 + 0.001*u**2` on the **pre-transition** state with `u = max_torque*tanh(logit)`, so the return of *any* policy lies in `[-max_step*(pi**2 + 0.1*max_speed**2 + 0.001*max_torque**2), 0]` — `-16.2736*max_step` at the defaults — and the environment never terminates.
Pendulum's wrap is `x - 2*pi*floor((x+pi)/(2*pi))` (a floor-mod into `[-pi, pi)`, so `+pi` folds onto `-pi`), not `evoxc.remainder`, which is fmod on stablehlo/iree and keeps the sign of the dividend; a policy that spins the pole past twelve turns still scores the *wrapped* angle, which the test checks by asserting the unwrapped cost is never smaller in magnitude and is >100x larger on the rows that really left the window (~226x on the row that spins ~75 rad).
Pendulum clips the velocity **before** the angle integrates, so `theta' = theta + clip(theta_dot + (...)*dt, +/-max_speed)*dt`; from `(0, 7.9)` at `u = 2` the unclipped velocity is `8.2` but the carried one is exactly `8.0`, so the angle advances by `0.4` and not `0.41` — and the same step's cost is still `6.245` off the *pre-clip* `7.9`. The hand-derived `(-3.5, 7.9, 30)` row pins the same clip at a non-zero angle with a saturated torque.
MountainCar pays the goal bonus exactly once: `done` is written into the loop's `alive` flag, the accumulator is masked by the **pre-step** alive value, and the state is frozen afterwards, so a policy that reaches the goal at step `k` returns the same total at every horizon `>= k` (the frozen state still satisfies `done`, so an unmasked bonus would keep growing).
MountainCar's reward is `(100 if done else 0) - 0.1*tanh(logit)**2`, so the idle policy (`logit = 0`) returns exactly `0.0` at every horizon — the deceptive optimum, and the reason the shipped example does not solve the task; the bonus is paid once while the penalty is charged on every scoring step, which is why the constructor's `ATTAINABLE_CEILING` is `93.0` and not the nominal `100`, and why `fitness_target` is validated against `93.0` (accepted) while `93.5` raises.
MountainCar's penalty is charged on the *squashed* action `a = tanh(logit)`, and `clip(a, -1, 1)` is unobservable through a policy because `|tanh| <= 1` (it saturates to exactly `1.0` in float32 at `logit = 30`); the tests pin `a`, not the redundant clip.
Only the left wall zeroes the velocity (`position == min_position and velocity < 0`); the `0.6` clamp keeps the velocity, and `done` is the conjunction `position' >= goal_position and velocity' >= goal_velocity`, so reaching `0.45` while rolling backwards is not done — `ATTAINABLE_CEILING` assumes the goal is reached early enough that the remaining penalty cannot cost more than 7.
MountainCar's `-0.1*max_step` floor is only approached, not attained, in float32 (`-99.89905` at `max_step = 999` against a `-99.9` bound), so the bound is asserted as an inequality and the exact value is left to the oracle.
Pendulum and MountainCar have neither a reset knob nor a NaN census: NaN logits reach `-inf` by propagating through the action penalty (`0.001*u**2` / `0.1*a**2`), and on MountainCar a NaN that only appears after the goal is masked away with the rest of the frozen episode.
All three RL `show`s are finite-safe: a NaN-poisoned policy prints its report (`nan` in the return/mean columns, `n/a` or "no return" wording per environment) rather than raising from an `int()`/`round()` on a non-finite value.
`FuncFit.MAX_DATASET_NBYTES` is compared with a strict `>` against `(S, I) + (S, O)` float32 bytes: 48 bytes passes with the budget at exactly 48 and fails at 47, and the same check runs at construction, in `setup` and again at bake time (a subclass that lowers the budget after construction makes `run_evaluate` raise).
`CustomFuncFit(method="grid")` builds the per-axis `np.arange(low, high, step)` and takes their row-major cartesian product with the first axis slowest, so `S` is the product of the grid lengths and is unrelated to `num_samples`.
`CustomFuncFit` validates `func(low_bounds)` and the box/method/step configuration before it reaches `FuncFit.__init__`, so a bad box wins over a bad `error_method`; a low bound `>=` the matching high bound is rejected ("strictly below"), and a non-finite bound is rejected ("bounds must be finite").
`cartesian_product` is not re-exported by `tensorneat.problem` or `tensorneat.problem.func_fit`; it is reached as `problem.func_fit.custom.cartesian_product`, and it raises `common.TensorNEATError` (not `AssertionError`) for mismatched ranks and rank > 2.
`algorithm.NEAT` rejects `pop_size < species_size * min_species_size` (default `10 * 1`), so the arity cross-check builds it at `pop_size = 10`; a smaller population raises `TensorNEATError` before the arity can be read.
`setup(state)` returns the same `State` object and registers no keys; `setup(None)` starts from the same empty key set, and `setup` on a `State` carrying other keys leaves them untouched.
`problem.base.build_options(state)` returns `{"backend": ...}` from the *registered* selection (else `"numpy"`), adds `device` only when registered and not `None`, and expands `compile_options`; `show` funnels through it, so a bogus registered backend raises `evoxc.BackendError` (`unknown backend '<name>'; registered backends: numpy`) instead of silently running numpy.
The `BaseProblem` skeleton raises `NotImplementedError` from `evaluate`/`input_shape`/`output_shape`/`show`, while `show_details` is the documented no-op that `Pipeline.auto_run` may call on any problem.

## Known gaps (audit)
CartPole's default reset distribution is never bounded (only determinism/divergence), Pendulum's `_reset` is checked for shape/dtype only, and only MountainCar's reset interval is asserted independently.
MountainCar's `_advance` force clip (`clip(action, -1, 1)`) is never reached with `|action| > 1`: the policies only emit `tanh` values and the hand-built rows pass actions in `[-1, 1]`.
`test_prepared_rollout.py` pins the prepared pass at the CartPole call site only; the Pendulum/MountainCar `prepared_query` call sites are untested.
The `show` of a *finite* Pendulum/MountainCar policy is asserted only as part of the finite-safe pair (no absolute column values are pinned), and CartPole's `show` header for a `repeat_times > 1` policy is only reached through the NaN case.
`CustomFuncFit`'s `method="sample"` dataset distribution is only checked for reproducibility and in-box membership, not shape-by-shape against a second seeded draw.
The three RL `show`s are covered for a NaN policy; an *infinite* (non-NaN) return is not constructed, because the returns are bounded by construction.
`problem.func_fit.custom`'s `func(low_bounds)` validation is exercised through its error message only, never with a `func` that returns an array (the documented per-sample output contract).

## Conventions
Nothing imports `tensorneat`, `support` or `evoxc` at module scope: `../conftest.py` prepends `src/`, `benchmarks/legacy_jax` and `test/` to `sys.path` at collection time, so every input is a `scope="module"` fixture that imports inside its body.
Those imports are plain statements — the suite must never convert a broken or regressed module into a skip, so a green run here really executed every kernel it claims to.
Every graph runs through `support.runner` only, through the fixtures in `conftest.py`, never a module-scope import; `show`/`build_options`/the constructor checks are host-side and are called directly.
Shapes stay small (`pop <= 8`, `S <= 8`; horizons `max_step <= 50` for CartPole/func-fit, `<= 200` for Pendulum, and `999` only for MountainCar at population 1) and the backend is always `"numpy"`; no `jax`/`torch`, no network, no GPU, no display.
A `mape` case that divides by zero target emits `RuntimeWarning: divide by zero` from `evoxc`'s numpy divide; that module-level test carries `filterwarnings("ignore::RuntimeWarning")` so the suite's warning census stays at the parity modules' three.

## Constraints
A test may not edit `../../../src`, `../../../benchmarks` or `pyproject.toml`; a defect or a doc conflict found here goes into the report to the parent.
A src defect is never hidden: keep the real assertion and mark the test `@pytest.mark.xfail(strict=True, reason="src defect: …")`. No such xfail exists today.
Files stay under ~1000 lines: `test_cartpole.py` 883, `test_func_fit.py` 803, `test_mountaincar.py` 777, `test_pendulum.py` 769, `test_problem_api.py` 649, `test_custom.py` 472, `conftest.py` 335, `test_rl_common.py` 329, `test_prepared_rollout.py` 203.
`test_rl_common.py`'s 196 cases are cheap parametrizations of host-side validators (no graph is built), so its case count is large without affecting the directory's wall clock.
Suite output must be deterministic — CartPole randomness is driven by explicit integer `key_seed`s and `CustomFuncFit` by explicit `seed`s, never by the global numpy state; Pendulum and MountainCar likewise only ever pass an integer `key_seed` (never a literal drawn state) so a re-run reproduces every number.
`pytest.mark.slow` and `pytest.mark.parity` are not used here: every case is a batched `while_loop` over at most a few hundred float32 steps on populations of at most eight individuals (~6 s for the whole directory).
