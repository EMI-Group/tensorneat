# docs

## Intent
Sphinx site (autodoc + napoleon + viewcode, theme `sphinx_rtd_theme`) that renders the API of the `src/tensorneat` 0.2.0 tree; it documents the code, it does not replace the `tutorials/` notebooks or the top-level `README.md`.
Build command: `uv run --extra docs sphinx-build -W -b html docs docs/_build` (run `uv sync --extra docs` first; the `docs` extra in `pyproject.toml` is the source of truth).
`docs/requirements.txt` pins only the Sphinx toolchain (`sphinx >= 7.0`, `sphinx-rtd-theme`) and is not a build path: pip cannot install the package from it, because `evoxc >= 0.1.1` only resolves through `[tool.uv.sources]` and PyPI has no satisfying release.
`docs/_build/` is gitignored (`docs/_build/*` in `.gitignore`) and is never committed.
The CI gate is the `docs` job in `.github/workflows/ci.yaml`: `uv sync --extra docs` then the same `-W` build, so a warning fails the pipeline.
The hosted build is driven by the repo-root `.readthedocs.yaml`: ubuntu-24.04 + Python 3.12 (the `requires-python` floor is 3.11), `uv venv $READTHEDOCS_VIRTUALENV_PATH` then `uv sync --extra docs` into that venv — a plain `pip install .` cannot work because `evoxc >= 0.1.1` is resolved from a git tag whose metadata still says `0.1.0`.
RTD builds strictly: `sphinx.fail_on_warning: true`, and because the overridden `build.html` command replaces RTD's default (the place RTD injects its own `-W`), that command passes `-W` explicitly alongside `-T` (full traceback on exceptions, unrelated to warnings).

## API Surface
`docs/conf.py` holds no content: it puts `../src` (absolute, CWD-independent) on `sys.path` when that directory exists, reads `version`/`release` from `importlib.metadata.version("tensorneat")` with a `"0.2.0"` fallback, sets `copyright = "2026, Lishuang Wang"`, `autodoc_default_options = {members, show-inheritance, undoc-members: False}`, `extensions = [autodoc, napoleon, viewcode]`, `exclude_patterns = ["_build", ...]`, `html_theme = "sphinx_rtd_theme"`.
`docs/index.rst` is the front page: intent paragraph (NEAT/HyperNEAT tensorization on `evoxc`, no JAX/PyTorch), a backend paragraph (`numpy` default reference interpreter with no optional dependency, `iree` compiled and working end to end via `uv sync --extra iree` and still slower per generation on CPU, `xla` requires a user-supplied PJRT C API plugin `.so` located by `EVOXC_PJRT_PLUGIN` or by `Pipeline(compile_options={"plugin_path": ...})`, the option winning over the variable, `tvm` untested here), a second paragraph on the `device=` axis (a kind string or `evoxc.Device` forwarded to `evoxc.build` with tensors placed once after `setup`, the kind also selecting the accelerator kernel formulations, the measured accelerator record in `benchmarks/GPU.md`), a quickstart matching the real `Pipeline`/`algorithm.NEAT`/`problem.XOR` API (`setup()` builds nothing; the per-shape graph is compiled by the first `step`/`auto_run`), one paragraph on the `host_payload` knob (`True` default copies the four gene arrays to host numpy; `False` — constructor or per-call `step` — returns the payload as the backend left it and the reporting paths materialise it only on the generations that need it), one sentence naming the host-only `BaseGenomeHost.grad_from_payload` path, a "Running on an accelerator" section, an "API reference" toctree pointing at `source/modules`, and GitHub links to `README.md`, `benchmarks/RESULTS.md`, `benchmarks/BACKENDS.md`, `benchmarks/GPU.md`.
The "Running on an accelerator" section carries the two copy-pasteable recipes: `uv sync --extra iree` then `Pipeline(backend="iree", device="rocm", compile_options={"target_backends": ["rocm"]})`, and for XLA the `uv pip install --no-deps jax-rocm7-pjrt` step (after the sync — a later `uv sync` prunes it; the NVIDIA wheel is `jax-cuda12-pjrt` and the kind `"cuda"`), the `export EVOXC_PJRT_PLUGIN=$(uv run python -c "import sysconfig; print(sysconfig.get_paths()['purelib'])")/jax_plugins/xla_rocm7/xla_rocm_plugin.so` line, and `Pipeline(..., backend="xla", device="rocm")`.
The variable is mandatory on the pinned `evoxc`: its availability probe takes no options and reads only `EVOXC_PJRT_PLUGIN`, and the pinned tag scans `plugin_path` → that variable → a few well-known library directories, never `site-packages/jax_plugins` (a newer `evoxc` does, which the section states).
The section also carries one semantics sentence (host-side `setup` on CPU, one placement of the runtime tensors, nothing implicit, the per-shape compile excluded from every per-generation figure) and one headline span — 3.6–13.4 ms/generation on XLA-ROCm and 10.3–61.5 on IREE-ROCm against 43–965 on the reference interpreter, seed 42, six cases — with the matrix left to `benchmarks/GPU.md`.
The page has no install section and no link to `tutorials/quickstart.ipynb`, so installing (the plain `pip install tensorneat` path does not exist; `uv sync` or the git-pinned `evoxc` + `pip install --no-deps` are the only working ones) and the notebook are reachable only through the README link; the XLA recipe installs a PJRT plugin wheel, which is not a way to install this package.
`docs/source/modules.rst` is the API root and the only page `index.rst` links to; it toctrees the package root `tensorneat`.
`docs/source/tensorneat.problem.rl.*.rst` covers the three RL modules (`cartpole` → `CartPole`, `mountaincar` → `MountainCarContinuous`, `pendulum` → `Pendulum`), all three listed by the `tensorneat.problem.rl` package page.
`src/tensorneat/problem/rl/_common.py` is `_`-prefixed and therefore deliberately has no page.

## Constraints
The stub set mirrors `src/tensorneat`: one page per public module (`source/tensorneat.<module>.rst`) and one landing page per package/subpackage (`source/tensorneat.<pkg>.rst`); `_`-prefixed modules (`algorithm/neat/_keys.py`, `_kernels.py`, `_distance.py`, `_validation.py`; `problem/rl/_common.py`; the accelerator helpers are public, the `_`-prefixed ones stay private) get no page.
When `src/tensorneat` gains or loses a public module, add or delete the matching stub and its toctree entry in the enclosing package page plus that page's one-line intent — `find src/tensorneat -name '*.py' ! -name '__init__.py' ! -name '_*' | sort` versus `ls docs/source/*.rst` is the sync check.
The stub set is complete, accelerator pass included: every non-`_` module has one page, covering all seven `genome/operations/mutation/` modules (`arrays`, `base`, `cycle`, `cycle_accelerator`, `default`, `degree`, `plan`, `recurrent`), all seven `genome/operations/distance/` modules (`base`, `consts`, `default`, `dense`, `digest`, `grouped`, `index_free`, `layout`), the three `genome/operations/` accelerator and alignment modules (`alignment`, `alignment_accelerator`) and the three `problem/rl/` modules.
That is 89 pages: `modules.rst`, 18 package landing pages and 70 module pages (`find src/tensorneat -name '*.py' ! -name '__init__.py' ! -name '_*'` has 70 matches).
A package landing page's one-line intent names what the package really contains, not just its classes: the mutation page names the mutation contract, the structural write plan, both operators, the cycle predicate with its scatter-free accelerator spelling, the row toolkit they build on, and the diagnostic in-degree audit, because `degree.py` is an audit rather than an operator; the distance page names the grouped k-centre route and the `merge`/`index_free` formulations; the `common` page names the accelerator spelling of the schedule's two scatter writes and the `kernel_mode`/`KERNEL_MODES` static that selects it.
Module pages carry exactly one `.. automodule::` with `:members:` and `:show-inheritance:`; that page is the single place an object is documented, because every package `__init__.py` merely re-exports and a second registration makes each unqualified cross-reference ambiguous (and emits duplicate-object warnings).
`automodule :members:` renders only a module's `__all__` entries (`_`-prefixed names are skipped even when listed in `__all__`, which is why `host_payload.py`'s eleven `_`-helpers stay prose); `host_payload.rst` is therefore its module docstring plus `EVAL_CHUNK_ROWS`, `DEVICE_EVAL_CHUNK_BYTES`, `eval_chunk_rows` and `materialize_payload`.
An explicit directive appears only where the one `automodule` cannot be the sole registration, in two shapes: `.. autoattribute::` on `tensorneat.algorithm.hyperneat.genes.rst` (which excludes `HyperNEATConn.attr_specs` from `:members:`), and `.. autofunction::` on `tensorneat.common.tensorization.rst` for `derive_schedule`, whose `@evoxc.defn` wrapper is a `Defn` instance with `__module__ = "evoxc.trace.defn"`, so `automodule :members:` drops it as an imported member; that directive renders the wrapper's `(*args, **kwargs)` signature because `Defn` exposes no `__signature__`, so the page's `Args:` block is the real parameter list.
Adding an explicit directive for a name `automodule :members:` already registers fails `-W` with `duplicate object description of …, other instance in source/…` (verified with `EVAL_CHUNK_ROWS`), so a module whose only public name is one documented data attribute needs no second directive.
Package pages are pure landing pages: one sentence of intent plus a `:maxdepth: 4` toctree over subpackages/submodules, never an `automodule`.
When a class documents a member in its own `Attributes:` section, napoleon already emits an `.. attribute::` for it, so the module page excludes that name via `:exclude-members:` rather than hiding the object; for the `NamedTuple` scaffolds that means the whole field list (`distance/digest.py`, `distance/layout.py` — `marker_pad` included — and `distance/grouped.py`'s `GroupedDigest`), so a new field on any of them must be appended to that one sorted line or the build fails with `duplicate object description`.
`:exclude-members:` is the only suppression used: `suppress_warnings`, `nitpicky = False` and page-level `:no-index:` are not acceptable shortcuts.
Every page must stay reachable from `source/modules.rst`; an unreachable page warns `toc.not_included`, which `-W` turns into a failure.
Pages stay 5–20 lines; a page that needs more is documenting more than one thing.

## Known Issues
Two public-looking objects are absent from their module's `__all__`, so `automodule :members:` never registers them and a reader following the docs cannot find them.
`DEFAULT_GENOME_CONN_ADD = 0.4` and `DEFAULT_GENOME_CONN_DELETE = 0.05` live in `src/tensorneat/genome/operations/mutation/default.py` under an eight-line `#:` doc comment, but that module's `__all__ = ["DefaultMutation"]`; they are the connection gates every `DefaultGenome()`/`RecurrentGenome()` ships when no operator is passed, so the documented `DefaultMutation` defaults (`0.2`/`0.2`) are not the ones a plain pipeline uses.
`FamilyTerms` lives in `src/tensorneat/genome/operations/distance/dense.py` with a class docstring and an `Attributes:` section, but that module's `__all__ = ["enabled", "measure_centre"]`; it is the `NamedTuple` the private `_family_terms` helper returns, named only as plain text in that helper's `Returns:` block.
Both are visible today only in the `viewcode` module source, never as a documented object or a resolvable cross-reference; closing the gap is either a source-side `__all__` change or an explicit `autoattribute`/`autoclass` on the module page, and the non-nitpicky build reports neither.

## Test Strategy
Verification is the build itself, and it must start from a removed output directory: `rm -rf docs/_build && uv run --extra docs sphinx-build -W -b html docs docs/_build -w "$TMPDIR/w.log"` must exit 0 with an empty `$TMPDIR/w.log` (0 lines) and print `build succeeded.`; an incremental rebuild reuses the pickled doctree and can report 0 warnings even when a clean build fails.
Note the pipeline exit code: piping the build into `tail`/`tee` hides it, so capture the exit status of `sphinx-build` itself.
Spot-check the rendered API: `grep -o 'id="tensorneat.pipeline.Pipeline"' docs/_build/source/tensorneat.pipeline.html`, `grep -o 'id="tensorneat.genome.host.BaseGenomeHost"' docs/_build/source/tensorneat.genome.host.html`, `id="tensorneat.common.tensorization.derive_schedule"`, and confirm `docs/_build/index.html` shows the quickstart without leaking literal RST markup.
Spot-check the accelerator pages the same way: `id="tensorneat.common.schedule_accelerator.kernel_mode"`, `id="tensorneat.genome.operations.distance.grouped.GroupedDigest"`, `id="tensorneat.genome.operations.distance.index_free.resolve"`, `id="tensorneat.genome.operations.alignment_accelerator.homologous_pair_accelerator"`, `id="tensorneat.genome.operations.mutation.cycle_accelerator.closes_cycle_accelerator"`, and that all five are listed by their package landing pages.
Spot-check the RL pages the same way: `id="tensorneat.problem.rl.pendulum.Pendulum"`, `id="tensorneat.problem.rl.mountaincar.MountainCarContinuous"`, `id="tensorneat.problem.rl.cartpole.CartPole"`, and all three modules listed by `docs/_build/source/tensorneat.problem.rl.html`.
`uv sync --extra docs` must be run first; `uv` lives at `~/.local/bin/uv` and may not be on `PATH`.
The docs build itself is the release gate for this node; the test suite that runs beside it is described in the repo-root `CONTEXT.md`.
Nothing in the suite `xfail`s: `test/unit/algorithm/test_hyperneat.py::test_forward_reads_the_substrate_output_neurons` passes, because `HyperNEAT.forward` reads its output rows from `Transformed.output_slot` (the substrate's output keys `I .. I+O-1`), not from the last `num_outputs` node rows.
